## 1.什么是 XSS 攻击？

**记忆口诀：**「恶意脚本混进页面，三种类型记心间：存储、反射、DOM 型」

**核心要点：**
- XSS（Cross-Site Scripting）是跨站脚本攻击，本质是未过滤的恶意代码被浏览器当作可信脚本执行
- 分为存储型、反射型、DOM 型三种，区别在于恶意代码的存储位置和注入环节
- 危害包括窃取 Cookie/DOM 数据、破坏页面、流量劫持、DOS 攻击等

### 详细解答

XSS（Cross-Site Scripting，跨站脚本攻击）是一种**代码注入攻击**。攻击者将恶意脚本注入网站，使其在用户的浏览器中运行，从而窃取 Cookie、localStorage 等敏感信息，或冒充用户执行操作。

**本质原因：** 网站未对恶意代码进行过滤，恶意脚本与正常代码混合，浏览器无法区分哪些脚本是可信的，导致恶意代码被执行。

#### 攻击危害

| 危害类型 | 说明 |
| --- | --- |
| 数据窃取 | 获取 DOM、Cookie、localStorage 等页面数据 |
| 冒充用户 | 以用户身份调用接口执行操作 |
| 破坏页面 | 篡改 DOM 结构，影响用户体验 |
| 流量劫持 | 将链接指向恶意网站 |
| DOS 攻击 | 发送大量合理请求，占用服务器资源 |

#### 三种 XSS 类型对比

| 类型 | 恶意代码存储位置 | 注入环节 | 常见场景 |
| --- | --- | --- | --- |
| **存储型** | 目标服务器数据库 | 服务端拼接 HTML 返回 | 论坛发帖、商品评论、私信 |
| **反射型** | URL 参数中 | 服务端从 URL 取出并拼入 HTML | 搜索、跳转、带参链接 |
| **DOM 型** | URL 参数中 | 前端 JS 取出并执行 | 前端路由、innerHTML 拼接 |

#### 攻击步骤

**存储型 XSS：**
1. 攻击者将恶意代码提交到目标网站数据库
2. 用户访问时，服务端从数据库取出并拼入 HTML 返回
3. 浏览器解析执行，恶意代码一并执行
4. 恶意代码窃取数据或冒充用户操作

**反射型 XSS：**
1. 攻击者构造含恶意代码的特殊 URL
2. 用户打开 URL，服务端从 URL 取出恶意代码拼入 HTML
3. 浏览器解析执行恶意代码
4. 与存储型的区别：恶意代码存在 URL 中，不在数据库

**DOM 型 XSS：**
1. 攻击者构造含恶意代码的特殊 URL
2. 用户打开 URL，前端 JS 从 URL 取出恶意代码并执行
3. 与反射型的区别：取出和执行均由**浏览器端**完成，属于前端 JS 安全漏洞，而非服务端漏洞

### 面试追问

1. **存储型和反射型 XSS 的核心区别是什么？** 存储型 XSS 的恶意代码持久化存储在目标服务器数据库中，任何访问相关页面的用户都可能触发；反射型 XSS 的恶意代码存在于 URL 参数中，需要用户主动点击恶意链接才会触发，不会持久存储在服务器上。反射型通常需要结合钓鱼、社工等手段诱导用户点击。

2. **DOM 型 XSS 为什么归类为前端漏洞？** 因为 DOM 型 XSS 的整个攻击链路（从 URL 读取恶意代码到执行）完全发生在浏览器端，不经过服务端处理。例如 `location.hash` 被直接写入 `innerHTML`，服务端即使做了转义也无法防御，必须由前端在数据渲染和字符串拼接时做安全处理。

## 2.如何防御 XSS 攻击？

**记忆口诀：**「转义输出 + CSP 白名单 + HttpOnly Cookie，三层防线挡 XSS」

**核心要点：**
- 输入输出转义：对插入 HTML 的内容做充分转义，DOM 型需在前端渲染时判断
- CSP（内容安全策略）：建立白名单，限制可加载和执行的外部资源
- 敏感信息保护：Cookie 设 HttpOnly、使用验证码防止脚本冒充用户

### 详细解答

XSS 危害极大，防御需要从**输入输出处理**、**浏览器策略**和**敏感信息保护**三个层面入手。

#### 1. 输入输出转义

| 防御方式 | 说明 |
| --- | --- |
| 纯前端渲染 | 不使用服务端拼接 HTML（避免 SSR 拼接注入） |
| 输出转义 | 对插入 HTML 的代码做 HTML 实体转义（`<` → `&lt;` 等） |
| DOM 型防御 | 前端获取、渲染、拼接字符串时，判断并过滤恶意代码 |

```js
// 简单转义示例
function escapeHtml(str) {
  return str
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;')
}
```

#### 2. CSP（Content Security Policy，内容安全策略）

CSP 本质是建立**白名单**，告诉浏览器哪些外部资源可以加载和执行，从而阻止恶意脚本注入。

**开启方式：**
- HTTP 响应头：`Content-Security-Policy: default-src 'self'`
- HTML meta 标签：`<meta http-equiv="Content-Security-Policy" content="default-src 'self'">`

配置规则后，拦截由浏览器自动完成，无需手动处理每个请求。

#### 3. 敏感信息保护

- **HttpOnly Cookie**：设置 Cookie 的 `HttpOnly` 属性，JS 无法读取，防止脚本窃取
- **验证码**：关键操作要求验证码，防止脚本冒充用户执行操作
- **SameSite Cookie**：限制第三方站点携带 Cookie

#### 防御策略总结

```
用户输入 → 服务端校验 + 转义 → 前端渲染时再转义
         ↓
      CSP 白名单限制脚本来源
         ↓
      HttpOnly 保护 Cookie，验证码保护关键操作
```

### 面试追问

1. **CSP 和输入转义有什么区别？各自适用什么场景？** 输入转义是**被动防御**，针对已知注入点逐处处理，适合精确控制输出内容；CSP 是**主动防御**，从浏览器层面限制脚本来源，即使存在遗漏的注入点，外部恶意脚本也无法执行。两者应配合使用：转义处理已知风险，CSP 兜底未知风险。

2. **为什么 HttpOnly 不能单独防御 XSS？** HttpOnly 只能防止 JS 读取 Cookie，但 XSS 攻击不仅限于窃取 Cookie。攻击者仍可通过 XSS 直接以用户身份发起请求（浏览器会自动携带 Cookie）、篡改页面 DOM、进行钓鱼欺骗等。HttpOnly 是重要补充手段，不能替代输入转义和 CSP。

## 3.什么是 CSRF 攻击？

**记忆口诀：**「借你 Cookie 冒充你，跨站伪造请求来攻击」

**核心要点：**
- CSRF（Cross-Site Request Forgery）是跨站请求伪造，利用用户已登录状态冒充用户发请求
- 本质是 Cookie 会在同源请求中自动携带，第三方站点可借此绕过身份验证
- 常见类型：GET 型（img 标签）、POST 型（隐藏表单）、链接型（a 标签）

### 详细解答

CSRF（Cross-Site Request Forgery，跨站请求伪造）是指攻击者诱导用户进入第三方网站，该网站向被攻击网站发送跨站请求。若用户在被攻击网站中已保存登录状态，攻击者可利用该状态绕过后台验证，**冒充用户**向服务器执行操作。

**本质：** 利用 Cookie 会在同源请求中自动携带发送给服务器的特性，实现用户冒充。

#### 攻击前提

1. 用户已登录目标网站，浏览器存有有效 Cookie
2. 用户被诱导访问攻击者控制的页面
3. 目标接口未做 CSRF 防护

#### 三种常见攻击类型

| 类型 | 实现方式 | 触发条件 |
| --- | --- | --- |
| **GET 型** | `<img src="https://bank.com/transfer?to=hacker&amount=1000">` | 用户打开含恶意 img 的页面 |
| **POST 型** | 隐藏自动提交的 `<form action="https://bank.com/transfer">` | 用户进入含隐藏表单的页面 |
| **链接型** | `<a href="https://bank.com/transfer?...">点击领奖</a>` | 用户点击恶意链接 |

#### 攻击流程

```
1. 用户登录 bank.com，浏览器保存 Session Cookie
2. 用户访问 attacker.com（邮件/广告诱导）
3. attacker.com 页面自动向 bank.com 发起转账请求
4. 浏览器自动携带 bank.com 的 Cookie
5. bank.com 验证 Cookie 有效，执行转账操作
```

### 面试追问

1. **CSRF 和 XSS 有什么本质区别？** XSS 是**注入恶意脚本**到目标网站页面中执行，攻击发生在目标站点内；CSRF 是**利用用户身份**在第三方站点发起对目标网站的请求，目标网站页面本身未被篡改。XSS 能读取 Cookie（非 HttpOnly），CSRF 只能利用 Cookie 自动携带的特性，无法读取 Cookie 内容。

2. **为什么 GET 型 CSRF 仍然有效？很多接口不是要求 POST 吗？** 历史上许多 Web 应用未严格区分 GET/POST 语义，敏感操作（如删除、转账）可能通过 GET 完成；此外 RESTful 设计不当也会导致状态变更接口接受 GET。现代开发应遵循「GET 幂等、POST 变更」原则，但仅靠 HTTP 方法区分不足以防御 CSRF，仍需 Token 等机制。

## 4.如何防御 CSRF 攻击？

**记忆口诀：**「同源检测、CSRF Token、双重 Cookie、SameSite 四件套」

**核心要点：**
- 同源检测：校验 Origin/Referer 请求头，过滤非法来源
- CSRF Token：服务端下发随机 Token，请求时携带并验证
- 双重 Cookie：Cookie + URL 参数双重验证，攻击者无法读取 Cookie
- SameSite Cookie：限制 Cookie 在跨站请求中携带

### 详细解答

#### 四种防御方案对比

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **同源检测** | 校验 Origin/Referer | 实现简单 | Referer 可伪造；会屏蔽搜索引擎来源 |
| **CSRF Token** | 请求携带服务端随机 Token | 安全性高 | 需全站加 Token；分布式 session 需额外处理 |
| **双重 Cookie** | Cookie 值与 URL 参数比对 | 无需 session 存储 | XSS 存在时失效；无法隔离子域 |
| **SameSite** | 限制跨站 Cookie 携带 | 浏览器原生支持 | Strict 模式影响外链跳转体验 |

#### 1. 同源检测

服务器根据请求头中的 `Origin` 或 `Referer` 判断请求来源是否合法：

```
Origin: https://trusted-site.com  → 允许
Referer 缺失且 Origin 缺失        → 拒绝
Referer 来自搜索引擎              → 通常放行（但也可能被利用）
```

#### 2. CSRF Token

```html
<!-- 服务端渲染时嵌入 Token -->
<form action="/transfer" method="POST">
  <input type="hidden" name="csrf_token" value="随机Token值" />
  <button type="submit">转账</button>
</form>
```

服务端验证：请求中的 Token 与 session 中存储的 Token 一致才放行。

#### 3. 双重 Cookie 验证

1. 用户访问时，服务端向域名注入 Cookie（随机字符串）
2. 发起请求时，从 Cookie 取出该值，放入 URL 参数或请求头
3. 服务端比对 Cookie 值与参数值是否一致

利用攻击者只能**利用** Cookie、无法**读取** Cookie 的特点。

#### 4. SameSite Cookie

| 模式 | 行为 |
| --- | --- |
| **Strict** | Cookie 在任何跨站请求中都不携带 |
| **Lax**（默认） | 仅顶级导航 GET 请求（如链接跳转）可携带 |

```http
Set-Cookie: session=abc; SameSite=Strict; Secure; HttpOnly
```

#### 最佳实践

生产环境通常**组合使用**：SameSite=Lax 作为基础防护 + CSRF Token 保护敏感操作 + Origin 校验作为补充。

### 面试追问

1. **CSRF Token 在分布式/负载均衡环境下怎么解决？** 传统方案将 Token 存在 session 中，请求被转发到无该 session 的服务器时会验证失败。解决方案：① 改用 JWT 等无状态 Token，不依赖 session；② 将 Token 存储在 Redis 等共享存储；③ 改用双重 Cookie 方案，Token 存在客户端 Cookie 中，不依赖服务端 session。

2. **SameSite=Strict 和 Lax 怎么选？** Lax 是大多数浏览器的默认值，允许从外部链接点击进入时携带 Cookie（如邮件中的链接），用户体验较好；Strict 完全禁止跨站携带，安全性最高，但用户从外部链接进入时需要重新登录。金融类高安全场景用 Strict，普通 Web 应用 Lax 通常足够，配合 CSRF Token 保护写操作。

## 5.什么是中间人攻击？如何防范中间人攻击？

**记忆口诀：**「通信两端以为直连，中间有人偷梁换柱；HTTPS 证书是王道」

**核心要点：**
- MITM 攻击者分别与通信两端建立连接，拦截并篡改传输数据
- 典型场景：伪造公钥、SSL 剥离、公共 Wi-Fi 嗅探
- 防范核心：HTTPS、证书校验、避免公共 Wi-Fi、不忽略浏览器警告

### 详细解答

中间人攻击（Man-in-the-Middle Attack，MITM）是指攻击者与通信两端分别建立独立联系并交换数据，使两端误以为在直接通信，实际上整个会话被攻击者完全控制。

#### 攻击过程（以 HTTPS 为例）

```
正常流程：
  客户端 ←──公钥──→ 服务端
  客户端 ──加密数据──→ 服务端

MITM 攻击流程：
1. 客户端请求服务端，被中间人截获
2. 服务端发送公钥，被中间人截获
3. 中间人保留真实公钥，向客户端发送伪造公钥
4. 客户端用伪造公钥加密数据，发给中间人
5. 中间人用伪造私钥解密，获得明文
6. 中间人用真实公钥重新加密，发给服务端
7. 两端均 unaware，中间人可读写全部通信内容
```

#### 常见攻击手段

| 手段 | 说明 |
| --- | --- |
| SSL 剥离 | 将 HTTPS 降级为 HTTP，明文传输 |
| 伪造证书 | 自签 CA 证书，欺骗客户端信任 |
| ARP 欺骗 | 局域网内冒充网关 |
| DNS 劫持 | 将域名解析到攻击者服务器 |
| 恶意 Wi-Fi 热点 | 公共热点嗅探流量 |

#### 防范措施

1. **全站 HTTPS**：确保访问的每个网站都使用 HTTPS，防止 SSL 剥离
2. **不忽略证书警告**：浏览器提示证书异常时，绝不继续访问
3. **避免公共 Wi-Fi**：必须使用时应配合 VPN 加密通道
4. **HSTS**：`Strict-Transport-Security` 响应头强制浏览器只用 HTTPS 访问
5. **证书固定（Certificate Pinning）**：客户端只信任特定证书/公钥
6. **及时更新系统与浏览器**：修复已知安全漏洞

#### HTTPS 如何防御 MITM

HTTPS 通过 **CA 证书体系** 验证服务器身份：浏览器内置受信任 CA 列表，服务端证书由 CA 签发，客户端验证证书链完整性。攻击者的自签证书不在受信任列表中，浏览器会发出警告。

### 面试追问

1. **HTTPS 一定能防止中间人攻击吗？什么情况下 HTTPS 也会失效？** 不能绝对保证。以下情况 HTTPS 可能失效：① 用户忽略证书警告继续访问；② 设备被植入恶意根证书（企业代理、恶意软件）；③ 攻击者获取了合法域名的证书（如 CA 被攻破）；④ SSL 剥离攻击成功将连接降级为 HTTP。因此 HTTPS 需配合 HSTS、用户安全意识共同防御。

2. **HSTS 是什么？它如何增强 HTTPS 安全性？** HSTS（HTTP Strict Transport Security）是服务端通过响应头 `Strict-Transport-Security: max-age=31536000; includeSubDomains` 告知浏览器：在指定时间内，该域名只能通过 HTTPS 访问，禁止 HTTP 降级。即使攻击者尝试 SSL 剥离，浏览器也会拒绝 HTTP 连接，直接强制 HTTPS，从而关闭 MITM 中常见的降级攻击入口。

## 6.有哪些可能引起前端安全的问题?

**记忆口诀：**「XSS 注入、iframe 滥用、CSRF 伪造、第三方库埋雷」

**核心要点：**
- XSS：未过滤用户输入导致恶意脚本执行
- iframe 滥用：第三方内容不受控，可运行脚本/弹窗
- CSRF：利用已认证用户身份发起非预期请求
- 恶意第三方库：npm 依赖被植入恶意代码

### 详细解答

前端安全威胁来源多样，以下是四类最常见的问题：

#### 1. 跨站脚本（XSS）

一种代码注入方式，因与 CSS 缩写冲突而称 XSS（Cross-Site Scripting）。攻击者将恶意脚本注入页面，其他用户浏览时脚本被执行。

- **注入载体**：JavaScript、HTML、CSS、Flash 等
- **常见场景**：论坛发帖、评论区、搜索框、URL 参数
- **根本原因**：服务端/前端未对用户输入做严格限制和转义

#### 2. iframe 滥用

iframe 内容来自第三方，默认不受主站控制：

| 风险 | 说明 |
| --- | --- |
| 脚本执行 | iframe 内可运行任意 JavaScript |
| 弹窗劫持 | Flash 插件、弹出对话框 |
| 点击劫持 | 透明 iframe 覆盖诱骗用户点击 |
| 钓鱼页面 | 嵌入伪造的登录表单 |

**防御**：设置 `sandbox` 属性限制 iframe 能力，使用 CSP 的 `frame-ancestors` 限制嵌入。

#### 3. 跨站请求伪造（CSRF）

攻击者设置陷阱，强制已认证用户执行非预期的状态变更操作（转账、改密码、发邮件等），属于**被动攻击**——用户无需主动输入，只需保持登录状态并访问恶意页面。

#### 4. 恶意第三方库

现代前端开发大量依赖 npm 等包管理器的第三方库：

- 供应链攻击：维护者账号被盗，发布含恶意代码的新版本
- 恶意包：仿冒知名包名（typosquatting）
- 间接依赖：深层依赖中的恶意代码难以察觉

**防御措施**：
- 锁定依赖版本（lock 文件）
- 使用 `npm audit` / Snyk 等安全扫描工具
- 审查高权限依赖（如 postinstall 脚本）
- 优先选择维护活跃、下载量大的知名库

### 面试追问

1. **iframe 的 sandbox 属性有哪些常用值？** 常用值包括：`allow-scripts`（允许 JS）、`allow-same-origin`（允许同源访问）、`allow-forms`（允许表单提交）、`allow-popups`（允许弹窗）。不加任何值时 sandbox 最严格，禁止脚本、表单、弹窗等。典型用法：`<iframe sandbox="allow-scripts allow-same-origin" src="...">`，在允许必要功能的同时限制危险操作。

2. **如何防范 npm 供应链攻击？** ① 使用 lock 文件锁定精确版本，避免自动升级；② 定期运行 `npm audit` 检查已知漏洞；③ 审查 package.json 中的 postinstall/preinstall 脚本；④ 使用 npm 的 `--ignore-scripts` 安装后再手动审查；⑤ 启用 Dependabot 等自动化依赖更新与安全告警；⑥ 对关键依赖做 checksum 校验。

## 7.网络劫持有哪几种，如何防范？

**记忆口诀：**「DNS 劫持改解析，HTTP 劫持加广告；全站 HTTPS 是良方」

**核心要点：**
- DNS 劫持：篡改域名解析，将用户导向错误 IP（如输入京东跳转淘宝）
- HTTP 劫持：明文传输被运营商篡改响应内容（如插入广告）
- 防范核心：全站 HTTPS 加密，DNS 劫持还需 DNSSEC/DoH 等

### 详细解答

网络劫持指攻击者或运营商在用户与目标服务器通信过程中，篡改或插入内容。

#### 两种主要劫持类型

| 类型 | 原理 | 典型表现 |
| --- | --- | --- |
| **DNS 劫持** | 篡改 DNS 解析结果 | 输入 jd.com 跳转到 taobao.com |
| **HTTP 劫持** | 篡改 HTTP 明文响应 | 访问 Google 出现贪玩蓝月广告 |

#### DNS 劫持的两种方式

1. **DNS 强制解析**：修改运营商本地 DNS 记录，将用户流量引导到缓存/广告服务器
2. **302 跳转**：监控网络出口流量，对可劫持的内容返回 302 跳转，引导用户到指定页面

#### HTTP 劫持

由于 HTTP 是**明文传输**，运营商或中间节点可以：
- 读取响应内容
- 在 HTML 中插入广告脚本
- 替换页面中的资源链接

#### 防范措施

| 劫持类型 | 防范方案 |
| --- | --- |
| **DNS 劫持** | DNSSEC 验证、DoH/DoT 加密 DNS 查询、使用可信 DNS（8.8.8.8） |
| **HTTP 劫持** | **全站 HTTPS**（最有效），明文无法被篡改 |
| **通用** | VPN 加密全部流量、HSTS 强制 HTTPS |

**为什么 HTTPS 能防 HTTP 劫持？** HTTPS 对传输内容加密，运营商无法获取明文，自然无法插入广告或篡改内容。这也是现代 Web 推动全站 HTTPS 的重要原因之一。

> 注：DNS 劫持因涉嫌违法，目前已受监管，相对较少；HTTP 劫持在纯 HTTP 站点上仍然普遍。

### 面试追问

1. **DoH 和 DoT 是什么？它们如何防止 DNS 劫持？** DoH（DNS over HTTPS）和 DoT（DNS over TLS）都是加密 DNS 查询的协议。传统 DNS 查询是明文 UDP，易被劫持或监听；DoH 通过 HTTPS 传输 DNS 请求，DoT 通过 TLS 传输，中间人无法篡改或窃听 DNS 响应，从而防止 DNS 劫持。Chrome、Firefox 等浏览器已支持 DoH。

2. **HTTPS 能防止 DNS 劫持吗？** HTTPS 本身**不能**防止 DNS 劫持——如果 DNS 被劫持到攻击者 IP，HTTPS 握手时会发现证书不匹配并报警，但用户可能忽略警告。HTTPS 防的是 HTTP 内容劫持和 MITM 内容篡改。防 DNS 劫持需要 DNSSEC、DoH/DoT 等 DNS 层方案，两者需配合使用。

## 8.进程与线程的概念

**记忆口诀：**「进程是资源容器，线程是执行单元；CPU 时间片上的两个维度」

**核心要点：**
- 进程是资源分配的最小单位，线程是 CPU 调度的最小单位
- 进程是程序的运行实例，拥有独立的虚拟内存空间
- 线程是进程内的执行单元，共享进程资源

### 详细解答

从本质上说，进程和线程都是 CPU 工作时间片的描述，但抽象层次不同：

| 概念 | 定义 | 类比 |
| --- | --- | --- |
| **进程** | 程序的运行实例，资源分配的最小单位 | 一个工厂 |
| **线程** | 进程内的执行单元，CPU 调度的最小单位 | 工厂里的工人 |

#### 进程的组成

启动程序时，操作系统会创建一块内存，包含：
- **代码段**：程序指令
- **数据段**：运行中的数据
- **主线程**：执行任务的线程

这个完整的运行环境称为**进程**。进程运行在**虚拟内存**上——操作系统为每个进程提供独立的虚拟地址空间，解决有限物理内存与无限需求之间的矛盾。

#### 进程与线程的四个关系特点

1. **线程崩溃 → 进程崩溃**：进程中任意线程执行出错，都会导致整个进程崩溃
2. **共享数据**：同一进程内的线程共享进程的数据（堆内存、全局变量等）
3. **内存回收**：进程退出时，操作系统回收所有资源；即使线程内存泄漏，进程退出后也会被回收
4. **进程隔离**：不同进程的内容相互隔离，一个进程崩溃不影响其他进程

#### Chrome 多进程架构

Chrome 采用多进程架构提升稳定性与安全性：

| 进程 | 职责 |
| --- | --- |
| **浏览器进程** | 界面显示、用户交互、子进程管理、存储 |
| **渲染进程** | HTML/CSS/JS 渲染，Blink + V8 运行于此，每 Tab 默认一个 |
| **GPU 进程** | 3D CSS、UI 绘制等 GPU 加速 |
| **网络进程** | 页面网络资源加载 |
| **插件进程** | 插件运行隔离，防止插件崩溃影响浏览器 |

打开一个网页，最少需要 **4 个进程**：1 网络 + 1 浏览器 + 1 GPU + 1 渲染。有插件则再加 1 个。

**多进程代价**：更高内存占用（每个进程含 JS 运行环境副本）、架构更复杂。

### 面试追问

1. **为什么 Chrome 采用多进程而不是多线程架构？** 主要是**稳定性**和**安全性**。多进程利用操作系统进程隔离，一个 Tab 的渲染进程崩溃不影响其他 Tab 和浏览器主进程；渲染进程运行在沙箱中，限制了恶意代码对系统的访问。多线程共享内存，一个线程崩溃可能导致整个进程崩溃，隔离性不如多进程。

2. **虚拟内存解决了什么问题？** 虚拟内存让每进程拥有独立的虚拟地址空间，带来三个好处：① 进程间内存隔离，互不干扰；② 可以使用超过物理内存大小的地址空间（通过交换文件/page fault）；③ 简化编程模型，程序无需关心物理内存布局。同一物理地址在不同进程中可映射到不同虚拟地址。

## 9.进程和线程的区别

**记忆口诀：**「进程管资源，线程管调度；进程要通信，线程享内存」

**核心要点：**
- 进程是独立应用，线程从属于进程
- 进程拥有独立资源，线程共享进程资源
- 进程切换开销大，线程切换开销小

### 详细解答

| 对比维度 | 进程 | 线程 |
| --- | --- | --- |
| **定义** | 资源分配的最小单位 | CPU 调度的最小单位 |
| **独立性** | 独立应用，有独立地址空间 | 不能独立存在，依附于进程 |
| **资源** | 拥有独立的内存、文件句柄等 | 共享所属进程的堆、全局变量等 |
| **通信** | 需 IPC（管道、消息队列、共享内存等） | 可直接共享进程内资源 |
| **切换开销** | 大（需切换页表、保存/恢复 CPU 环境） | 小（只需保存/恢复少量寄存器） |
| **创建/销毁** | 开销大（分配/回收内存、I/O 等） | 开销小 |
| **崩溃影响** | 进程间隔离，不影响其他进程 | 一个线程崩溃可能导致整个进程崩溃 |
| **调度** | 进程切换会引起线程切换 | 线程切换不引起进程切换 |

#### 深入理解

**资源角度**：进程是「拥有资源」的基本单位，线程是「使用资源」的基本单位。线程不拥有资源，但可以访问进程的资源。

**调度角度**：线程是 CPU 调度的基本单位。同一进程的多个线程可并发执行，但同一时刻一个 CPU 核心只执行一个线程。

**通信角度**：线程间通信简单（共享变量 + 锁），但需处理线程安全问题；进程间通信复杂（需内核介入），但隔离性更好。

**开销角度**：创建进程需要分配内存、建立页表、初始化 PCB；创建线程只需分配栈空间和线程控制块。进程切换涉及虚拟地址空间切换（TLB 刷新），线程切换在同一地址空间内，开销远小于进程切换。

### 面试追问

1. **多线程相比多进程有什么优势和劣势？** 优势：① 创建和切换开销小；② 线程间共享数据方便，无需 IPC；③ 适合 I/O 密集型任务并发。劣势：① 线程安全问题（竞态、死锁）；② 一个线程崩溃可能导致整个进程崩溃；③ 无法利用多核隔离性做安全沙箱。选择取决于场景：需要隔离用多进程，需要高效通信用多线程。

2. **用户线程和内核线程有什么区别？** 内核线程（Kernel Thread）由操作系统内核直接调度，是 CPU 调度的实体；用户线程（User Thread）在用户空间由线程库管理，内核无感知。多对一模型（多个用户线程映射一个内核线程）切换快但无法利用多核；一对一模型（每个用户线程对应一个内核线程）如 Linux pthread，可真正并行但创建开销大。

## 10.浏览器渲染进程的线程有哪些

**记忆口诀：**「GUI 渲染、JS 引擎、事件触发、定时器、XHR 请求，五大线程各司其职」

**核心要点：**
- 渲染进程包含 5 种线程：GUI 渲染、JS 引擎、事件触发、定时器、异步 HTTP 请求
- GUI 渲染线程与 JS 引擎线程**互斥**，JS 执行时 GUI 更新被挂起
- 定时器由独立线程计时，到期后将回调放入事件队列

### 详细解答

浏览器渲染进程（单个 Tab）内部包含 **5 种线程**：

| 线程 | 职责 | 注意事项 |
| --- | --- | --- |
| **GUI 渲染线程** | 解析 HTML/CSS，构建 DOM/CSSOM/渲染树，绘制页面 | 与 JS 引擎线程互斥 |
| **JS 引擎线程** | 解析执行 JavaScript（V8） | 单 Tab 只有一个，单线程 |
| **事件触发线程** | 管理事件循环，将事件回调放入任务队列 | 属于浏览器，非 JS 引擎 |
| **定时器触发线程** | setTimeout/setInterval 的计时 | 独立计时，到期放入事件队列 |
| **异步 HTTP 请求线程** | XMLHttpRequest / fetch 的网络请求 | 状态变更时将回调放入事件队列 |

#### 1. GUI 渲染线程

- 负责渲染浏览器页面
- 解析 HTML → DOM 树，解析 CSS → CSSOM 树 → 渲染树 → 布局 → 绘制
- 触发重绘（repaint）和回流（reflow）时执行
- **与 JS 引擎线程互斥**：JS 执行时 GUI 线程挂起，GUI 更新保存在队列中等待 JS 空闲

#### 2. JS 引擎线程

- 也称为 JS 内核，负责解析和执行 JavaScript
- 一个 Tab 页中**永远只有一个** JS 引擎线程在运行
- JS 执行时间过长 → 页面渲染不连贯 → 页面加载阻塞

#### 3. 事件触发线程

- 属于浏览器而非 JS 引擎，控制事件循环
- 当 JS 执行 setTimeout、或浏览器内核其他线程（鼠标点击、AJAX 等）产生事件时，将任务添加到事件队列
- 事件触发后，放入待处理队列队尾，等待 JS 引擎空闲时执行

#### 4. 定时器触发线程

- setInterval 与 setTimeout 所在的线程
- 浏览器定时器**不由 JS 引擎计时**（JS 单线程阻塞会影响计时准确性）
- 独立线程计时，到期后将回调放入事件队列
- **W3C 规定**：定时器最小间隔 4ms（小于 4ms 按 4ms 处理）
- 定时器回调在设定时间点**不一定准时执行**，只是在该时间点将任务加入队列

#### 5. 异步 HTTP 请求线程

- XMLHttpRequest 连接后，浏览器新开线程发起请求
- 检测到状态变更时，若有回调函数，产生状态变更事件，将回调放入事件队列
- 等待 JS 引擎空闲后执行

#### 线程协作关系

```
GUI 渲染线程 ←──互斥──→ JS 引擎线程
                              ↑
              事件触发线程 ────┤  任务队列
              定时器线程 ──────┤
              XHR 线程 ────────┘
```

### 面试追问

1. **为什么 GUI 渲染线程和 JS 引擎线程是互斥的？** 因为 JavaScript 可以操作 DOM（如 `document.getElementById().style.color = 'red'`），如果 JS 执行和 GUI 渲染同时进行，可能出现 JS 修改 DOM 的同时渲染线程也在读取/绘制 DOM，导致渲染结果不一致（脏读）。互斥保证了 JS 操作 DOM 时渲染暂停，JS 执行完毕后渲染线程再统一处理积累的 GUI 更新。

2. **setTimeout(fn, 0) 是立即执行吗？** 不是。`0` 表示「尽快执行」，实际流程是：定时器线程计时 0ms 后将回调放入**宏任务队列**，需等待当前同步代码和所有微任务执行完毕后，JS 引擎空闲时才执行。W3C 还规定最小间隔为 4ms，所以 `setTimeout(fn, 0)` 实际延迟至少 4ms。

## 11.进程之间的通信方式

**记忆口诀：**「管道消息信号量，共享内存套接字，六种 IPC 记清楚」

**核心要点：**
- 进程隔离导致无法直接共享数据，需 IPC 机制通信
- 常见方式：管道、消息队列、信号量、信号、共享内存、套接字
- 共享内存最快但需信号量同步；套接字可跨主机通信

### 详细解答

由于进程之间内存严格隔离，需要通过**进程间通信（IPC）** 机制交换数据。

#### 六种 IPC 方式对比

| 方式 | 特点 | 适用场景 |
| --- | --- | --- |
| **管道** | 单向、血缘进程、字节流 | 父子进程简单数据传递 |
| **消息队列** | 消息列表、有类型、异步 | 进程间结构化消息传递 |
| **信号量** | 计数器、互斥与同步 | 共享内存的访问控制 |
| **信号** | 异步通知、预定义事件 | 进程间事件通知（如 SIGKILL） |
| **共享内存** | 最快、多进程映射同一块内存 | 大量数据高速交换 |
| **套接字** | 可跨主机、基于网络 | 网络通信（HTTP 底层） |

#### 1. 管道（Pipe）

操作系统在内核中开辟一段**缓冲区**：
- 进程 A 写入数据 → 缓冲区 → 进程 B 读取
- **单向通信**，只能血缘关系进程使用
- 生命周期随进程，内部提供同步机制

#### 2. 消息队列（Message Queue）

- 消息的链表/list，进程可添加/读取消息
- 每个消息有**类型**，接收方可按类型独立接收
- 避免管道的同步阻塞问题
- 缺点：消息有最大长度限制，频繁通信需频繁拷贝内存

#### 3. 信号量（Semaphore）

- 本质是一个**计数器**，实现进程间互斥与同步
- 例：初始值 1，进程 A 访问共享资源时值变 0，进程 B 看到 0 则阻塞等待
- 通常与共享内存配合使用

#### 4. 信号（Signal）

- Unix 最古老的 IPC 方式
- 操作系统通知进程发生了预定义事件（如 SIGTERM 终止、SIGINT 中断）
- 异步、原始的通知机制

#### 5. 共享内存（Shared Memory）

- 映射一段可被多个进程访问的内存
- **最快的 IPC 方式**，因为数据不需要拷贝
- 需配合信号量解决多进程竞争问题（类似线程安全）

#### 6. 套接字（Socket）

- 前面五种都是同一主机上的进程通信
- Socket 可实现**跨主机**通信
- 浏览器发起 HTTP 请求 → 服务器返回数据，底层就是 Socket 通信

### 面试追问

1. **共享内存为什么最快，还需要信号量？** 共享内存最快是因为进程直接读写同一块物理内存，无需内核拷贝数据（管道/消息队列每次通信都要拷贝）。但多进程同时读写共享内存会产生竞态条件（类似多线程问题），信号量作为互斥锁，保证同一时刻只有一个进程访问临界区，确保数据一致性。

2. **浏览器中哪些场景用到了进程间通信？** Chrome 多进程架构中大量用到 IPC：① 渲染进程与浏览器主进程通信（如 JS 调用 window.alert）；② 渲染进程与 GPU 进程通信（渲染指令传递）；③ 渲染进程与网络进程通信（资源请求）；④ 插件进程与浏览器进程通信。Chrome 使用 Mojo IPC 框架实现高效的跨进程通信。

## 12.僵尸进程和孤儿进程是什么？

**记忆口诀：**「父走子留叫孤儿，子走父不管变僵尸；init 收养孤儿，父进程要 wait 收僵尸」

**核心要点：**
- 孤儿进程：父进程先退出，子进程被 init（PID=1）收养
- 僵尸进程：子进程先退出，父进程未回收其资源，进程描述符仍残留
- 僵尸进程占用 PID，大量积累会耗尽系统进程表

### 详细解答

| 概念 | 产生条件 | 处理方式 | 危害 |
| --- | --- | --- | --- |
| **孤儿进程** | 父进程退出，子进程仍在运行 | 被 init 进程（PID=1）收养，由 init 回收 | 无危害，系统自动处理 |
| **僵尸进程** | 子进程退出，父进程未调用 wait/waitpid | 进程描述符（PCB）残留在进程表中 | 占用 PID，大量积累可耗尽进程表 |

#### 孤儿进程

```
父进程(PPID=100) ──fork──→ 子进程(PPID=100)
父进程退出
子进程(PPID=100) → 被 init(PID=1) 收养 → PPID 变为 1
init 负责收集子进程退出状态
```

- 孤儿进程会被 **init 进程**（Linux 中 PID 为 1）收养
- init 会定期调用 wait 回收其退出状态
- 对系统无危害

#### 僵尸进程

```
父进程 ──fork──→ 子进程
子进程执行完毕，发送 SIGCHLD 信号
父进程未调用 wait/waitpid 回收
→ 子进程 PCB 残留在进程表 → 成为僵尸进程（状态 Z）
```

- 子进程已终止，但**进程描述符**（PCB）仍保留
- 保留原因：父进程可能需要读取子进程退出码
- 父进程调用 `wait()` 或 `waitpid()` 后，内核才清除 PCB

#### 危害与解决

- 每个僵尸进程占用一个 PID
- 大量僵尸进程会**耗尽系统进程表**，导致无法创建新进程
- 解决：父进程正确调用 `wait/waitpid`；或杀死父进程（子进程被 init 收养后回收）

```c
// 防止僵尸进程
signal(SIGCHLD, SIG_IGN);  // 忽略 SIGCHLD，内核自动回收
// 或
while (waitpid(-1, &status, WNOHANG) > 0);  // 主动回收
```

### 面试追问

1. **为什么僵尸进程不占用内存但有害？** 僵尸进程的代码段和数据段已被回收，不占用内存资源，但其**进程控制块（PCB）** 仍保留在内核进程表中，占用 PID。操作系统进程表大小有限（如 Linux 默认 `/proc/sys/kernel/pid_max`），大量僵尸进程耗尽 PID 后，系统无法 fork 新进程，服务可能因此瘫痪。

2. **如何查看和处理系统中的僵尸进程？** 查看：`ps aux | grep 'Z'` 或 `top` 中 STATE 为 Z 的进程。处理：① 找到僵尸进程的父进程 PID，修复父进程使其正确 wait；② 若父进程无法修改，可 kill 父进程，子进程被 init 收养并回收；③ 预防：注册 SIGCHLD 信号处理函数，在回调中 wait 回收子进程。

## 13.死锁产生的原因？如果解决死锁的问题？

**记忆口诀：**「互斥持有不剥夺，环路等待四条件；破一即可防死锁」

**核心要点：**
- 死锁：多个进程争夺资源陷入僵局，无外力无法推进
- 四个必要条件：互斥、请求与保持、不可剥夺、环路等待
- 解决：预防（破坏条件）、避免（银行家算法）、检测+恢复

### 详细解答

**死锁**是指多个进程在运行过程中因争夺资源而造成僵局，若无外力作用，都将无法继续推进。

#### 资源分类

| 类型 | 说明 | 示例 |
| --- | --- | --- |
| **可剥夺资源** | 可被其他进程或系统强制剥夺 | CPU、主存 |
| **不可剥夺资源** | 分配后不能强行收回，只能进程用完释放 | 打印机、磁带机 |

#### 产生死锁的原因

**1. 竞争资源**
- 竞争不可剥夺资源：系统只有一台打印机，P1 占用后 P2 再请求则阻塞
- 竞争临时资源：硬件中断、信号、消息、缓冲区等，通信顺序不当导致死锁

**2. 进程推进顺序非法**

```
P1 持有 R1，请求 R2（阻塞）
P2 持有 R2，请求 R1（阻塞）
→ 互相等待 → 死锁
```

#### 四个必要条件（同时满足才死锁）

| 条件 | 含义 |
| --- | --- |
| **互斥** | 资源只能被一个进程占用 |
| **请求与保持** | 进程阻塞于新请求时，不释放已持有的资源 |
| **不可剥夺** | 已分配的资源只能由持有者主动释放 |
| **环路等待** | 存在进程-资源的环形等待链 |

#### 解决方案

**1. 死锁预防**（破坏四个条件之一）

| 策略 | 破坏的条件 |
| --- | --- |
| 资源一次性分配 | 请求与保持（要么全部分配，要么不分配） |
| 持有并等待时不再分配其他资源 | 请求与保持 |
| 可剥夺资源 | 不可剥夺（得不到新资源则释放已有资源） |
| 资源有序分配法 | 环路等待（按编号递增顺序请求资源） |

**2. 死锁避免** — 银行家算法：分配前模拟是否会导致不安全状态

**3. 死锁检测与恢复** — 允许死锁发生，定期检测并恢复（终止进程或剥夺资源）

**4. 鸵鸟策略** — 忽略死锁（大多数操作系统采用，因为预防代价高）

### 面试追问

1. **银行家算法的基本思想是什么？** 银行家算法在分配资源前，先模拟分配后系统是否仍处于**安全状态**（存在安全序列使所有进程都能完成）。若分配后不存在安全序列，则拒绝分配，进程等待。它属于死锁**避免**策略，不破坏必要条件，而是在运行时动态判断是否会导致死锁，比预防策略资源利用率高，但计算开销大。

2. **为什么大多数操作系统选择鸵鸟策略？** 因为死锁预防（如一次性分配所有资源）资源利用率低，死锁避免（银行家算法）计算开销大且需预知最大资源需求，检测与恢复影响用户体验。实际中死锁发生概率较低，操作系统通过合理的资源调度顺序、超时机制等降低概率，发生死锁时用户重启即可，综合成本最低。

## 14.如何实现浏览器内多个标签页之间的通信?

**记忆口诀：**「中介者模式来通信，WebSocket、SharedWorker、localStorage、postMessage 四方案」

**核心要点：**
- 标签页之间无法直接通信，需通过中介者模式转发消息
- 常用方案：WebSocket、SharedWorker、localStorage、postMessage
- 各方案适用场景不同：实时性、持久性、复杂度各有差异

### 详细解答

多个标签页之间无法直接通信，本质上都采用**中介者模式**：标签页与中介者通信，中介者负责消息转发。

#### 四种通信方案对比

| 方案 | 中介者 | 实时性 | 持久性 | 复杂度 |
| --- | --- | --- | --- | --- |
| **WebSocket** | 服务器 | 高（推送） | 依赖服务器 | 中 |
| **SharedWorker** | 共享线程 | 高 | 页面生命周期内 | 中 |
| **localStorage** | localStorage + storage 事件 | 中（事件驱动） | 持久化 | 低 |
| **postMessage** | 目标窗口引用 | 高 | 窗口存在期间 | 低 |

#### 1. WebSocket

标签页通过 WebSocket 与服务器通信，服务器作为中转站转发消息：

```js
// Tab A 发送
ws.send(JSON.stringify({ type: 'chat', data: 'hello' }))

// 服务器推送给 Tab B
// Tab B 接收
ws.onmessage = (e) => console.log(e.data)
```

适合需要**服务端参与**的实时通信场景。

#### 2. SharedWorker

SharedWorker 在多个页面生命周期内创建**唯一线程**，共享该线程实现数据交换：

```js
// 两个 Tab 共享同一个 SharedWorker
const worker = new SharedWorker('shared.js')
worker.port.start()
worker.port.postMessage('hello from Tab A')
worker.port.onmessage = (e) => console.log(e.data)
```

```js
// shared.js
const ports = []
onconnect = (e) => {
  const port = e.ports[0]
  ports.push(port)
  port.onmessage = (e) => {
    ports.forEach(p => p.postMessage(e.data)) // 广播
  }
}
```

#### 3. localStorage

利用 `storage` 事件监听 localStorage 变化（**仅在其他 Tab 修改时触发**，当前 Tab 不触发）：

```js
// Tab A 写入
localStorage.setItem('msg', JSON.stringify({ text: 'hello' }))

// Tab B 监听
window.addEventListener('storage', (e) => {
  if (e.key === 'msg') console.log(JSON.parse(e.newValue))
})
```

#### 4. postMessage

获取目标标签页的 `window` 引用后直接通信：

```js
// Tab A 打开 Tab B 并持有引用
const newTab = window.open('https://example.com/pageB')
newTab.postMessage('hello', 'https://example.com')

// Tab B 接收
window.addEventListener('message', (e) => {
  if (e.origin === 'https://example.com') console.log(e.data)
})
```

#### 方案选择建议

- **纯前端、简单场景** → localStorage 或 BroadcastChannel（同源广播 API）
- **纯前端、复杂逻辑** → SharedWorker
- **需服务端同步** → WebSocket
- **已知目标窗口** → postMessage

### 面试追问

1. **BroadcastChannel 和 localStorage 事件有什么区别？** BroadcastChannel 是 HTML5 提供的同源广播 API，专门用于 Tab 间通信，API 更简洁（`channel.postMessage()` / `channel.onmessage`），无需读写 storage。localStorage 事件是"副作用"通信——通过写 storage 触发其他 Tab 的 storage 事件，需要序列化/反序列化，且有存储大小限制（约 5MB）。BroadcastChannel 语义更清晰，是更现代的方案。

2. **SharedWorker 和 Service Worker 能用于 Tab 通信吗？** SharedWorker 可以，它就是为跨 Tab 共享线程设计的。Service Worker 主要用于离线缓存和网络代理，虽然也能接收 postMessage，但它的生命周期与页面注册关联，设计目的不是 Tab 间通信，用它做 Tab 通信是 hack 用法，不如 SharedWorker 或 BroadcastChannel 合适。

## 15.对Service Worker的理解

**记忆口诀：**「独立线程做缓存，HTTPS 必须请求拦截；install 缓存 fetch 拦截」

**核心要点：**
- Service Worker 是浏览器背后的独立线程，可实现离线缓存、消息推送、网络代理
- 必须使用 HTTPS（localhost 除外），因涉及请求拦截
- 生命周期：注册 → install（缓存资源）→ activate → fetch（拦截请求）

### 详细解答

Service Worker 是运行在浏览器背后的**独立线程**，与主线程分离，无法直接访问 DOM，但可以实现：

- **离线缓存**
- **消息推送**
- **网络代理**（拦截和处理网络请求）
- **后台同步**

#### 核心特点

| 特点 | 说明 |
| --- | --- |
| 独立线程 | 不阻塞主线程，不影响页面性能 |
| 无法访问 DOM | 通过 postMessage 与页面通信 |
| 必须 HTTPS | 涉及请求拦截，需安全上下文（localhost 除外） |
| 持久化 | 关闭页面后仍可运行，直到被注销 |
| 生命周期独立 | 与页面生命周期解耦 |

#### 缓存实现三步骤

**1. 注册 Service Worker**

```js
// index.js
if ('serviceWorker' in navigator) {
  navigator.serviceWorker
    .register('/sw.js')
    .then(reg => console.log('SW 注册成功', reg.scope))
    .catch(err => console.log('SW 注册失败', err))
}
```

**2. install 事件 — 缓存静态资源**

```js
// sw.js
self.addEventListener('install', e => {
  e.waitUntil(
    caches.open('my-cache-v1').then(cache => {
      return cache.addAll(['./index.html', './index.js', './style.css'])
    })
  )
})
```

**3. fetch 事件 — 拦截请求，优先读缓存**

```js
self.addEventListener('fetch', e => {
  e.respondWith(
    caches.match(e.request).then(response => {
      // 缓存命中 → 直接返回
      if (response) return response
      // 未命中 → 发起网络请求
      return fetch(e.request)
    })
  )
})
```

#### 生命周期

```
注册(register) → 安装(install) → 激活(activate) → 运行(fetch/message)
                     ↓                                    ↓
               缓存静态资源                          拦截网络请求
                                                          ↓
                                                     终止/更新
```

- 新的 SW 安装后处于 **waiting** 状态，直到所有旧 SW 控制的页面关闭才 **activate**
- 可通过 `skipWaiting()` 和 `clients.claim()` 强制立即激活

#### 调试

Chrome DevTools → Application → Service Workers 面板可查看注册状态、缓存内容。

### 面试追问

1. **Service Worker 和 Web Worker 有什么区别？** Web Worker 由页面创建和管理，生命周期与页面绑定，页面关闭则 Worker 终止，主要用于 offload 计算密集型任务。Service Worker 独立于页面，由浏览器事件驱动（install/activate/fetch），页面关闭后仍可运行，主要用于网络代理和缓存。Service Worker 必须 HTTPS，Web Worker 无此限制。

2. **Service Worker 更新策略是怎样的？如何让用户立即使用新版本？** 浏览器每次导航时会 byte-check SW 脚本文件，有变化则安装新版本。新 SW 安装完成后进入 waiting 状态，等旧 SW 控制的所有页面关闭后才 activate。若需立即更新：新 SW 中调用 `self.skipWaiting()`，activate 事件中调用 `self.clients.claim()` 立即接管所有页面。也可在页面检测 `registration.waiting` 并提示用户刷新。

## 16.对浏览器的缓存机制的理解

**记忆口诀：**「强缓存不请求，协商缓存问一声；Expires 和 Cache-Control，Last-Modified 和 ETag」

**核心要点：**
- 浏览器缓存分强缓存和协商缓存，通过 HTTP Header 控制
- 强缓存：不发请求，直接用本地缓存（Expires / Cache-Control）
- 协商缓存：强缓存失效后，向服务器验证资源是否变更（Last-Modified / ETag）

### 详细解答

浏览器 HTTP 缓存策略分为**强缓存**和**协商缓存**，均通过设置 HTTP Header 实现。

#### 缓存决策流程

```
发起请求
  ↓
强缓存是否命中？（Cache-Control / Expires）
  ├── 是 → 直接使用本地缓存（200 from cache）
  └── 否 ↓
协商缓存是否命中？（Last-Modified / ETag）
  ├── 304 → 资源未变，使用本地缓存
  └── 200 → 资源已变，返回新资源并更新缓存
```

#### 强缓存

不向服务器发送请求，直接从本地缓存读取资源。

| Header | 版本 | 说明 | 缺点 |
| --- | --- | --- | --- |
| **Expires** | HTTP/1.0 | 绝对过期时间（服务器时间点） | 受本地时间影响，可能不准 |
| **Cache-Control** | HTTP/1.1 | 相对过期时间，如 `max-age=300`（5 分钟） | 无 |

**优先级**：Cache-Control > Expires

```http
Cache-Control: max-age=31536000, public
```

#### 协商缓存

强缓存失效后，浏览器携带缓存标识向服务器验证资源是否变更。

| Header | 版本 | 请求头 | 验证方式 |
| --- | --- | --- | --- |
| **Last-Modified** | HTTP/1.0 | If-Modified-Since | 比较最后修改时间 |
| **ETag** | HTTP/1.1 | If-None-Match | 比较资源唯一标识 |

**Last-Modified 流程：**
1. 首次请求 → 响应头 `Last-Modified: Wed, 15 Jun 2026 10:00:00 GMT`
2. 再次请求 → 请求头 `If-Modified-Since: Wed, 15 Jun 2026 10:00:00 GMT`
3. 服务器比较 → 未变返回 304，已变返回 200 + 新资源

**ETag 流程：**
1. 首次请求 → 响应头 `ETag: "abc123"`
2. 再次请求 → 请求头 `If-None-Match: "abc123"`
3. 服务器比较 token → 一致 304，不一致 200 + 新 ETag

**优先级**：ETag > Last-Modified（ETag 更精确，但 Last-Modified 性能更好）

#### 无缓存策略时

浏览器使用**启发式算法**：`(Date - Last-Modified) × 10%` 作为缓存时间。

### 面试追问

1. **Last-Modified 有什么缺陷？ETag 如何弥补？** Last-Modified 只能精确到**秒级**，1 秒内多次修改的文件无法感知变化；且文件内容未变但修改时间变了（如重新部署）会导致缓存失效。ETag 是资源内容的哈希/唯一标识，内容不变则 ETag 不变，精确度更高。但 ETag 需服务器计算哈希，性能开销大于 Last-Modified 的时间戳比较。

2. **Cache-Control 的 no-cache 和 no-store 有什么区别？** `no-cache` 不是"不缓存"，而是"缓存但使用前必须向服务器验证"——有协商缓存，无强缓存。`no-store` 才是"完全不缓存"，每次请求都从服务器拉取最新资源。记忆：`no-cache` = 可以存，但要问服务器；`no-store` = 不要存。

## 17.浏览器资源缓存的位置有哪些？

**记忆口诀：**「内存最快 Service Worker 可控，磁盘容量大 Push 会话级」

**核心要点：**
- 四种缓存位置：Memory Cache、Service Worker Cache、Disk Cache、Push Cache
- 查找优先级：Memory Cache → Service Worker → Disk Cache → Push Cache → 网络
- 各有特点：速度、容量、持久性、可控性不同

### 详细解答

浏览器资源缓存按存储位置和特性分为四个层级：

#### 缓存位置对比

| 缓存位置 | 速度 | 容量 | 持久性 | 可控性 |
| --- | --- | --- | --- | --- |
| **Memory Cache** | 最快（~0ms） | 小 | 页面关闭即失效 | 浏览器自动管理 |
| **Service Worker** | 快（~10ms） | 中 | 持久（手动清除） | 开发者完全可控 |
| **Disk Cache** | 较慢 | 大 | 持久 | 浏览器根据 Header 管理 |
| **Push Cache** | — | 小 | 会话级（关闭连接即释放） | HTTP/2 服务器推送 |

#### 1. Memory Cache（内存缓存）

- 读取效率最高，但容量有限
- 随着进程释放而释放，**关闭 Tab 即失效**
- 浏览器自动决定哪些资源放入（小文件、当前页面临时资源等）

#### 2. Service Worker Cache

- 运行在 JS 主线程之外，无法直接访问 DOM
- 开发者通过 Cache API **自由控制**缓存哪些文件、如何匹配、如何读取
- 缓存是**持续性**的，不受浏览器 disable cache 影响
- 未命中时调用 `fetch()` 走后续缓存链路
- DevTools 中显示为 from ServiceWorker，即使实际数据来自 Memory/Disk Cache

#### 3. Disk Cache（磁盘缓存）

- 存储在硬盘中，容量大，持久化
- 根据 HTTP Header 判断缓存策略
- **跨站点相同 URL 的资源可复用**（同一 URL 不会重复请求）
- 覆盖面最广的缓存类型

#### 4. Push Cache（HTTP/2 推送缓存）

- HTTP/2 特性，以上三种都未命中时才使用
- **会话级**：连接关闭即释放
- 只能使用一次，浏览器可拒绝已存在的推送
- Edge/Safari 兼容性较差

#### 缓存查找优先级

```
Memory Cache → Service Worker → Disk Cache → Push Cache → 网络请求
  (~0ms)         (~10ms)         (较慢)        (会话级)     (~100ms+)
```

### 面试追问

1. **为什么 JS 文件通常存在 Memory Cache 而不是 Disk Cache？** 因为 JS 文件执行频繁，浏览器会将当前页面已加载的 JS 保留在内存中以便快速再次执行。Memory Cache 读取无需磁盘 I/O，速度最快。但 Memory Cache 容量有限且随 Tab 关闭释放，刷新页面后可能需要从 Disk Cache 或网络重新加载。CSS/图片等资源更常存 Disk Cache，因为体积大且不需要"执行"。

2. **Disable cache 在 DevTools 中勾选了，Service Worker 缓存还会生效吗？** 不会。DevTools 的 Disable cache 主要影响 HTTP 缓存（Memory Cache 和 Disk Cache），但 Service Worker 的 fetch 拦截在 HTTP 缓存之前执行，理论上仍可返回 SW 缓存。不过 Chrome DevTools 在 Disable cache 时也会 bypass Service Worker 缓存，确保开发者看到真实的网络行为。生产环境中 SW 缓存不受用户侧 disable cache 影响。

## 18.协商缓存和强缓存的区别

**记忆口诀：**「强缓存不问服务器，协商缓存发请求验身份；200 拿新的，304 用旧的」

**核心要点：**
- 强缓存：不发请求，直接使用本地缓存（Cache-Control / Expires）
- 协商缓存：发请求验证，304 用缓存，200 拿新资源（Last-Modified / ETag）
- 两者配合：先强缓存 → 失效后协商缓存 → 再失效则重新下载

### 详细解答

#### 核心区别

| 对比项 | 强缓存 | 协商缓存 |
| --- | --- | --- |
| **是否发请求** | 不发请求 | 发请求验证 |
| **控制 Header** | Cache-Control、Expires | Last-Modified/ETag + If-Modified-Since/If-None-Match |
| **命中结果** | 200 (from memory/disk cache) | 304 Not Modified |
| **未命中结果** | 进入协商缓存 | 200 + 新资源 |
| **优先级** | 先检查 | 强缓存失效后检查 |

#### 强缓存详解

**Cache-Control 常用值：**

| 值 | 含义 |
| --- | --- |
| `max-age=3600` | 缓存有效期 3600 秒 |
| `public` | 任何对象（客户端、CDN）都可缓存 |
| `private` | 仅浏览器缓存，CDN 不可缓存（含用户信息的 HTML） |
| `no-cache` | 跳过强缓存，每次验证（走协商缓存） |
| `no-store` | 禁止任何缓存，每次都请求服务器 |
| `s-maxage=3600` | CDN 专用，优先级高于 max-age |

**no-cache vs no-store（易混淆）：**
- `no-cache`：可以缓存，但使用前必须向服务器确认（有协商缓存）
- `no-store`：完全不缓存，每次都从服务器获取

#### 协商缓存详解

**触发条件：**
1. 强缓存过期（`max-age` 超时）
2. 设置了 `no-cache`

**Last-Modified 缺点：**
- 只能精确到秒，1 秒内多次修改无法感知
- 文件内容未变但修改时间变了，缓存失效

**ETag 优势：**
- 资源内容的唯一标识，内容不变则 ETag 不变，更精确
- 优先级高于 Last-Modified

**注意**：负载均衡环境下，Last-Modified 应保持一致；ETag 各服务器值不同，可能影响负载均衡，高并发场景慎用 ETag。

#### 完整协作流程

```
浏览器发起请求
  ↓
检查 Cache-Control / Expires → 强缓存命中？
  ├── 是 → 200 from cache（不请求）
  └── 否 ↓
发送请求 + If-Modified-Since / If-None-Match
  ↓
服务器验证 → 资源变更？
  ├── 否 → 304，浏览器用本地副本
  └── 是 → 200 + 新资源，更新缓存
```

### 面试追问

1. **实际项目中 HTML、JS、CSS 的缓存策略怎么配？** 通常采用「HTML 不缓存 + 静态资源强缓存 + 文件名哈希」策略：HTML 设 `Cache-Control: no-cache`（每次验证，确保引用最新资源）；JS/CSS 打包时加 content hash（如 `app.a1b2c3.js`），设 `Cache-Control: max-age=31536000, immutable`（长期强缓存，文件名变则 URL 变，自动加载新版本）。这样 HTML 每次验证，静态资源几乎不走网络。

2. **immutable 指令有什么用？** `Cache-Control: immutable` 告诉浏览器该资源在有效期内**绝不会改变**，即使刷新页面（F5）也不发条件请求验证，直接使用缓存。配合文件名哈希使用效果最好——文件名含 hash，内容变了 hash 就变，URL 不同，不存在"旧 URL 内容更新"的问题，可以安全地跳过刷新时的协商缓存验证，减少不必要的 304 请求。

## 19.为什么需要浏览器缓存？

**记忆口诀：**「减请求、降负担、提速度，静态资源本地读」

**核心要点：**
- 浏览器缓存将请求过的静态资源存储在本地，再次访问时直接读取
- 减少服务器负担、加快页面加载、减少网络数据传输
- 核心策略：资源未更新用本地缓存，已更新则从服务器拉取

### 详细解答

浏览器缓存针对**前端静态资源**（JS、CSS、图片、字体等），核心目标是：首次请求时拉取并保存到本地，后续访问时若资源未更新则直接使用本地副本。

#### 工作流程

```
首次访问：
  浏览器 → 请求静态资源 → 服务器 → 返回资源 + 缓存策略 Header
  浏览器 → 存储到本地（Memory Cache / Disk Cache）

再次访问：
  浏览器 → 检查缓存策略 → 资源未过期？
    ├── 是 → 直接读本地缓存（强缓存）
    └── 否 → 向服务器验证（协商缓存）
              ├── 未变 → 304，用本地缓存
              └── 已变 → 200，拉取新资源并更新缓存
```

#### 三大优点

| 优点 | 说明 |
| --- | --- |
| **减少服务器负担** | 大量静态资源请求被本地缓存消化，服务器 QPS 降低 |
| **加快页面加载速度** | 本地读取（Memory Cache ~0ms）远快于网络请求（~100ms+） |
| **减少网络数据传输** | 节省用户流量，弱网环境下体验提升明显 |

#### 实际收益

- 一个 Web 页面通常包含数十到上百个静态资源
- 无缓存时每次访问都需全量下载（可能数 MB）
- 有缓存时仅 HTML 和变更资源需请求，加载时间从秒级降到毫秒级
- 对 CDN 成本和服务器带宽也有显著节省

#### 缓存不是万能的

- 动态数据（API 响应）通常不适合长期缓存
- 缓存策略不当可能导致用户看到旧版本（需版本号/hash 管理）
- 首次访问（冷启动）无法受益于缓存

### 面试追问

1. **浏览器缓存和 CDN 缓存有什么区别？** 浏览器缓存存在于**用户本地**（Memory/Disk），仅该用户该浏览器受益，由 HTTP Header 控制。CDN 缓存存在于**边缘节点服务器**，同一节点附近的所有用户共享，由 Cache-Control 的 s-maxage 等控制。两者配合：CDN 减少回源压力，浏览器缓存减少 CDN 请求，形成「浏览器 → CDN → 源站」三级缓存链路。

2. **缓存会导致用户看到旧代码怎么办？** 常用方案：① **文件名哈希**（webpack contenthash），内容变则文件名变，自动破缓存；② HTML 设 no-cache 确保每次拿到最新引用；③ 版本号/query 参数（如 `app.js?v=2.0`），但不如哈希可靠；④ 部署时 Service Worker 更新策略，确保 SW 缓存也同步更新。核心原则：HTML 不缓存，静态资源永久缓存 + 文件名绑定内容。

## 20.对浏览器内核的理解

**记忆口诀：**「内核分两块：渲染引擎画页面，JS 引擎跑脚本」

**核心要点：**
- 浏览器内核 = 渲染引擎 + JS 引擎（现代浏览器中 JS 引擎已高度独立）
- 渲染引擎：解析 HTML/CSS，将内容显示在浏览器窗口
- 常见内核：Chrome/Blink、Firefox/Gecko、Safari/WebKit

### 详细解答

浏览器内核（Browser Kernel）是浏览器最核心的部分，主要负责页面渲染和脚本执行。

#### 两大组成部分

| 组件 | 职责 | 常见实现 |
| --- | --- | --- |
| **渲染引擎** | 解析 HTML/CSS，渲染页面内容 | Blink（Chrome）、WebKit（Safari）、Gecko（Firefox） |
| **JS 引擎** | 解析和执行 JavaScript | V8（Chrome）、SpiderMonkey（Firefox）、JavaScriptCore（Safari） |

#### 渲染引擎

- 在浏览器窗口中**显示**所请求的内容
- 默认可渲染 HTML、XML 文档及图片
- 可通过插件扩展其他格式（如 PDF 阅读器插件）
- 核心流程：HTML 解析 → DOM 树 → CSS 解析 → CSSOM 树 → 渲染树 → 布局 → 绘制

#### JS 引擎

- 解析和执行 JavaScript，实现网页**动态效果**
- 最初渲染引擎和 JS 引擎没有明确区分
- 随着 JS 引擎越来越独立（如 V8 可用于 Node.js），**内核**一词倾向于单指**渲染引擎**

#### 主流浏览器内核

| 浏览器 | 渲染引擎 | JS 引擎 |
| --- | --- | --- |
| Chrome / Edge | Blink | V8 |
| Safari | WebKit | JavaScriptCore (Nitro) |
| Firefox | Gecko | SpiderMonkey |

#### 内核与浏览器架构的关系

```
浏览器
├── 浏览器主进程（UI、网络、存储管理）
├── 渲染进程
│   ├── 渲染引擎（Blink/WebKit/Gecko）→ 排版渲染
│   └── JS 引擎（V8 等）→ 脚本执行
├── GPU 进程
├── 网络进程
└── 插件进程
```

渲染引擎和 JS 引擎都运行在**渲染进程**中，但 JS 引擎也可独立用于其他运行时（Node.js 使用 V8，不含渲染引擎）。

### 面试追问

1. **Blink 和 WebKit 是什么关系？** WebKit 是 Safari 基于 KHTML 开发的渲染引擎。2013 年 Google 从 WebKit 中 fork 出 Blink 作为 Chrome 的渲染引擎。两者同源但已独立发展：Blink 移除了 WebKit 的一些复杂层，采用多进程架构优化，现由 Google 主导；WebKit 由 Apple 主导，用于 Safari 和 iOS 所有浏览器（iOS 强制 WebKit）。语法上很多 CSS 前缀仍共用 `-webkit-`。

2. **为什么说「Chrome 内核是 Blink」而不是 V8？** 因为业界说的「浏览器内核」 traditionally 指**渲染引擎**——负责 HTML 解析、CSS 计算、布局绘制的部分，即「浏览器如何显示页面」。V8 是 JS 引擎，负责脚本执行，虽然至关重要，但属于运行时而非「渲染内核」。类似地，说「Safari 内核是 WebKit」也是指渲染引擎。不过现代讨论中有时也会把 JS 引擎纳入广义的内核范畴。

## 21. 常见的浏览器内核比较

**记忆口诀：**「Trident 老 IE 慢，Gecko 强但耗内存，Presto 快但兼容性差，Webkit 快容错低，Blink 是 Webkit 分支」

**核心要点：**
- 浏览器内核（渲染引擎）负责解析 HTML/CSS 并渲染页面，不同内核在性能、兼容性、资源消耗上各有取舍
- 主流内核演进：Trident → Gecko/Presto/Webkit → Blink
- 现代浏览器大多基于 Chromium（Blink）或 Webkit，IE 的 Trident 已逐步淘汰

### 详细解答

| 内核 | 代表浏览器 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **Trident** | IE | 早期市场占有率极高，大量网页基于其标准编写 | 与 W3C 标准脱节，Bug 多、安全性差，长期未更新 |
| **Gecko** | Firefox | 功能强大，支持复杂网页效果和浏览器扩展 | 内存消耗较大 |
| **Presto** | 旧版 Opera | 公认网页速度最快，JS 处理比其他内核快约 3 倍 | 为追求速度牺牲了部分网页兼容性 |
| **Webkit** | Safari | 浏览速度较快，优于 Gecko 和 Trident | 对非标准代码容错性低，部分网页无法正确显示 |
| **Blink** | Chrome、新版 Opera | 基于 Webkit 分支，Google 与 Opera 共同维护，性能持续优化 | 与 Webkit 存在分化，部分特性不兼容 |

#### 内核演进关系

```
KHTML → Webkit → Blink（Chrome 2013 年从 Webkit 分叉）
Gecko（Mozilla 独立开发）
Trident（IE 专用，已淘汰）
Presto（Opera 旧内核，已弃用）
```

**Webkit 背景：** Webkit 前身是 KDE 小组的 KHTML 引擎，是 KHTML 的开源分支。2013 年 Google 宣布 Chromium 项目采用 Blink 渲染引擎，Blink 本质上是 Webkit 的一个分支，就像 Webkit 是 KHTML 的分支一样。

### 面试追问

1. **为什么 Chrome 要从 Webkit 分叉出 Blink？** Google 认为 Webkit 代码库过于臃肿，且 Google 与 Apple 在 Webkit 发展方向上存在分歧。分叉后 Google 可以更快推进自己的渲染优化和多进程架构，减少与 Safari 的代码耦合，同时 Opera 也加入了 Blink 阵营共同维护。

2. **Presto 内核为什么被 Opera 放弃？** Presto 虽然速度快，但维护成本高、兼容性不足，难以跟上 Web 标准快速演进。Opera 转向 Webkit/Blink 后，可以直接复用 Chromium 生态，降低开发成本，同时获得更好的标准兼容性和扩展支持。

## 22. 常见浏览器所用内核

**记忆口诀：**「IE 用 Trident，Firefox 用 Gecko，Safari 用 Webkit，Chrome 用 Blink，国产浏览器双核居多」

**核心要点：**
- 不同浏览器采用不同渲染内核，国产浏览器普遍采用「双核」策略
- Chrome 内核已从 Webkit 切换为 Blink
- 双核浏览器通常提供「兼容模式（IE/Trident）」和「高速模式（Webkit/Blink）」

### 详细解答

| 浏览器 | 内核 |
| --- | --- |
| IE | Trident（俗称 IE 内核） |
| Chrome | 早期 Webkit，现为 **Blink**（统称 Chromium 内核） |
| Firefox | **Gecko** |
| Safari | **Webkit** |
| Opera | 早期 Presto → Webkit → **Blink** |
| 360、猎豹 | IE + Chrome **双内核** |
| 搜狗、遨游、QQ 浏览器 | Trident（兼容模式）+ Webkit（高速模式） |
| 百度、世界之窗 | IE 内核 |
| 2345 浏览器 | IE + Chrome 双内核 |
| UC 浏览器 | 自称 U3 内核，实际基于 Webkit/Trident 或 Gecko |

#### 双核浏览器工作原理

国产浏览器普遍采用双核策略，目的是同时兼顾**老网站兼容**和**新网站性能**：

- **兼容模式**：调用 Trident 内核，模拟 IE 行为，保证银行、政务等老旧系统正常运行
- **高速模式**：调用 Webkit/Blink 内核，获得更快的渲染速度和更好的标准支持

浏览器通常会根据 User-Agent 或用户手动切换来决定使用哪个内核。

### 面试追问

1. **如何判断当前浏览器使用的是哪个内核？** 可以通过 `navigator.userAgent` 初步判断，但更可靠的方式是检测特有 API：如 `window.chrome` 存在且非 Edge 则可能是 Blink；Firefox 的 Gecko 会在 UA 中包含 `Gecko`；IE 可通过 `document.documentMode` 或 `-ms-` 前缀特性检测。现代 Edge 已基于 Chromium（Blink）。

2. **为什么国产浏览器喜欢做双核？** 中国市场长期存在大量基于 IE 标准开发的网站（网银、政务系统等），单核浏览器无法兼顾兼容性。双核让用户无需安装 IE 即可访问老网站，同时在新网站上享受 Webkit/Blink 的高性能，是一种务实的过渡方案。

## 23. 浏览器的主要组成部分

**记忆口诀：**「UI 界面、浏览器引擎、渲染引擎、网络、UI 后端、JS 引擎、数据存储，七大组件各司其职」

**核心要点：**
- 现代浏览器由用户界面、浏览器引擎、渲染引擎、网络、UI 后端、JS 解释器、数据存储七大部分组成
- 浏览器引擎负责在用户界面和渲染引擎之间传递指令
- Chrome 的多进程架构：每个标签页对应独立的渲染进程

### 详细解答

| 组件 | 职责 |
| --- | --- |
| **用户界面（UI）** | 地址栏、前进/后退按钮、书签菜单等，除页面内容外的所有可见部分 |
| **浏览器引擎** | 在用户界面和渲染引擎之间传递指令，协调各模块工作 |
| **渲染引擎（呈现引擎）** | 解析 HTML/CSS，构建 DOM 和 CSSOM，生成渲染树并绘制到屏幕 |
| **网络** | 处理 HTTP 请求等网络调用，提供与平台无关的网络接口 |
| **UI 后端** | 绘制基本窗口控件（组合框、窗口等），底层调用操作系统 UI 方法 |
| **JavaScript 解释器** | 解析和执行 JavaScript 代码 |
| **数据存储** | 持久层，存储 Cookie、IndexedDB 等数据 |

#### Chrome 多进程架构

与大多数浏览器不同，Chrome 采用**多进程架构**：

- 每个标签页对应一个**独立的渲染进程**（呈现引擎实例）
- 一个标签页崩溃不会影响其他标签页
- 浏览器进程、GPU 进程、网络进程等各自独立，提升安全性和稳定性

```
浏览器进程（Browser Process）
├── 渲染进程 × N（每个 Tab 一个）
├── GPU 进程
├── 网络进程
└── 插件进程
```

### 面试追问

1. **渲染引擎和浏览器引擎有什么区别？** 浏览器引擎是「调度中心」，负责接收 UI 指令并传递给渲染引擎，同时协调 JS 引擎、网络等模块。渲染引擎（如 Blink、Webkit）专注于「页面渲染」——解析 HTML/CSS、布局、绘制。两者是上下层协作关系，而非同一概念。

2. **Chrome 为什么要给每个标签页单独开进程？** 主要出于**稳定性**和**安全性**考虑：一个页面崩溃或遭遇恶意脚本不会拖垮整个浏览器；进程间沙箱隔离限制了攻击面。代价是内存占用更高，但现代硬件通常可以承受，Google 认为稳定性收益更大。

## 24. 浏览器的渲染过程

**记忆口诀：**「解析 HTML 建 DOM，解析 CSS 建 CSSOM，合并生成渲染树，布局算位置，绘制上屏幕」

**核心要点：**
- 渲染流程：DOM 树 → CSSOM 树 → 渲染树 → 布局（Layout/Reflow）→ 绘制（Paint）
- 渲染树只包含可见节点，不可见元素（如 `display:none`）不会进入渲染树
- 渲染是渐进式的，不会等所有 HTML 下载完才开始

### 详细解答

#### 完整渲染流程

```
HTML 字节流
  ↓ 解析
DOM 树                    CSS 字节流
                            ↓ 解析
                         CSSOM 规则树
  ↓ 合并
渲染树（Render Tree）
  ↓ 布局（Layout / Reflow）
计算每个节点的精确位置和大小
  ↓ 绘制（Paint）
调用渲染对象的 paint 方法，绘制到屏幕
```

#### 各阶段说明

| 阶段 | 说明 |
| --- | --- |
| **构建 DOM 树** | HTML 解析器将文档解析为 DOM 节点树 |
| **构建 CSSOM 树** | CSS 解析器解析样式表，生成 CSS Object Model |
| **构建渲染树** | 将 DOM 与 CSSOM 合并，只包含可见节点及其样式 |
| **布局（Layout）** | 计算每个渲染对象在视口中的精确位置和大小，也称「回流/重排」 |
| **绘制（Paint）** | 遍历渲染树，调用 paint 方法将内容绘制到屏幕，使用 UI 基础组件 |

#### 关键细节

- **渲染树 ≠ DOM 树**：DOM 中不可见的元素（`display:none`、`head` 等）不会进入渲染树；一个 DOM 元素可能对应多个渲染对象（如 `::before`、`::after`）
- **渐进式渲染**：渲染引擎不会等所有 HTML 解析完才渲染，而是**解析一部分就展示一部分**，同时继续下载剩余资源，提升用户体验

### 面试追问

1. **DOM 树和渲染树有什么区别？** DOM 树包含文档中所有节点（包括 `<head>`、`display:none` 元素等）；渲染树只包含**需要绘制到屏幕上的可见节点**，且每个节点都携带计算后的样式信息。DOM 是文档结构，渲染树是视觉呈现结构，两者不是一一对应关系。

2. **为什么 CSSOM 必须在渲染树之前构建好？** 因为浏览器需要知道每个 DOM 节点的样式才能决定它是否可见、如何布局。没有 CSSOM，就无法判断哪些节点该进入渲染树，也无法计算布局。CSS 解析可以与 DOM 解析并行，但合并成渲染树必须等 CSSOM 就绪。

## 25. 浏览器渲染优化

**记忆口诀：**「JS 放底部用 async/defer，CSS 用 link 放 head，减少回流重绘，合并读写 DOM」

**核心要点：**
- JS 会阻塞 HTML 解析和 CSS 解析，CSS 会阻塞渲染和 JS 执行
- 减少回流（Reflow）和重绘（Repaint）是性能优化核心
- 利用浏览器渲染队列机制，合并 DOM 读写操作

### 详细解答

#### （1）JavaScript 优化

JS 既阻塞 HTML 解析，也阻塞 CSS 解析。优化方式：

| 加载方式 | 行为 |
| --- | --- |
| 普通 `<script>` | 立即停止 HTML 解析，下载并执行 JS，完成后继续解析 |
| `async` | 异步下载，下载完**立即执行**，不保证多个 async 脚本的顺序 |
| `defer` | 异步下载，**HTML 解析完成后**按顺序执行 |

**最佳实践：**
- 将 JS 文件放在 `</body>` 前
- 避免在 body 中间写 `<script>` 标签
- 无依赖的脚本加 `async`，有依赖的脚本加 `defer`

#### （2）CSS 优化

| 引入方式 | 行为 |
| --- | --- |
| `<link>` | 浏览器另开线程加载 CSS，GUI 渲染线程继续解析 HTML |
| `@import` | 阻塞渲染，等 CSS 下载完才继续（不推荐） |
| `<style>` 内联 | 直接渲染，无额外请求 |

- CSS 写在 `<head>` 中，让浏览器尽早发起请求
- 优先使用 `<link>`，避免 `@import`
- CSS 量少时用内联 `<style>`

#### （3）DOM / CSSOM 优化

- HTML 层级不要太深
- 使用语义化标签，减少特殊处理
- CSS 选择器层级尽量浅（选择器从右向左匹配）

#### （4）减少回流与重绘

| 优化手段 | 原理 |
| --- | --- |
| 低层级 DOM 操作 | 减少影响范围 |
| 避免 `table` 布局 | 小改动可能引发整个 table 重排 |
| 修改 class 而非直接改 style | 批量变更样式 |
| 使用 `absolute`/`fixed` 脱离文档流 | 变更不影响其他元素 |
| 使用 `documentFragment` | 批量 DOM 操作后一次性插入 |
| 先 `display:none` 再操作 DOM | 隐藏元素上的操作不触发回流 |
| **合并读写操作** | 利用浏览器渲染队列批处理 |

**渲染队列机制：** 浏览器会将多次回流/重绘操作放入队列，达到一定数量或时间间隔后**批量处理**，多次回流合并为一次。因此应将多个读操作或写操作放在一起，避免读写穿插。

```js
// ❌ 触发多次回流
el.style.width = '100px'
const w = el.offsetWidth  // 强制回流
el.style.height = '100px'

// ✅ 批量写，再读
el.style.cssText = 'width:100px;height:100px'
const w = el.offsetWidth  // 只触发一次回流
```

### 面试追问

1. **async 和 defer 的核心区别是什么？** 两者都是异步下载，不阻塞 HTML 解析。区别在于执行时机：`async` 下载完立即执行，顺序不可控；`defer` 等 HTML 解析完成后按文档顺序执行。有依赖关系的脚本用 `defer`，独立脚本（如统计代码）用 `async`。

2. **什么是渲染队列？如何利用它优化性能？** 浏览器不会每次 DOM 变更都立即回流，而是将操作放入队列，批量处理。如果 JavaScript 中读写 DOM 属性穿插进行（如读 offsetWidth 后写 style），会强制清空队列造成多次回流。优化方法是**先批量写、再批量读**，让浏览器一次性完成布局计算。

## 26. 渲染过程中遇到 JS 文件如何处理？

**记忆口诀：**「遇 script 停解析，JS 引擎接管执行，执行完再续解析，defer/async 可破局」

**核心要点：**
- HTML 解析器遇到 `<script>` 会暂停 DOM 构建，将控制权交给 JS 引擎
- JS 执行完毕后，浏览器从中断处恢复 HTML 解析
- 使用 `defer` 或 `async` 可打破阻塞，实现异步加载

### 详细解答

#### 默认行为（无 defer/async）

```
HTML 解析中...
  ↓ 遇到 <script>
暂停 DOM 构建 ──→ 下载 JS 文件 ──→ JS 引擎执行
                                      ↓
                              执行完毕，恢复 HTML 解析
```

1. HTML 解析器构建 DOM 时遇到 `<script>` 标签
2. **暂停文档解析**，浏览器下载 JS 文件（若尚未下载）
3. 将控制权移交给 **JavaScript 引擎**执行脚本
4. JS 执行完毕后，浏览器从**中断处**恢复 HTML 解析

#### 为什么建议 script 放 body 底部？

首屏渲染需要尽快构建 DOM 并绘制，若在 `<head>` 中加载 JS，会阻塞整个页面渲染。放在 `</body>` 前可以让 HTML 和 CSS 先解析渲染，JS 最后执行。

#### 现代解决方案

```html
<!-- 异步加载，下载完立即执行，适合无依赖脚本 -->
<script async src="analytics.js"></script>

<!-- 异步加载，HTML 解析完后按顺序执行，适合有依赖的脚本 -->
<script defer src="app.js"></script>
```

| 属性 | 是否阻塞解析 | 执行时机 | 顺序保证 |
| --- | --- | --- | --- |
| 无 | 阻塞 | 立即执行 | 按文档顺序 |
| `defer` | 不阻塞 | DOM 解析完成后 | 保证顺序 |
| `async` | 不阻塞 | 下载完立即执行 | 不保证顺序 |

### 面试追问

1. **JS 为什么会阻塞 HTML 解析？** 因为 JS 可能通过 `document.write` 等方式修改 DOM，解析器必须等 JS 执行完才能确定后续 DOM 结构。若不暂停解析，可能出现 JS 操作的节点尚未被解析器创建的竞态问题。

2. **defer 脚本和 DOMContentLoaded 谁先触发？** `DOMContentLoaded` 会等所有 **defer 脚本执行完毕**后才触发。defer 脚本在 DOM 解析完成后、DOMContentLoaded 之前按顺序执行。而 async 脚本可能在 DOMContentLoaded 之前或之后执行，顺序不确定。

## 27. CSS 如何阻塞文档解析？

**记忆口诀：**「CSS 本身不阻解析，但 JS 要读样式，CSSOM 未就绪则 JS 和解析一起等」

**核心要点：**
- CSS 加载本身不直接阻塞 HTML 解析（DOM 构建可继续）
- 但 CSS 会阻塞渲染（没有 CSSOM 就无法生成渲染树）
- JS 执行前必须等 CSSOM 构建完成，否则 JS 可能读到错误的样式值

### 详细解答

#### 阻塞机制

理论上 CSS 不改变 DOM 结构，HTML 解析不必等 CSS。但存在关键问题：

> JavaScript 执行时可能调用 `getComputedStyle()` 等 API 读取样式，若 CSSOM 尚未构建完成，会返回错误值。

因此浏览器的行为是：

```
遇到 <script> 需要执行
  ↓
CSSOM 是否构建完成？
  ├── 是 → 立即执行 JS，继续解析
  └── 否 → 暂停 JS 执行和 HTML 解析，先下载并构建 CSSOM
              ↓
         CSSOM 就绪后，执行 JS，再继续解析
```

#### 三种阻塞关系

| 资源 | 阻塞 HTML 解析 | 阻塞渲染 | 阻塞 JS 执行 |
| --- | --- | --- | --- |
| CSS | 否（间接） | **是** | **是**（CSSOM 未就绪时） |
| JS（无 defer/async） | **是** | 是 | — |
| JS（defer/async） | 否 | 否 | — |

#### 最佳实践

- CSS 放在 `<head>` 中尽早加载，缩短 CSSOM 构建时间
- 使用 `<link>` 而非 `@import`（`@import` 会阻塞解析）
- 关键 CSS 内联，非关键 CSS 异步加载

### 面试追问

1. **CSS 会阻塞 DOM 构建吗？** 严格来说 CSS **不会直接阻塞** DOM 树的构建，HTML 解析器可以并行构建 DOM。但 CSS 会阻塞**渲染**（无 CSSOM 无法生成渲染树），且会**间接阻塞** HTML 解析——当解析器遇到 `<script>` 时，若 CSSOM 未就绪，HTML 解析也会暂停。

2. **为什么 link 加载 CSS 不阻塞，@import 会阻塞？** `<link>` 由浏览器并行下载，HTML 解析线程继续工作；`@import` 是 CSS 内部的导入，浏览器必须先下载完当前 CSS 文件、解析到 @import 规则后才知道还要下载另一个文件，形成串行依赖，阻塞渲染线程。

## 28. 什么情况会阻塞渲染？

**记忆口诀：**「HTML 和 CSS 阻塞渲染，JS 阻塞解析和渲染，defer/async 可解 JS 阻塞」

**核心要点：**
- 渲染前提是生成渲染树，HTML 和 CSS 都是必要输入
- 普通 `<script>` 会暂停 DOM 构建，阻塞渲染
- 优化方向：减小首屏资源体积、扁平 DOM 层级、JS 异步加载

### 详细解答

#### 阻塞渲染的因素

| 因素 | 阻塞方式 | 解决方案 |
| --- | --- | --- |
| **HTML** | 必须解析完才能构建完整 DOM | 减小 HTML 体积，扁平层级 |
| **CSS** | 必须构建 CSSOM 才能生成渲染树 | CSS 放 head，用 link 并行加载 |
| **JS（普通 script）** | 暂停 DOM 解析，阻塞渲染 | 放 body 底部，或用 defer/async |
| **JS 依赖 CSS** | CSSOM 未就绪时 JS 不执行，间接阻塞 | 优先加载关键 CSS |

#### 渲染阻塞流程

```
首屏渲染需要：
  DOM 树（HTML 解析） + CSSOM 树（CSS 解析） → 渲染树 → 布局 → 绘制

任何一环被阻塞，首屏渲染就会延迟
```

#### 优化策略

1. **减小首屏资源**：压缩 HTML/CSS/JS，减少需要解析的文件大小
2. **扁平 DOM 层级**：减少解析和布局计算量
3. **优化 CSS 选择器**：选择器从右向左匹配，层级越浅越快
4. **JS 异步加载**：`defer` 用于有依赖脚本，`async` 用于独立脚本
5. **script 不必放底部**：加了 defer/async 后可以放 `<head>` 中提前下载

### 面试追问

1. **图片加载会阻塞渲染吗？** 默认情况下，`<img>` 不会阻塞 HTML 解析和 DOM 构建，但会阻塞 **load 事件**的触发。图片是替换元素，下载完成后会触发重绘。若图片未设宽高，加载完成后可能导致布局偏移（CLS），影响用户体验。

2. **defer 脚本会阻塞渲染吗？** 不会。defer 脚本异步下载，不阻塞 HTML 解析，在 DOM 解析完成后才执行。此时首屏 DOM 和 CSSOM 通常已就绪，渲染树可以生成，首屏渲染不必等 defer 脚本执行完。

## 29. 浏览器本地存储方式及使用场景

**记忆口诀：**「Cookie 小且随请求走，LocalStorage 持久大容量，SessionStorage 会话级，IndexedDB 存大量结构化数据」

**核心要点：**
- 浏览器提供 Cookie、LocalStorage、SessionStorage、IndexedDB 等多种本地存储
- 各方案在容量、生命周期、是否随请求发送、API 类型上差异明显
- 选型依据：数据大小、持久性需求、是否需要自动携带到服务端

### 详细解答

#### 四种存储对比

| 特性 | Cookie | LocalStorage | SessionStorage | IndexedDB |
| --- | --- | --- | --- | --- |
| 容量 | ~4KB | ~5MB | ~5MB | ≥250MB，无明确上限 |
| 生命周期 | 可设过期时间 | 永久（手动清除） | 标签页关闭即清除 | 永久（手动清除） |
| 随请求发送 | **是** | 否 | 否 | 否 |
| API 类型 | 字符串 | 键值对（同步） | 键值对（同步） | 对象仓库（异步） |
| 同源策略 | 是 | 是 | 是（更严格，同窗口） | 是 |

#### （1）Cookie

**特性：**
- 创建后名称不可修改，无法跨域共享
- 每个域名最多 20 个 Cookie，每个最大 4KB
- 每次 HTTP 请求自动携带，有安全风险

**安全属性：**

| 属性 | 作用 |
| --- | --- |
| `HttpOnly` | 禁止 JS 读取，防 XSS 窃取 |
| `Secure` | 仅 HTTPS 发送 |
| `SameSite` | 防 CSRF：`Strict` / `Lax` / `None` |
| `Domain` / `Path` | 限制生效范围 |

**使用场景：** 登录态（Session ID）、页面点击统计、需服务端感知的少量状态

#### （2）LocalStorage

```js
localStorage.setItem('theme', 'dark')
localStorage.getItem('theme')
localStorage.removeItem('theme')
localStorage.clear()
```

**使用场景：** 换肤设置、用户偏好、不常变动的个人信息、购物车（配合服务端）

#### （3）SessionStorage

与 LocalStorage API 相同，但数据仅在**当前标签页**有效，关闭窗口后清除。

**使用场景：** 表单草稿、临时浏览记录、单次会话的游客信息

#### （4）IndexedDB

**使用场景：** 离线应用、大量结构化数据、二进制文件（图片、视频）、需要索引和事务的复杂数据

### 面试追问

1. **Cookie 和 Session 是如何配合实现登录的？** 用户登录后，服务端生成唯一 `session_id` 并存入服务端 Session 存储，通过 `Set-Cookie` 将 `session_id` 写入客户端 Cookie。后续请求浏览器自动携带 Cookie，服务端通过 `session_id` 查找对应用户信息，实现身份识别。

2. **LocalStorage 和 SessionStorage 都不可以被爬虫爬取吗？** 是的，两者都是浏览器本地存储，JavaScript 可以读写，但服务端和爬虫无法直接访问（除非通过 XSS 注入脚本读取）。Cookie 会随 HTTP 请求发送到服务端，因此服务端可以感知 Cookie 内容。

## 30. Cookie、LocalStorage、SessionStorage区别

**记忆口诀：**「Cookie 4KB 随请求，Local 持久 5MB，Session 关页就没，同源皆受限」

**核心要点：**
- 三者都是浏览器端存储，但容量、生命周期、是否随请求发送差异显著
- Cookie 由服务端设置，适合身份认证；Web Storage 由前端操作，适合本地数据
- 大量数据应使用 IndexedDB

### 详细解答

| 对比项 | Cookie | LocalStorage | SessionStorage |
| --- | --- | --- | --- |
| **来源** | 最初由服务端 Set-Cookie 设置 | HTML5 前端 API | HTML5 前端 API |
| **容量** | ~4KB | ~5MB | ~5MB |
| **生命周期** | 可设 expires/max-age | 永久，除非手动删除 | 当前窗口/标签页关闭即清除 |
| **请求携带** | 每次同源请求自动携带 | 不携带 | 不携带 |
| **共享范围** | 同源页面共享 | 同源所有页面共享 | 仅同一窗口同源页面 |
| **API** | `document.cookie`（繁琐） | `setItem/getItem`（简洁） | 同 LocalStorage |
| **服务端访问** | 可以（随请求发送） | 不可以 | 不可以 |

#### 选型指南

```
需要服务端感知（登录态）     → Cookie
需要持久化大量本地数据       → LocalStorage
临时会话数据（表单、草稿）   → SessionStorage
超大量结构化数据             → IndexedDB
```

#### 补充：IndexedDB

当本地存储大量数据时，使用 IndexedDB——浏览器提供的本地数据库，采用对象仓库（Object Store）存储，更接近 NoSQL，支持索引、事务和二进制数据。

### 面试追问

1. **为什么 Cookie 容量只有 4KB 还要用它？** 因为 Cookie 的核心价值不是存储，而是**随 HTTP 请求自动发送到服务端**。这是实现无状态 HTTP 协议下身份认证的唯一原生机制。LocalStorage 无法自动携带到服务端，不适合做登录态。

2. **SessionStorage 为什么比 LocalStorage 共享范围更严格？** SessionStorage 的设计目标是「单次会话」数据隔离。同一浏览器打开两个标签页访问同一网站，它们各有独立的 SessionStorage，互不可见。而 LocalStorage 在同源所有标签页间共享，适合全局偏好设置。

## 31. 前端储存的方式有哪些？

**记忆口诀：**「Cookie、Local、Session、IndexedDB 四大主流，Web SQL 已废弃」

**核心要点：**
- 前端存储包括 Cookie、LocalStorage、SessionStorage、IndexedDB，以及已废弃的 Web SQL
- 各方案在容量、API 风格、同步/异步、兼容性上各有特点
- 现代项目优先使用 IndexedDB 存大量数据，Web Storage 存中等数据，Cookie 做认证

### 详细解答

| 存储方式 | 容量 | 特点 | 状态 |
| --- | --- | --- | --- |
| **Cookie** | ~4KB | 兼容性好，随请求自动携带，使用繁琐需自行封装 | 主流使用 |
| **LocalStorage** | ~5MB | 操作简单，永久存储，同步 API，兼容 IE8+ | 主流使用 |
| **SessionStorage** | ~5MB | 与 LocalStorage 类似，会话级，关闭页面即清除 | 主流使用 |
| **IndexedDB** | ≥250MB | NoSQL，键值对，异步，支持事务和二进制 | HTML5 标准，主流使用 |
| **Web SQL** | — | 关系型数据库，用 SQL 操作，类似 SQLite | **2010 年被 W3C 废弃** |

#### 各方案 API 风格

```js
// Cookie — 字符串操作，繁琐
document.cookie = 'name=value; expires=...; path=/'

// LocalStorage / SessionStorage — 同步键值对
localStorage.setItem('key', 'value')

// IndexedDB — 异步，支持事务
const request = indexedDB.open('myDB', 1)
request.onsuccess = (e) => { /* 操作数据库 */ }
```

#### 选型建议

- **身份认证、少量状态** → Cookie
- **用户偏好、主题、持久缓存** → LocalStorage
- **表单草稿、临时状态** → SessionStorage
- **离线应用、大量结构化/二进制数据** → IndexedDB

### 面试追问

1. **Web SQL 为什么被废弃？** W3C 废弃 Web SQL 主要因为：规范依赖 SQLite 特定实现，难以形成独立于某一数据库的标准；浏览器厂商（除 Firefox 外）虽实现了但缺乏统一规范；IndexedDB 作为替代方案被正式纳入 HTML5 标准，提供了更好的跨浏览器一致性。

2. **前端存储方案中哪些可以被 JavaScript 直接读取？** 四种主流方案都可以被 JS 读取（Cookie 可通过 `document.cookie`，除非设置了 `HttpOnly`）。但 Cookie 设置了 `HttpOnly` 后 JS 无法读取，这是防 XSS 的重要安全手段。LocalStorage、SessionStorage、IndexedDB 都可以被 JS 读写，因此存储敏感信息时需警惕 XSS 攻击。

## 32. IndexedDB有哪些特点？

**记忆口诀：**「键值异步大空间，支持事务二进制，同源限制 NoSQL」

**核心要点：**
- IndexedDB 是 HTML5 标准的浏览器内 NoSQL 数据库
- 异步操作不阻塞主线程，支持事务保证数据一致性
- 存储空间远大于 LocalStorage，支持二进制数据

### 详细解答

| 特点 | 说明 |
| --- | --- |
| **键值对存储** | 采用对象仓库（Object Store），所有类型数据直接存入，包括 JS 对象；每条记录有唯一主键，重复则报错 |
| **异步** | 操作不锁死浏览器，用户可继续交互；对比 LocalStorage 的同步 API，适合大量数据读写 |
| **支持事务** | 一系列操作要么全部成功，要么全部回滚，不存在只改写一部分的情况 |
| **同源限制** | 每个数据库对应创建它的域名，网页只能访问自身域名下的数据库 |
| **存储空间大** | 一般不少于 250MB，甚至没有上限（取决于磁盘空间和浏览器策略） |
| **支持二进制** | 可存储 ArrayBuffer 和 Blob 对象，适合图片、文件等 |

#### 基本使用示例

```js
const request = indexedDB.open('myDatabase', 1)

request.onupgradeneeded = (event) => {
  const db = event.target.result
  const store = db.createObjectStore('users', { keyPath: 'id' })
  store.createIndex('name', 'name', { unique: false })
}

request.onsuccess = (event) => {
  const db = event.target.result
  const tx = db.transaction('users', 'readwrite')
  const store = tx.objectStore('users')
  store.add({ id: 1, name: 'Alice' })
}
```

#### 与 LocalStorage 对比

| 特性 | IndexedDB | LocalStorage |
| --- | --- | --- |
| API 风格 | 异步 | 同步 |
| 数据结构 | 对象仓库 + 索引 | 字符串键值对 |
| 容量 | ≥250MB | ~5MB |
| 事务 | 支持 | 不支持 |
| 二进制 | 支持 | 不支持 |

### 面试追问

1. **IndexedDB 的事务有哪些模式？** 三种：`readonly`（只读，可并发）、`readwrite`（读写，独占）、`versionchange`（数据库升级，独占）。同一时间内，对同一 Object Store 只能有一个 `readwrite` 事务，保证数据一致性。

2. **什么场景下应该用 IndexedDB 而不是 LocalStorage？** 当数据量超过 5MB、需要结构化查询（索引）、需要事务保证、需要存储二进制文件（如离线缓存图片/视频）、或需要异步操作避免阻塞主线程时，应选 IndexedDB。LocalStorage 适合简单的键值对持久化。

## 33. 什么是同源策略

**记忆口诀：**「协议域名端口三一致，否则就是跨域，JS 访问受限但资源加载不受限」

**核心要点：**
- 同源策略是浏览器核心安全机制，限制不同源之间的 JS 交互
- 同源要求：协议、域名、端口三者完全一致
- 主要限制：Cookie/Storage 访问、DOM 操作、Ajax 请求

### 详细解答

> **同源策略**：限制了从同一个源加载的文档或脚本如何与另一个源的资源进行交互。这是浏览器隔离潜在恶意文件的重要安全机制。

**同源定义：** 协议（Protocol）、域名（Domain）、端口（Port）三者必须一致。

#### 同源判断示例

以 `http://store.company.com/dir/page.html` 为基准：

| URL | 是否同源 | 原因 |
| --- | --- | --- |
| `http://store.company.com/dir/inner/another.html` | ✅ 同源 | 仅路径不同 |
| `https://store.company.com/secure.html` | ❌ 跨域 | 协议不同 |
| `http://store.company.com:81/dir/etc.html` | ❌ 跨域 | 端口不同 |
| `http://news.company.com/dir/other.html` | ❌ 跨域 | 域名不同 |

#### 同源策略的三方面限制

| 限制对象 | 说明 |
| --- | --- |
| **Cookie / LocalStorage / IndexedDB** | 当前域的 JS 不能读取其他域的存储数据 |
| **DOM** | 当前域的 JS 不能操作其他域的 DOM（如 iframe 内容） |
| **Ajax** | 当前域的 JS 不能向其他域发送 XMLHttpRequest / Fetch 请求 |

#### 不受同源策略限制的情况

同源策略**只限制 JavaScript**，以下资源加载不受限：

- `<img>` 的 src
- `<link>` 的 href
- `<script>` 的 src
- `<iframe>` 的 src（可加载，但 JS 不能操作其 DOM）

因为这些资源的加载不会把响应内容交给 JS 处理，不存在通过响应结果进行恶意操作的风险。

### 面试追问

1. **同源策略的目的是什么？** 保护用户信息安全。防止恶意网站通过 JS 读取其他网站的 Cookie（窃取登录态）、操作其他网站的 DOM（钓鱼）、或发送伪造请求（CSRF）。它是浏览器安全模型的基石。

2. **`<img src="其他域图片">` 为什么不受同源策略限制？** 因为 `<img>` 加载是浏览器直接渲染图片，响应内容不会暴露给页面的 JavaScript（无法通过 JS 读取图片像素数据以外的跨域信息）。没有通过 JS 操作响应结果的风险，所以不受限。但 Canvas 绘制跨域图片会「污染」Canvas，导致无法导出。

## 34. 如何解决跨域问题

**记忆口诀：**「CORS 最正统，JSONP 只 GET，postMessage 窗口通，代理隐藏真实源」

**核心要点：**
- 跨域是浏览器同源策略导致的，服务端之间不存在跨域
- CORS 是最标准、最推荐的方案，需浏览器和服务端共同支持
- 其他方案：JSONP、postMessage、Nginx/Node 代理、document.domain 等

### 详细解答

#### 方案总览

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **CORS** | 服务端设置响应头允许跨域 | 标准方案，支持所有 HTTP 方法 | 需服务端配合 |
| **JSONP** | 利用 `<script>` 无跨域限制 | 兼容老浏览器 | 仅 GET，不安全 |
| **postMessage** | HTML5 窗口间通信 API | 安全灵活 | 仅限窗口/iframe 通信 |
| **Nginx 反向代理** | 代理服务器转发请求 | 对前端透明 | 需运维配置 |
| **Node 中间件代理** | 开发环境 webpack-dev-server proxy | 开发方便 | 仅开发环境 |
| **document.domain** | 设置相同主域 | 简单 | 仅限主域相同的子域 |
| **WebSocket** | 协议本身支持跨域 | 全双工通信 | 需服务端支持 |

#### （1）CORS（跨域资源共享）

浏览器将 CORS 分为**简单请求**和**非简单请求**：

**简单请求条件：**
- 方法为 GET、HEAD、POST
- 头信息不超过：Accept、Accept-Language、Content-Language、Content-Type（限三种值）

**简单请求流程：** 浏览器直接发请求，附带 `Origin` 头；服务端返回 `Access-Control-Allow-Origin`。

**非简单请求流程：** 先发 **OPTIONS 预检请求**，服务端返回允许的方法、头信息、是否允许 Cookie 等；预检通过后，才发正式请求。

```js
// 服务端需设置的响应头（非简单请求）
Access-Control-Allow-Origin: http://api.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: X-Custom-Header
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 1728000  // 预检结果缓存时间
```

**携带 Cookie 的三个条件：**
1. 前端设置 `withCredentials: true`
2. 服务端 `Access-Control-Allow-Credentials: true`
3. `Access-Control-Allow-Origin` 不能为 `*`，必须指定具体域名

#### （2）JSONP

```js
function handleCallback(res) {
  console.log(res)
}
const script = document.createElement('script')
script.src = 'http://api.example.com/data?callback=handleCallback'
document.head.appendChild(script)
// 服务端返回：handleCallback({"data": "..."})
```

利用 `<script>` 标签不受同源策略限制，仅支持 GET，存在 XSS 风险。

#### （3）postMessage

```js
// 发送方
iframe.contentWindow.postMessage(JSON.stringify(data), 'http://target.com')

// 接收方
window.addEventListener('message', (e) => {
  if (e.origin !== 'http://trusted.com') return  // 验证来源
  const data = JSON.parse(e.data)
})
```

#### （4）Nginx 反向代理

```nginx
server {
    listen 80;
    server_name www.domain1.com;
    location /api/ {
        proxy_pass http://www.domain2.com:8080/;
        add_header Access-Control-Allow-Origin http://www.domain1.com;
        add_header Access-Control-Allow-Credentials true;
    }
}
```

前端请求同源的 `/api/`，Nginx 转发到 domain2，浏览器无跨域感知。

#### （5）开发环境代理

```js
// webpack.config.js
devServer: {
  proxy: {
    '/api': {
      target: 'http://www.domain2.com:8080',
      changeOrigin: true
    }
  }
}
```

### 面试追问

1. **简单请求和非简单请求的区别？预检请求的作用是什么？** 简单请求（GET/HEAD/POST + 有限头信息）直接发送，无需预检。非简单请求（如 PUT/DELETE、自定义头）会先发 OPTIONS 预检，询问服务端是否允许该跨域请求。预检通过后才会发正式请求，防止跨域请求对服务端造成非预期影响。

2. **JSONP 和 CORS 相比有什么安全隐患？** JSONP 通过 `<script>` 加载，服务端返回的是可执行 JS 代码，若服务端被攻击或不可信，可能返回恶意脚本（XSS）。CORS 是浏览器原生机制，响应数据不会作为脚本执行，且可通过 `Access-Control-Allow-Origin` 精确控制允许的来源，安全性更高。

## 35. 正向代理和反向代理的区别

**记忆口诀：**「正向代理客户端，反向代理服务端，一个帮客户翻墙，一个帮服务器分流」

**核心要点：**
- 正向代理代表客户端发请求，客户端知道代理的存在
- 反向代理代表服务器接收请求，客户端不知道后端真实服务器
- 核心区别：代理的对象不同（客户端 vs 服务端）

### 详细解答

| 对比项 | 正向代理（Forward Proxy） | 反向代理（Reverse Proxy） |
| --- | --- | --- |
| **代理对象** | 客户端 | 服务端 |
| **客户端感知** | 客户端知道并配置代理 | 客户端不知道后端服务器 |
| **服务端感知** | 服务端以为请求来自代理 IP | 服务端知道是代理转发 |
| **典型场景** | VPN、科学上网、公司内网访问外网 | 负载均衡、HTTPS 卸载、隐藏后端 |
| **部署位置** | 客户端侧或客户端网络内 | 服务端侧 |

#### 正向代理

```
客户端 ──→ 正向代理 ──→ 目标服务器
         （代理替客户端发请求）

场景：公司内网通过代理访问外网（防火墙限制）
      VPN 隐藏客户端真实 IP
```

- 客户端**主动配置**代理地址
- 目标服务器看到的是**代理的 IP**，不知道真实客户端

#### 反向代理

```
客户端 ──→ 反向代理 ──→ 后端服务器 A
                      ──→ 后端服务器 B
                      ──→ 后端服务器 C

场景：Nginx 负载均衡、CDN、API 网关
```

- 客户端以为在直接访问服务器，**不知道后端有多台服务器**
- 反向代理负责请求分发、SSL 终止、缓存、安全防护

### 面试追问

1. **Nginx 做跨域代理属于正向还是反向代理？** 属于**反向代理**。Nginx 部署在服务端，客户端请求发到 Nginx（同源），Nginx 将请求转发到后端 API 服务器。客户端不知道真实的后端地址，Nginx 代表后端接收和处理请求。

2. **正向代理和反向代理在跨域场景中分别怎么用？** 正向代理：客户端配置代理，由代理服务器代为请求目标 API（如开发时用 Charles/Fiddler）。反向代理：在服务端部署 Nginx，前端请求同源的 Nginx 地址，Nginx 转发到跨域 API 并添加 CORS 头，前端无跨域问题。实际开发中反向代理更常用。

## 36. Nginx的概念及其工作原理

**记忆口诀：**「Nginx 轻量高性能，事件驱动异步处理，Master 管 Worker 扛请求」

**核心要点：**
- Nginx 是轻量级 Web 服务器，也用于反向代理、负载均衡、HTTP 缓存
- 采用事件驱动（event-driven）模型，区别于 Apache 的进程/线程模型
- Master 进程管理 Worker 进程，Worker 进程可同时处理大量请求

### 详细解答

#### Nginx 的定位

Nginx 是一款**高性能 HTTP 服务器和反向代理服务器**，主要用途：

| 用途 | 说明 |
| --- | --- |
| Web 服务器 | 静态资源托管（HTML、CSS、JS、图片） |
| 反向代理 | 将请求转发到后端应用服务器 |
| 负载均衡 | 将流量分发到多个后端节点 |
| HTTP 缓存 | 缓存响应减少后端压力 |
| SSL 终止 | 在 Nginx 层处理 HTTPS 加解密 |

#### 工作原理

**架构模型：Master-Worker**

```
Master Process（主进程）
  ├── 读取配置
  ├── 绑定端口
  ├── 创建/管理 Worker 进程
  └── 平滑重启、热升级

Worker Process × N（工作进程）
  ├── 每个 Worker 独立处理请求
  ├── 采用 epoll/kqueue 事件驱动
  └── 单 Worker 可处理数千并发连接
```

#### 与 Apache 的核心区别

| 特性 | Nginx | Apache |
| --- | --- | --- |
| 模型 | **Event-driven（事件驱动）** | Process/Thread-based（进程/线程） |
| 并发处理 | 单 Worker 处理大量连接 | 每个进程/线程处理一个连接 |
| 内存占用 | 低 | 相对较高 |
| 静态资源 | 极高效 | 一般 |
| 动态内容 | 需反向代理到后端（如 Node/Java） | 内置模块直接处理 |

**事件驱动原理：** Nginx 使用 epoll（Linux）/ kqueue（BSD）等 I/O 多路复用机制，一个 Worker 进程通过事件循环同时监控多个连接，哪个连接有数据就处理哪个，无需为每个连接创建进程/线程，因此高并发下性能优异。

### 面试追问

1. **Nginx 为什么比 Apache 性能高？** 核心在于 I/O 模型：Nginx 是事件驱动的异步非阻塞模型，少量 Worker 进程就能处理数万并发连接；Apache 传统模式为每个连接分配一个进程/线程，连接数增加时上下文切换和内存开销急剧上升。Nginx 特别适合静态资源服务和高并发反向代理场景。

2. **Nginx 的 Master 进程挂了会怎样？** Worker 进程会继续运行并完成已在处理的请求，但无法接受新连接，也无法热更新配置。通常 Master 进程非常稳定，极少崩溃。若 Master 退出，需要重新启动 Nginx 服务，Master 会重新读取配置并 fork 新的 Worker 进程。

## 37. 事件是什么？事件模型？

**记忆口诀：**「DOM0 直接绑，IE 冒泡两阶段，DOM2 捕获冒泡三阶段，addEventListener 是标准」

**核心要点：**
- 事件是用户操作或浏览器行为（click、load、scroll 等）的封装，包含事件信息和操作方法
- 三种事件模型：DOM0（直接绑定）、IE（冒泡）、DOM2（捕获 + 冒泡）
- DOM2 是标准模型，通过 addEventListener 注册，第三个参数控制捕获/冒泡

### 详细解答

#### 什么是事件

事件是用户操作网页时发生的交互动作（click、mousemove、keydown 等），也可以是文档加载、窗口滚动/resize 等浏览器行为。事件被封装为 **event 对象**，包含：

- **事件属性**：type、target、currentTarget、timestamp 等
- **事件方法**：preventDefault()、stopPropagation()、stopImmediatePropagation() 等

#### 三种事件模型

| 模型 | 绑定方式 | 事件流 | 兼容性 |
| --- | --- | --- | --- |
| **DOM0** | `onclick = fn` 或 HTML 属性 | 无标准事件流（实际仅冒泡） | 所有浏览器 |
| **IE** | `attachEvent('onclick', fn)` | 两阶段：目标 → 冒泡到 document | 仅 IE |
| **DOM2** | `addEventListener('click', fn, useCapture)` | 三阶段：捕获 → 目标 → 冒泡 | 标准，现代浏览器 |

#### DOM2 事件流三阶段

```
Window
  ↓ 捕获阶段（Capture）：从外到内
Document
  ↓
<html>
  ↓
<body>
  ↓
<div>          ← 目标阶段（Target）
  ↓ 冒泡阶段（Bubble）：从内到外
<body>
  ↓
<html>
  ↓
Document
  ↓
Window
```

```js
// DOM2 标准写法
element.addEventListener('click', handler, false)  // false = 冒泡（默认）
element.addEventListener('click', handler, true)   // true = 捕获

// DOM0 写法
element.onclick = function(e) { /* ... */ }
```

#### 事件模型演进

- **DOM0**：简单直接，但同一事件只能绑定一个处理函数（后者覆盖前者）
- **IE**：引入冒泡概念，attachEvent 可绑定多个处理函数，但仅 IE 支持
- **DOM2**：W3C 标准，完整三阶段事件流，addEventListener 可绑定多个处理函数且可指定捕获/冒泡

### 面试追问

1. **事件捕获和事件冒泡有什么区别？实际开发中用哪个？** 捕获是从 Window 到目标元素（外→内），冒泡是从目标元素到 Window（内→外）。实际开发中**几乎都用冒泡**（addEventListener 第三个参数为 false 或省略），因为事件委托基于冒泡机制。捕获常用于需要在目标元素之前拦截事件的场景（如全局快捷键）。

2. **DOM0 和 DOM2 事件绑定有什么区别？** DOM0（`onclick = fn`）同一事件只能绑定一个处理函数，后绑定的覆盖先绑定的。DOM2（addEventListener）同一事件可绑定多个处理函数，按注册顺序执行。DOM0 的 handler 中 `this` 指向绑定元素；DOM2 取决于调用方式。现代开发应使用 DOM2。

## 38. 如何阻止事件冒泡

**记忆口诀：**「标准 stopPropagation，IE 用 cancelBubble，阻止冒泡不阻止默认行为」

**核心要点：**
- 阻止冒泡：`event.stopPropagation()`（W3C 标准）或 `event.cancelBubble = true`（IE）
- 阻止冒泡 ≠ 阻止默认行为，两者独立
- 阻止默认行为用 `event.preventDefault()`

### 详细解答

#### 阻止事件冒泡

```js
element.addEventListener('click', function(event) {
  // W3C 标准方法（推荐）
  event.stopPropagation()

  // IE 兼容写法
  event.cancelBubble = true
}, false)
```

#### 阻止默认行为

```js
element.addEventListener('click', function(event) {
  // 阻止默认行为（如链接跳转、表单提交）
  event.preventDefault()

  // IE 兼容写法
  event.returnValue = false
}, false)
```

#### 三个方法对比

| 方法 | 作用 | 兼容性 |
| --- | --- | --- |
| `stopPropagation()` | 阻止事件继续传播（捕获或冒泡） | W3C 标准 |
| `stopImmediatePropagation()` | 阻止传播 + 阻止同元素其他监听器执行 | W3C 标准 |
| `preventDefault()` | 阻止浏览器默认行为 | W3C 标准 |
| `cancelBubble = true` | 阻止冒泡 | IE 兼容 |
| `returnValue = false` | 阻止默认行为 | IE 兼容 |

#### 兼容性封装

```js
function stopBubble(e) {
  if (e.stopPropagation) {
    e.stopPropagation()
  } else {
    e.cancelBubble = true
  }
}
```

#### 典型使用场景

- 弹窗内的点击不应关闭弹窗（阻止冒泡到 document 上的关闭监听器）
- 嵌套元素各自有 click 事件，内层不希望触发外层
- 下拉菜单点击选项时不触发 document 上的「点击关闭菜单」

### 面试追问

1. **stopPropagation 和 stopImmediatePropagation 有什么区别？** `stopPropagation` 只阻止事件向父节点传播，同元素上其他监听器仍会执行。`stopImmediatePropagation` 不仅阻止传播，还会阻止**同元素上后续注册的监听器**执行。后者是前者的加强版。

2. **return false 能同时阻止冒泡和默认行为吗？** 在 DOM0 模型中（`onclick = function() { return false }`），`return false` 等效于同时调用 `preventDefault()` 和 `stopPropagation()`。但在 DOM2 的 addEventListener 中，return false **无效**，必须显式调用 `preventDefault()` 和 `stopPropagation()`。

## 39. 对事件委托的理解

**记忆口诀：**「利用冒泡上抛，父元素统一处理，少绑监听省内存，动态元素也能管」

**核心要点：**
- 事件委托利用事件冒泡，将子元素的事件处理逻辑委托给父元素
- 优点：减少内存消耗、支持动态元素、代码更简洁
- 局限：focus/blur 无冒泡，mousemove 性能差，不适合所有事件

### 详细解答

#### 概念

事件委托（Event Delegation，也称事件代理）是指**利用浏览器事件冒泡机制**，将子元素的事件监听函数定义在父元素上，由父元素统一处理多个子元素的事件。

#### 工作原理

```
用户点击 <li>
  ↓ 冒泡
<ul id="list">  ← 事件委托绑在这里
  ↓ event.target 指向实际被点击的 <li>
  ↓ 通过 target 判断并处理
```

#### 基本实现

```js
document.getElementById('list').addEventListener('click', function(e) {
  const target = e.target
  if (target.tagName.toLowerCase() === 'li') {
    console.log('点击了：', target.innerHTML)
  }
})
```

#### 优点

| 优点 | 说明 |
| --- | --- |
| **减少内存消耗** | 1000 个 `<li>` 只绑 1 个监听器，而非 1000 个 |
| **动态绑定** | 后续新增的 `<li>` 自动享有事件处理，无需重新绑定 |
| **代码简洁** | 统一管理，便于维护 |

#### 局限性

| 局限 | 原因 |
| --- | --- |
| focus / blur | 没有冒泡机制，无法委托 |
| mouseenter / mouseleave | 不冒泡 |
| mousemove / mouseout | 有冒泡但需不断计算位置，性能差 |
| 事件目标不确定 | 需要额外逻辑向上查找匹配元素 |

#### 性能注意事项

- 减少委托层级，避免绑定在 body 上
- 合并多个事件的委托到一次绑定，在回调中分发
- 只在必须的地方使用（如 AJAX 局部刷新区域）

### 面试追问

1. **事件委托为什么能支持动态元素？** 因为事件绑定在父元素上，事件冒泡时父元素的监听器始终会触发。新增的子元素不需要单独绑定，点击时事件从子元素冒泡到父元素，父元素通过 `event.target` 识别实际触发元素并处理。删除元素也无需解绑。

2. **哪些事件不适合用事件委托？** `focus` 和 `blur` 没有冒泡机制，无法委托。`mouseenter`/`mouseleave` 同样不冒泡。`mousemove` 虽然冒泡，但需要不断计算鼠标位置来判断目标元素，性能开销大。这些事件需要直接绑定在目标元素上。

## 40. 事件委托的使用场景

**记忆口诀：**「列表菜单表格行，动态增删用委托，点击目标非自身就向上找父」

**核心要点：**
- 列表、菜单、表格等大量重复元素是最典型的委托场景
- 点击目标可能是子元素（span、img），需向上查找匹配的目标元素
- 动态增删的 DOM 结构特别适合事件委托

### 详细解答

#### 典型场景

| 场景 | 说明 |
| --- | --- |
| **列表项点击** | ul/ol 下大量 li 的点击处理 |
| **表格行操作** | tbody 中动态增删的行，统一处理编辑/删除 |
| **下拉菜单** | 菜单项点击，动态渲染的选项 |
| **标签页切换** | tab 栏的多个 tab 项 |
| **所有 a 标签** | 页面中链接的统一拦截或统计 |

#### 场景一：简单委托（target 就是目标元素）

```js
// 给页面所有 a 标签添加 click 事件
document.addEventListener('click', function(e) {
  if (e.target.nodeName === 'A') {
    console.log('点击了链接：', e.target.href)
  }
}, false)
```

#### 场景二：向上查找（target 可能是子元素）

当 a 标签内部有 `<span>`、`<img>` 等子元素时，点击子元素 `e.target` 指向的是 span/img 而非 a 标签：

```js
document.addEventListener('click', function(e) {
  let node = e.target
  // 向上遍历 DOM 树，直到找到 A 标签或到达 body
  while (node && node.nodeName !== 'BODY') {
    if (node.nodeName === 'A') {
      console.log('点击了链接：', node.href)
      break
    }
    node = node.parentNode
  }
}, false)
```

#### 场景三：列表 + 动态增删

```js
const list = document.getElementById('todo-list')

list.addEventListener('click', function(e) {
  const target = e.target

  // 删除按钮
  if (target.classList.contains('delete-btn')) {
    target.closest('li').remove()  // 无需解绑事件
  }

  // 完成切换
  if (target.classList.contains('toggle-btn')) {
    target.closest('li').classList.toggle('done')
  }
})

// 动态添加新项，自动享有事件处理
function addItem(text) {
  const li = document.createElement('li')
  li.innerHTML = `<span>${text}</span>
    <button class="toggle-btn">完成</button>
    <button class="delete-btn">删除</button>`
  list.appendChild(li)  // 无需 bindEvent
}
```

#### 现代简化：closest API

```js
document.addEventListener('click', function(e) {
  const link = e.target.closest('a')
  if (link) {
    console.log('点击了链接：', link.href)
  }
})
```

`Element.closest(selector)` 从当前元素向上查找匹配的祖先元素（含自身），比手动 while 循环更简洁。

### 面试追问

1. **事件委托中 event.target 和 event.currentTarget 有什么区别？** `event.target` 是**实际触发事件的元素**（如 li 内的 span）；`event.currentTarget` 是**绑定监听器的元素**（如委托绑定的 ul）。在事件委托中，两者通常不同，需要通过 target 向上查找来确定用户意图操作的元素。

2. **jQuery 的事件委托是怎么实现的？** jQuery 的 `.on('click', 'li', handler)` 就是事件委托。它内部在父元素上绑定监听器，当事件冒泡到父元素时，检查 `event.target` 是否匹配选择器（或在其祖先链中匹配），匹配则调用 handler，并将 handler 中的 `this` 指向匹配的元素。原理与原生事件委托完全一致。

## 41.对事件循环的理解

**记忆口诀：**「单线程跑 JS，同步先执行，微任务清完再宏任务，一轮循环就结束」

**核心要点：**
- 浏览器 JS 在单线程上执行，通过事件循环（Event Loop）协调同步代码与异步任务
- 异步任务分为宏任务（Macro Task）和微任务（Micro Task），微任务优先级高于宏任务
- 每轮循环：执行一个宏任务 → 清空全部微任务 → 必要时渲染 UI → 进入下一轮

### 详细解答

JavaScript 是单线程语言，所有任务都在一条主线程上处理。若某个任务执行时间过长，会阻塞后续任务，导致页面卡顿。浏览器通过**事件循环**机制，将任务分为**同步任务**和**异步任务**，异步任务又细分为**宏任务**和**微任务**，从而实现非阻塞执行。

#### 核心概念

| 概念 | 说明 |
| --- | --- |
| 执行栈（Call Stack） | 存放正在执行的函数，后进先出（LIFO） |
| 宏任务队列 | 存放 setTimeout、I/O、UI 渲染等宏任务，先进先出（FIFO） |
| 微任务队列 | 存放 Promise.then、MutationObserver 等微任务，先进先出（FIFO） |

#### 浏览器 Event Loop 执行流程

```
1. 执行全局同步代码（第一个宏任务：script）
2. 同步代码执行过程中，遇到宏任务 → 放入宏任务队列
                      遇到微任务 → 放入微任务队列
3. 同步代码执行完毕
4. 检查微任务队列，依次执行直到清空
5. 执行一个宏任务（从队列头部取出一个）
6. 再次清空微任务队列
7. 判断是否需要渲染 UI（通常约 16.6ms 一次）
8. 重复步骤 5-7，直到所有任务完成
```

**关键规则：**
- 每执行完**一个**宏任务，必须**清空**当前所有微任务，才能执行下一个宏任务
- 微任务执行过程中产生的新微任务，也会在本轮循环中被立即执行
- 宏任务中产生的微任务，会在该宏任务执行完后、下一个宏任务执行前被清空

#### 经典示例

```js
console.log('1')

setTimeout(() => {
  console.log('2')
  Promise.resolve().then(() => console.log('3'))
}, 0)

Promise.resolve().then(() => {
  console.log('4')
  setTimeout(() => console.log('5'), 0)
})

console.log('6')
// 输出：1 → 6 → 4 → 2 → 3 → 5
```

**执行分析：**
1. 同步：`1`、`6`
2. 微任务：`4`（同时 setTimeout 5 入宏任务队列）
3. 宏任务：`2`（同时 Promise 3 入微任务队列）
4. 微任务：`3`
5. 宏任务：`5`

#### Node.js 中的事件循环（简要）

Node.js 基于 **libuv** 实现事件循环，分为 6 个阶段：

| 阶段 | 作用 |
| --- | --- |
| timers | 执行 setTimeout/setInterval 到期回调 |
| pending callbacks | 执行系统级延迟回调 |
| idle, prepare | 内部使用，可忽略 |
| poll | 获取新的 I/O 事件，执行 I/O 回调 |
| check | 执行 setImmediate 回调 |
| close callbacks | 执行 close 事件回调（如 socket.on('close')） |

Node 中 `process.nextTick` 不属于 Event Loop 任何阶段，拥有**最高优先级**，每个阶段切换前都会先清空 nextTick 队列。

### 面试追问

1. **为什么微任务优先级高于宏任务？** 微任务（如 Promise 回调）通常用于处理当前任务的后续逻辑，需要尽快完成以保证数据一致性；若等到下一个宏任务才执行，可能导致状态不一致。浏览器设计为每轮宏任务后立即清空微任务，确保 Promise 链式调用能连续执行完毕。

2. **requestAnimationFrame 和 setTimeout 谁先执行？** `requestAnimationFrame` 回调在**浏览器渲染前**执行，属于渲染相关调度；`setTimeout` 是宏任务。一轮 Event Loop 中，宏任务执行完并清空微任务后，才会进入渲染阶段，此时 rAF 回调才会触发。因此同一轮循环中，setTimeout 先于 rAF 执行。

## 42.宏任务和微任务分别有哪些

**记忆口诀：**「宏：Script、Timer、I/O、UI；微：Promise、nextTick、MutationObserver」

**核心要点：**
- 宏任务由宿主环境（浏览器/Node）调度，每次 Event Loop 只执行一个
- 微任务由 JS 引擎创建，每轮宏任务执行后必须全部清空
- Node 中 process.nextTick 优先级高于 Promise 微任务

### 详细解答

| 分类 | 常见任务 | 说明 |
| --- | --- | --- |
| **宏任务** | 全局 Script 代码 | 整个 `<script>` 标签内容作为第一个宏任务 |
| | setTimeout / setInterval | 定时器回调 |
| | setImmediate（Node） | Node 专属，在 check 阶段执行 |
| | I/O 操作 | 文件读写、网络请求回调 |
| | UI 渲染 | 浏览器渲染相关任务 |
| | requestAnimationFrame | 部分资料将其归为宏任务 |
| **微任务** | Promise.then / catch / finally | ES6 Promise 回调 |
| | async/await | 本质是 Promise 语法糖，await 之后的代码相当于 .then |
| | MutationObserver | DOM 变化监听回调 |
| | queueMicrotask() | 手动创建微任务 |
| | process.nextTick（Node） | Node 专属，优先级最高，独立于 Event Loop |

#### 速查对比

```
宏任务（Macro Task）          微任务（Micro Task）
├── script 整体执行           ├── Promise 回调
├── setTimeout                ├── async/await 后续
├── setInterval               ├── MutationObserver
├── setImmediate (Node)       ├── queueMicrotask
├── I/O 回调                  └── process.nextTick (Node，优先级最高)
└── UI rendering
```

#### 判断技巧

- **看到 Promise / async/await** → 微任务
- **看到 setTimeout / setInterval** → 宏任务
- **Node 环境** → 额外记住 setImmediate（宏）和 process.nextTick（比微任务还优先）

### 面试追问

1. **async/await 和 Promise.then 的执行顺序一样吗？** 一样。`async` 函数中 `await` 之前的代码是同步执行，`await` 之后的代码相当于 `Promise.then` 回调，属于微任务。多个 await 依次执行时，每个 await 后的代码都会作为独立的微任务入队。

2. **MutationObserver 为什么是微任务？** DOM 变化可能连续触发多次，若用宏任务会导致中间状态被渲染到屏幕上。设计为微任务后，可以在同一轮 Event Loop 内批量处理所有 DOM 变更，避免不必要的重复渲染，保证 DOM 状态的一致性。

## 43.什么是执行栈

**记忆口诀：**「函数调用进栈，执行完出栈，后进先出；递归过深会爆栈」

**核心要点：**
- 执行栈（Call Stack）是 JS 引擎管理函数调用的栈结构，遵循 LIFO（后进先出）
- 全局代码、函数调用、嵌套调用都会压栈，执行完毕则弹栈
- 栈有大小限制，无限递归会导致 Stack Overflow

### 详细解答

执行栈（Execution Context Stack / Call Stack）是 JavaScript 引擎用来**追踪函数调用关系**的数据结构，本质上是一个**栈（Stack）**，遵循**先进后出（LIFO）**原则。

#### 工作原理

```js
function foo() {
  console.log('foo')
}
function bar() {
  foo()
}
bar()
```

**执行过程：**

```
1. 全局代码入栈          → [global]
2. bar() 被调用，bar 入栈  → [global, bar]
3. foo() 被调用，foo 入栈  → [global, bar, foo]
4. foo 执行完毕，foo 出栈  → [global, bar]
5. bar 执行完毕，bar 出栈  → [global]
6. 全局代码执行完毕        → []
```

#### 错误堆栈（Stack Trace）

报错信息中的调用栈就是执行栈的快照：

```js
function foo() {
  throw new Error('error')
}
function bar() {
  foo()
}
bar()

// Error: error
//   at foo (...)
//   at bar (...)
//   at ...
```

从下往上读：先进入 `bar`，再进入 `foo`，错误在 `foo` 中抛出。

#### 栈溢出（Stack Overflow）

```js
function bar() {
  bar() // 无限递归
}
bar()
// RangeError: Maximum call stack size exceeded
```

每次递归调用都会压入新栈帧，栈空间有限（通常几千到几万层），超出限制就会报栈溢出错误。

#### 执行栈 vs 任务队列

| 对比 | 执行栈 | 任务队列 |
| --- | --- | --- |
| 存放内容 | 正在执行的同步代码 | 等待执行的异步回调 |
| 数据结构 | 栈（LIFO） | 队列（FIFO） |
| 执行时机 | 立即执行 | 等执行栈清空后，由 Event Loop 调度 |

### 面试追问

1. **执行栈和执行上下文是什么关系？** 执行上下文（Execution Context）是 JS 代码运行时的环境，包含变量环境、词法环境、this 绑定等。每次函数调用都会创建新的执行上下文并**压入执行栈**，函数执行完毕则**弹出**。执行栈是管理多个执行上下文入栈/出栈的机制。

2. **为什么 JS 引擎要用栈而不是队列管理函数调用？** 函数调用天然具有嵌套和返回特性（A 调 B，B 执行完返回 A），栈的 LIFO 结构完美匹配「后调用的先返回」这一语义。若用队列，无法正确还原函数调用层级和返回地址。

## 44.Node 中的 Event Loop 和浏览器中的有什么区别？process.nextTick 执行顺序？

**记忆口诀：**「浏览器：宏微交替简单循环；Node：libuv 六阶段轮询；nextTick 优先级最高」

**核心要点：**
- 浏览器 Event Loop 以宏任务-微任务交替为主，结构简单
- Node Event Loop 基于 libuv，分为 timers → pending → idle → poll → check → close 六个阶段
- process.nextTick 不属于 Event Loop 任何阶段，每个阶段切换前优先清空

### 详细解答

Node.js 和浏览器的 Event Loop **完全不同**，Node 基于 **libuv** 实现，结构更复杂。

#### 浏览器 vs Node 对比

| 对比维度 | 浏览器 | Node.js |
| --- | --- | --- |
| 实现基础 | HTML 规范定义 | libuv 库 |
| 结构 | 宏任务队列 + 微任务队列 | 6 个阶段的循环 |
| 微任务 | Promise.then、MutationObserver | Promise.then + process.nextTick |
| 特有 API | requestAnimationFrame | setImmediate、process.nextTick |
| 渲染 | 有 UI 渲染步骤 | 无 UI 渲染 |

#### Node Event Loop 六个阶段

```
   ┌───────────────────────────┐
┌─>│         timers            │  setTimeout/setInterval 到期回调
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │    pending callbacks      │  系统级延迟 I/O 回调
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │   idle, prepare           │  内部使用
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │          poll             │  获取 I/O 事件，执行 I/O 回调
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │          check            │  setImmediate 回调
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │     close callbacks       │  socket.on('close') 等
│  └─────────────┬─────────────┘
└─────────────────┘
```

每个阶段：从对应队列取出回调执行 → 执行完毕清空微任务 → 进入下一阶段。

#### setTimeout vs setImmediate 执行顺序

**情况一：不在 I/O 回调中，顺序不确定**

```js
setTimeout(() => console.log('setTimeout'), 0)
setImmediate(() => console.log('setImmediate'))
// 可能输出 setTimeout 先，也可能 setImmediate 先
```

原因：`setTimeout(fn, 0)` 源码中实际最小延迟为 1ms。若进入 Event Loop 耗时 > 1ms，timers 阶段直接执行 setTimeout；若 < 1ms，则先进入 poll 再到 check 执行 setImmediate。

**情况二：在 I/O 回调中，setImmediate 一定先执行**

```js
const fs = require('fs')
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0)
  setImmediate(() => console.log('immediate'))
})
// 永远输出：immediate → timeout
```

原因：I/O 回调在 poll 阶段执行，执行完后队列空且有 setImmediate，直接进入 check 阶段。

#### process.nextTick 执行顺序

`process.nextTick` **不属于 Event Loop 任何阶段**，有独立的 `nextTickQueue`，在**每个阶段切换前**优先清空，优先级高于 Promise 微任务。

```js
setTimeout(() => {
  console.log('timer1')
  Promise.resolve().then(() => console.log('promise1'))
}, 0)

process.nextTick(() => {
  console.log('nextTick1')
  process.nextTick(() => console.log('nextTick2'))
})

Promise.resolve().then(() => console.log('promise2'))

// 输出：nextTick1 → nextTick2 → promise2 → timer1 → promise1
```

**完整优先级（从高到低）：**

```
process.nextTick > Promise 微任务 > 宏任务（timers/setImmediate/I/O）
```

### 面试追问

1. **为什么 Node 要设计 setImmediate 而不是只用 setTimeout(fn, 0)？** setImmediate 专用于 I/O 回调执行完毕后立即执行的逻辑，在 check 阶段触发，避免 timers 阶段的不确定延迟。典型场景：服务器 listen 后立即 accept 连接，写在 setImmediate 中可确保在 poll 阶段 I/O 事件处理完后执行，比 setTimeout(fn, 0) 更语义化且性能更好。

2. **Node 中微任务在哪个时机执行？** 每个 Event Loop 阶段执行完该阶段的回调队列后，会先清空 `process.nextTick` 队列，再清空 Promise 微任务队列，然后才进入下一个阶段。这与浏览器「一个宏任务后清空所有微任务」类似，但 Node 在每个阶段切换时都会执行这一步骤。

## 45.事件触发的过程是怎样的

**记忆口诀：**「捕获从外到内，目标阶段触发，冒泡从内到外；阻止传播分 stopPropagation 和 stopImmediatePropagation」

**核心要点：**
- DOM 事件传播分三阶段：捕获（Capture）→ 目标（Target）→ 冒泡（Bubble）
- addEventListener 第三个参数 useCapture 决定注册捕获还是冒泡监听
- stopPropagation 阻止传播，stopImmediatePropagation 还能阻止同元素其他监听器

### 详细解答

DOM 事件从触发到执行回调，经历**三个传播阶段**：

```
Window → Document → ... → 目标元素的父节点 → 目标元素 → 父节点 → ... → Window
  ←────────── 捕获阶段 ──────────→  ←目标→  ←────────── 冒泡阶段 ──────────→
```

#### 三阶段详解

| 阶段 | 方向 | 触发条件 |
| --- | --- | --- |
| 捕获阶段 | window → 目标元素 | 遇到 `useCapture: true` 的监听器 |
| 目标阶段 | 到达目标元素 | 在目标元素上触发所有监听器 |
| 冒泡阶段 | 目标元素 → window | 遇到 `useCapture: false` 的监听器 |

#### 注册事件

```js
// 第三个参数：false（默认）= 冒泡；true = 捕获
element.addEventListener('click', handler, false)
element.addEventListener('click', handler, true)

// 对象形式
element.addEventListener('click', handler, {
  capture: false,  // 同 useCapture
  once: true,      // 只触发一次后自动移除
  passive: true    // 不会调用 preventDefault（优化滚动性能）
})
```

#### 特例：同一元素上捕获和冒泡的顺序

若在同一节点上**同时**注册捕获和冒泡，按**注册顺序**执行，而非先捕获后冒泡：

```js
node.addEventListener('click', () => console.log('冒泡'), false)
node.addEventListener('click', () => console.log('捕获'), true)
// 点击输出：冒泡 → 捕获（按注册顺序）
```

#### 阻止事件传播

```js
// stopPropagation：阻止事件继续传播（捕获或冒泡方向）
event.stopPropagation()

// stopImmediatePropagation：阻止传播 + 阻止同元素其他监听器
event.stopImmediatePropagation()
```

```js
node.addEventListener('click', (e) => {
  e.stopImmediatePropagation()
  console.log('第一个')
}, false)

node.addEventListener('click', () => {
  console.log('第二个') // 不会执行
}, true)
```

**注意：** `stopPropagation` 不仅能阻止冒泡，也能阻止捕获阶段的传播。

### 面试追问

1. **事件委托（事件代理）的原理是什么？** 利用冒泡机制，将子元素的事件监听器绑定到父元素上。点击子元素时，事件冒泡到父元素，通过 `event.target` 判断实际触发的子元素。优点：减少监听器数量、动态添加的子元素无需重新绑定。`event.target` 是触发源，`event.currentTarget` 是绑定监听的元素。

2. **passive: true 有什么作用？** 告诉浏览器该监听器**不会**调用 `preventDefault()`，浏览器可以立即执行默认行为（如滚动），无需等待 JS 执行完毕。这对 touchstart/touchmove/wheel 等事件的滚动性能优化至关重要。若 passive 监听器中调用 preventDefault 会被忽略并报警告。

## 46.V8的垃圾回收机制是怎样的

**记忆口诀：**「可达性标记，新生代 Scavenge 复制翻转，老生代标记清除/整理，增量标记减卡顿」

**核心要点：**
- V8 采用分代回收：新生代（存活短）+ 老生代（存活久），分别用不同算法
- 新生代用 Scavenge 复制算法，老生代用标记-清除 + 标记-整理
- 增量标记将 GC 拆分为小任务穿插执行，减少全停顿（Stop-The-World）

### 详细解答

V8 垃圾回收基于**可达性分析**：从 GC Root（全局对象、调用栈中的引用等）出发，能访问到的为**活动对象**，不能访问到的为**垃圾**，最终被回收。

#### 垃圾回收四步流程

```
1. 标记：从 GC Root 遍历，区分活动对象与垃圾对象
2. 回收：释放垃圾对象占用的内存
3. 整理（可选）：移动存活对象，消除内存碎片
4. 重复：持续监控堆内存使用情况
```

#### 分代回收策略

| 代 | 存放对象 | 回收器 | 算法 | 特点 |
| --- | --- | --- | --- | --- |
| 新生代 | 新创建、存活短的小对象 | 副垃圾回收器 | Scavenge（复制） | 空间小（1-8MB），回收快 |
| 老生代 | 存活久、体积大的对象 | 主垃圾回收器 | 标记-清除 + 标记-整理 | 空间大，回收慢 |

#### 新生代：Scavenge 算法

新生代分为两个等大的半空间：**From 空间**（使用中）和 **To 空间**（空闲）。

```
1. 新对象分配在 From 空间
2. From 空间满 → 触发 GC
3. 标记 From 中的活动对象
4. 将活动对象复制到 To 空间，紧凑排列（消除碎片）
5. From 与 To 角色互换（翻转）
6. 经过两次 GC 仍存活的对象 → 晋升到老生代
```

#### 老生代：标记-清除 + 标记-整理

- **标记-清除**：标记活动对象 → 直接清除垃圾（产生内存碎片）
- **标记-整理**：标记后 → 将活动对象移到一端 → 清除边界外内存（解决碎片，但需移动对象，耗时更长）

大对象（超过新生代阈值）直接分配到老生代。

#### 全停顿与增量标记

JS 运行在主线程，GC 执行时需暂停 JS 执行，称为**全停顿（Stop-The-World）**。老生代 GC 耗时长，会导致页面卡顿。

V8 采用**增量标记（Incremental Marking）**：将标记过程拆分为多个小任务，穿插在 JS 任务之间执行，避免长时间阻塞主线程。

#### 开发优化建议

```js
// 1. 数组清空用 length = 0，而非重新赋值 []
arr.length = 0

// 2. 不再使用的对象置 null，断开引用
obj = null

// 3. 循环中的函数表达式尽量提取到外部复用
const handler = () => { /* ... */ }
for (let i = 0; i < n; i++) {
  list[i].addEventListener('click', handler)
}
```

#### 扩展：引用计数法的缺陷

引用计数法记录每个值被引用的次数，为 0 时回收。缺陷：**循环引用**无法回收。

```js
let obj1 = {}, obj2 = {}
obj1.ref = obj2
obj2.ref = obj1
obj1 = null
obj2 = null
// 引用计数法：两者互相引用，计数永不为 0，造成内存泄漏
// 可达性分析：从 GC Root 不可达，正确回收
```

### 面试追问

1. **为什么新生代空间要设置得很小？** Scavenge 算法需要复制存活对象，空间越大，复制耗时越长。新生代假设「大多数对象朝生夕死」，设置小空间（1-8MB）可以更快触发 GC、更快回收，整体吞吐量更高。存活久的对象会晋升到老生代，由标记-清除/整理算法处理。

2. **增量标记是如何减少卡顿的？** 传统 GC 一次性标记整个堆，可能阻塞主线程数百毫秒。增量标记将标记过程拆分为多个 5-10ms 的小任务，利用 JS 执行间隙穿插完成，每次暂停时间极短，用户感知不到卡顿。代价是总标记时间略长（需额外处理标记期间引用变化的三色标记法）。

## 47.哪些操作会造成内存泄漏？

**记忆口诀：**「全局变量、忘清定时器、DOM 引用残留、闭包滥用，四大泄漏元凶」

**核心要点：**
- 内存泄漏 = 不再需要的内存未被释放，持续占用导致可用内存减少
- 常见原因：意外全局变量、未清除的定时器、脱离 DOM 的引用、闭包持有大对象
- 预防：及时清理引用、使用 WeakMap/WeakSet、Chrome DevTools Memory 面板排查

### 详细解答

内存泄漏是指程序中**已不再需要的内存**没有被释放，导致可用内存持续减少，最终可能引发页面卡顿甚至崩溃。

#### 常见内存泄漏场景

| 类型 | 原因 | 示例 |
| --- | --- | --- |
| 意外全局变量 | 未声明的变量挂载到 window | `function foo() { bar = 'leak' }` |
| 未清除的定时器 | setInterval 持续运行，回调引用外部变量 | 组件销毁后定时器未 clear |
| DOM 引用残留 | JS 变量仍引用已从 DOM 移除的元素 | `const el = document.getElementById('btn'); document.body.removeChild(el)` |
| 闭包滥用 | 闭包持有不再需要的变量 | 大数组被闭包长期引用 |
| 事件监听未移除 | 组件销毁后监听器仍存在 | SPA 路由切换未 removeEventListener |
| 控制台引用 | console.log 的对象被 DevTools 保留 | 生产环境遗留 console.log |
| Map/Set 强引用 | 对象作 key 且不再使用时未 delete | 缓存 Map 无限增长 |

#### 代码示例

**1. 意外全局变量**

```js
function leak() {
  name = 'global' // 未声明，等价于 window.name
}
```

**2. 定时器泄漏**

```js
const data = fetchLargeData()
setInterval(() => {
  processData(data) // data 被闭包引用，永远无法回收
}, 1000)
// 修复：组件销毁时 clearInterval(id)
```

**3. DOM 引用泄漏**

```js
let element = document.getElementById('button')
document.body.removeChild(element)
element = null // 必须手动解除引用
```

**4. 闭包泄漏**

```js
function outer() {
  const hugeArray = new Array(1000000).fill('data')
  return function inner() {
    console.log(hugeArray.length) // hugeArray 被闭包持有
  }
}
const fn = outer() // hugeArray 无法回收
```

#### 排查与预防

```js
// 1. 使用 WeakMap/WeakSet，key 被回收时自动清除
const cache = new WeakMap()

// 2. 组件销毁时清理
componentWillUnmount() {
  clearInterval(this.timer)
  this.element.removeEventListener('click', this.handler)
}

// 3. Chrome DevTools → Memory → Heap Snapshot 对比快照
```

### 面试追问

1. **WeakMap 为什么能避免内存泄漏？** WeakMap 的 key 必须是对象，且对 key 是**弱引用**——当 key 对象没有其他引用时，GC 会自动回收 key 及其对应的 value，无需手动 delete。适合 DOM 节点关联数据的场景，节点移除后关联数据自动释放。

2. **SPA 应用中如何排查内存泄漏？** ① Chrome DevTools Memory 面板，路由切换前后各拍 Heap Snapshot，对比 Detached DOM tree 和 Retainers；② Performance Monitor 观察 JS heap size 是否持续增长；③ 检查组件销毁钩子是否清理了定时器、事件监听、订阅；④ 避免在全局 store 中缓存组件级大对象。

## 48.渲染合成层与GPU渲染加速

**记忆口诀：**「DOM 生 RenderObject，分层 RenderLayer，独立合成 Compositing Layer 上 GPU」

**核心要点：**
- 浏览器渲染分 Network → Parse → Render（Style/Layout/Paint/Composite）阶段
- RenderLayer 分层减少全局重绘；Compositing Layer 可交由 GPU 加速
- transform/opacity 只触发 Composite，will-change 可提前告知浏览器优化

### 详细解答

#### 浏览器渲染流程

```
HTML → DOM Tree
CSS  → CSSOM
         ↓
    Render Tree（RenderObject 树，仅可见节点）
         ↓
    Layout（计算几何位置，即重排 Reflow）
         ↓
    Paint（绘制像素，即重绘 Repaint）
         ↓
    Composite（合成层合并，输出到屏幕）
```

#### 四棵树状结构

| 树 | 说明 |
| --- | --- |
| DOM Tree | HTML 解析产物 |
| RenderObject Tree | DOM + CSSOM 合并，一一对应可视元素 |
| RenderLayer Tree | 特定条件下节点提升为独立渲染层 |
| GraphicsLayer Tree | 合成层，由 GPU 处理，多个 RenderLayer 可映射到一个 GraphicsLayer |

#### 触发 RenderLayer 分层（常见条件）

- `document` 根层
- `<video>`、`<canvas>` 元素
- `transform: translateZ(0)`、`opacity` 动画、`will-change`
- `position: fixed` / `sticky`
- z-index 较大的元素（可能触发隐式合成，造成「层爆炸」）

#### Compositing Layer（合成层）

RenderLayer 传递到合成线程后，满足以下条件会升级为 Compositing Layer，交由 **GPU** 处理：

- 3D 或 perspective transform
- 加速解码的 `<video>`
- 3D/2D 加速的 `<canvas>`
- transform 或 opacity 动画
- CSS 滤镜（filter）
- 子级已是 Compositing Layer

#### 分层渲染的优势

| 优势 | 说明 |
| --- | --- |
| 局部更新 | 单层变更不影响其他层，减少全局 Layout/Paint |
| GPU 加速 | 合成层计算交给 GPU，释放 CPU |
| 跳过 Layout/Paint | transform、opacity 变更只触发 Composite |

#### 性能优化

```css
/* 推荐：只触发 Composite */
.animated {
  transform: translateX(100px);
  opacity: 0.5;
}

/* 提前告知浏览器变化，触发分层优化 */
.sidebar {
  will-change: transform;
}

/* 强制开启硬件加速（慎用） */
.gpu-layer {
  transform: translateZ(0);
}
```

**will-change 注意事项：**
- 不要大面积使用，每个合成层占用独立内存
- 动画前动态添加，动画后移除
- 低端设备慎用，可能导致模糊或内存暴涨

#### 副作用：层爆炸

过多合成层会消耗大量 GPU 内存（每个 GraphicsLayer 拥有完整位图）。Chrome 96+ 对分层规则做了优化，但仍需避免滥用 `translateZ(0)` 和 `will-change`。

### 面试追问

1. **transform 和 top/left 做动画，性能差异在哪？** `top/left` 改变元素几何位置，触发 **Layout → Paint → Composite** 全流程；`transform` 只触发 **Composite**，跳过 Layout 和 Paint。因此 transform 动画性能远优于 top/left，是实现 60fps 动画的首选。

2. **什么是隐式合成层？如何避免层爆炸？** 当元素 A 在 Compositing Layer 之上，且 z-index 较高时，浏览器可能为 A 创建隐式合成层以保证正确叠放顺序。若大量元素触发隐式合成，会导致「层爆炸」，GPU 内存暴涨。避免方法：减少不必要的 z-index 层叠、不滥用 translateZ(0)、用 Chrome Layers 面板审查分层情况。

## 49.iframe如何理解？有什么特点？一般应用在什么场景？

**记忆口诀：**「iframe 是嵌套网页的可替换元素，天然隔离又带跨域与安全坑，微前端曾用它」

**核心要点：**
- iframe 是 HTML 可替换元素，在当前页面嵌入独立浏览上下文（完整网页）
- 优点：隔离性强；缺点：XSS、点击劫持、性能开销、SEO 不友好
- 场景：嵌入第三方内容（视频/地图/广告）、文档预览、传统微前端方案

### 详细解答

#### iframe 是什么

`<iframe>` 在当前页面中嵌入另一个完整的 HTML 文档，形成独立的**浏览上下文（Browsing Context）**。它属于**可替换元素（Replaced Element）**，类似 `<img>`、`<video>`、`<canvas>`——内容不受当前文档 CSS 渲染模型控制，拥有固有尺寸。

```html
<iframe
  src="https://example.com/page"
  width="800"
  height="600"
  sandbox="allow-scripts allow-same-origin"
></iframe>
```

#### 核心特点

| 特点 | 说明 |
| --- | --- |
| 独立文档 | 拥有独立的 window、document、DOM、CSSOM |
| 可替换元素 | CSS 可控制位置尺寸，但不影响 iframe 内部内容样式 |
| 跨域隔离 | 不同源 iframe 无法直接访问父页面 DOM（同源策略） |
| 独立渲染 | 内部页面独立渲染，不影响父页面布局（但占用资源） |
| 可设样式表 | iframe 内部可有自己的 CSS，不继承父文档样式 |

#### 安全隐患

| 风险 | 说明 | 防护 |
| --- | --- | --- |
| XSS | 嵌入页面含恶意脚本 | sandbox 属性、CSP |
| 点击劫持 | 透明 iframe 覆盖诱骗点击 | X-Frame-Options: DENY |
| CSRF | iframe 内自动发起跨站请求 | SameSite Cookie、CSP |

**安全防护措施：**

```html
<!-- sandbox 限制权限 -->
<iframe sandbox="allow-scripts allow-same-origin" src="..."></iframe>

<!-- 服务端响应头阻止被嵌入 -->
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'self'
```

#### 应用场景

1. **嵌入第三方内容**：在线视频、地图（Google Maps）、评论系统（Disqus）、广告
2. **集成第三方服务**：支付页面、OAuth 登录弹窗
3. **文档预览**：在线 Office、PDF 预览
4. **加载页面片段**：只展示外部页面的特定部分
5. **传统微前端**：每个子应用运行在独立 iframe 中，天然 JS/CSS 隔离
6. **安全沙箱**：隔离不可信的外部内容

#### 跨域通信

```js
// 子页面发送
parent.postMessage({ type: 'hello', data: 'world' }, 'https://parent.com')

// 父页面接收
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://child.com') return
  console.log(e.data)
})
```

#### 微前端中的角色

| 方案 | iframe 角色 |
| --- | --- |
| 传统方案 | 子应用完全运行在 iframe 中，隔离性最强 |
| qiankun / Single-SPA | 不再依赖 iframe，改用 JS 沙箱 + CSS 隔离 |
| Module Federation | Webpack 模块共享，无 iframe |

iframe 方案优点：实现简单、天然隔离；缺点：URL 不同步、弹窗/刷新问题、性能差（每个 iframe 独立渲染进程）、SEO 不友好。

### 面试追问

1. **iframe 和 Web Components 做微前端有什么区别？** iframe 是浏览器原生隔离，JS/CSS/DOM 完全独立，但通信靠 postMessage、路由/弹窗体验差、资源重复加载。Web Components（Shadow DOM）在同一文档内实现样式隔离，共享同一 JS 上下文，性能更好，但 JS 隔离需额外沙箱（如 Proxy），隔离性弱于 iframe。

2. **sandbox 属性的常见取值有哪些？** `allow-scripts`（允许脚本）、`allow-same-origin`（允许同源访问，与 scripts 同用才有效）、`allow-forms`（允许表单提交）、`allow-popups`（允许弹窗）、`allow-top-navigation`（允许导航顶层窗口）。不加任何值则最严格：禁止脚本、表单、弹窗、插件等。

## 50.为什么浏览器要限制并发连接数？

**记忆口诀：**「同域六连接，防拥塞保公平；HTTP/1 队头阻塞，多域名和 HTTP/2 来破局」

**核心要点：**
- 浏览器对同一域名限制并发 TCP 连接数（通常 6 个），超出请求排队等待
- 目的：平衡性能与资源消耗，避免客户端/服务端过载
- 突破手段：域名分片、资源合并、HTTP/2 多路复用、CDN 分发

### 详细解答

#### 什么是并发连接数限制

浏览器向服务器发起请求时，对**同一域名**下**同时进行**的 TCP 连接数设上限。Chrome/Firefox/Safari/Edge 默认值通常为 **6**。

```
同域名 10 个资源请求：
  批次1：6 个并发下载
  批次2：剩余 4 个排队，等批次1完成后再下载
  → 增加了等待时间
```

#### 为什么要限制

| 原因 | 说明 |
| --- | --- |
| 防止网络拥塞 | 过多并发连接占用带宽，导致延迟增大 |
| 保护客户端资源 | 端口（65535）、文件描述符、内存、线程均有上限 |
| 保护服务端 | 单 IP 连接过多可能触发 DDoS 防护或被服务端拒绝 |
| HTTP/1.x 队头阻塞 | 同一连接上请求串行响应，多连接也无法完全并行 |
| 公平调度 | 防止单个页面独占连接，影响其他标签页/应用 |
| 连接复用更优 | HTTP/1.1 keep-alive 下，复用连接比频繁三次握手更高效 |

#### 各浏览器默认限制

| 浏览器 | 同域名并发连接数 |
| --- | --- |
| Chrome | 6 |
| Firefox | 6-8 |
| Safari | 6 |
| Edge | 6 |

#### 突破并发限制的方法

| 方法 | 原理 |
| --- | --- |
| 域名分片（Domain Sharding） | static.example.com、img.example.com 各自 6 连接 |
| CDN | 静态资源部署到不同域名/CDN 节点 |
| 资源合并 | 多个小文件合并为一个（雪碧图、CSS/JS 打包） |
| 升级到 HTTP/2 | 单连接多路复用，不再受 6 连接限制 |
| 懒加载 | 非首屏资源延迟加载，减少同时请求数 |
| 内联小资源 | 小图标 base64 内联，减少请求数 |

```html
<!-- 域名分片示例 -->
<link rel="stylesheet" href="https://static1.cdn.com/a.css">
<link rel="stylesheet" href="https://static2.cdn.com/b.css">
```

### 面试追问

1. **HTTP/2 还需要域名分片吗？** 一般**不需要**。HTTP/2 在单个 TCP 连接上通过二进制分帧实现多路复用，多个请求/响应并行传输，不再受 6 连接限制。过多域名反而增加 TLS 握手开销和连接管理成本。但 HTTP/2 仍有 TCP 层队头阻塞问题，HTTP/3（QUIC）才彻底解决。

2. **队头阻塞（Head-of-Line Blocking）是什么？** HTTP/1.x 中，同一 TCP 连接上的响应必须按请求顺序返回，前一个响应慢会阻塞后续响应。即使开 6 个连接，每个连接内部仍有此问题。HTTP/2 在应用层解决了此问题（多 stream 并行），但 TCP 丢包会导致所有 stream 等待（TCP 队头阻塞），HTTP/3 基于 UDP 的 QUIC 协议让每个 stream 独立，丢包只影响单个 stream。

## 51.理解浏览器的多线程架构及渲染流程

**记忆口诀：**「五大进程分工，渲染进程多线程；GUI 与 JS 互斥，Worker 外挂算力」

**核心要点：**
- 现代浏览器多进程：浏览器进程、渲染进程、网络进程、GPU 进程、插件进程
- 渲染进程内多线程：GUI 渲染、JS 引擎、事件触发、定时器、异步 HTTP
- GUI 渲染线程与 JS 引擎线程互斥，JS 执行过长会阻塞页面渲染

### 详细解答

#### 浏览器五大进程

| 进程 | 职责 |
| --- | --- |
| 浏览器进程 | 地址栏、书签、前进后退、子进程管理、文件访问 |
| 渲染进程 | 每个 Tab 一个，负责页面渲染、JS 执行、事件循环 |
| 网络进程 | 网络资源加载（HTML/CSS/JS/图片） |
| GPU 进程 | 3D 绘制、合成层 GPU 加速 |
| 插件进程 | 每个插件独立进程（Flash 等） |

#### 多进程架构优势

- 单个 Tab 崩溃不影响整个浏览器
- 插件崩溃不影响浏览器
- 充分利用多核 CPU
- 沙箱模型隔离，提高安全性和稳定性

代价：内存占用更大（空间换稳定性）。

#### 渲染进程内的线程

| 线程 | 职责 |
| --- | --- |
| GUI 渲染线程 | 解析 HTML/CSS、构建 DOM/CSSOM、Layout、Paint |
| JS 引擎线程 | 执行 JavaScript（V8），单线程 |
| 事件触发线程 | 管理事件循环，将触发的回调放入任务队列 |
| 定时器线程 | setTimeout/setInterval 计时（非 JS 引擎计时） |
| 异步 HTTP 线程 | XMLHttpRequest/Fetch 网络请求 |

#### 关键线程关系

**GUI 渲染线程 ↔ JS 引擎线程：互斥**

```
JS 执行中 → GUI 线程挂起，DOM/CSS 更新被缓存
JS 空闲   → GUI 线程立即执行积压的更新
```

因此 JS 执行时间过长 → 页面渲染阻塞 → 用户感觉卡顿。

**Web Worker：JS 的多线程补充**

```js
const worker = new Worker('heavy-compute.js')
worker.postMessage({ data: largeArray })
worker.onmessage = (e) => console.log(e.data)
```

- Worker 是浏览器开的子线程，完全受主线程控制
- **不能操作 DOM**，通过 postMessage 通信
- 适合 CPU 密集型计算，不影响主线程渲染

| 对比 | Web Worker | SharedWorker |
| --- | --- | --- |
| 归属 | 单个页面 | 所有同源页面共享 |
| 实现 | 渲染进程内的线程 | 独立进程管理 |
| 场景 | 单页面重计算 | 多 Tab 共享状态 |

#### 首次渲染流程

```
1. 解析 HTML → DOM Tree
2. 解析 CSS  → CSSOM
3. 合并       → Render Tree（仅可见节点）
4. Layout     → 计算每个节点几何位置（重排）
5. Layer      → 分层，生成 Layer Tree
6. Paint      → 绘制各层像素（重绘）
7. Composite  → 合成线程合并图层 → 显示到屏幕
```

#### 关键渲染路径（CRP）优化

| 阶段 | 触发条件 | 性能开销 |
| --- | --- | --- |
| Layout（重排） | 改变尺寸/位置/布局属性 | 最高 |
| Paint（重绘） | 改变颜色/阴影等视觉属性 | 中等 |
| Composite（合成） | transform/opacity 变化 | 最低 |

**优化目标：** 动画尽量只触发 Composite，避免 Layout 和 Paint，实现 60fps。

### 面试追问

1. **为什么渲染进程不直接请求网络资源？** 安全沙箱限制。渲染进程执行不可信的网络内容（HTML/JS），若可直接访问网络，漏洞被利用后攻击者能随意发起请求。因此所有网络请求由**浏览器内核（网络进程）**代理，渲染进程通过 IPC 通信，内核还会检查跨域、HTTPS 混合内容等安全策略。

2. **一个 Tab 一定对应一个渲染进程吗？** 不一定。Chrome 的**站点隔离（Site Isolation）**策略下，同一站点（相同 eTLD+1）共享渲染进程，不同站点的 iframe 会分配到不同渲染进程。这是为了防御 Spectre/Meltdown 漏洞——恶意 iframe 无法读取同进程内其他站点数据。

## 52.如何理解 preload 指令

**记忆口诀：**「preload 告诉浏览器马上要用，高优先级预加载进缓存，别滥用防浪费带宽」

**核心要点：**
- `<link rel="preload">` 告知浏览器当前页面即将使用的资源，请优先加载
- 预加载资源放入内存缓存，后续使用时无需等待网络
- 需配合 `as` 属性声明资源类型；未使用的 preload 会浪费带宽

### 详细解答

#### 是什么

`preload` 是一种资源提示（Resource Hint），相当于告诉浏览器：**「这个资源当前页面马上要用，请尽快加载。」**

#### 为什么需要

Web 页面依赖大量外部资源（JS、CSS、字体、图片），使用时才发起请求会导致等待。`preload` 让浏览器**提前**在空闲时加载关键资源，缩短后续使用的等待时间。

#### 怎么用

```html
<link rel="preload"
  href="/fonts/main.woff2"
  as="font"
  type="font/woff2"
  crossorigin>

<link rel="preload"
  href="/js/critical.js"
  as="script">

<link rel="preload"
  href="/css/above-fold.css"
  as="style">
```

**`as` 属性必须正确设置**，否则浏览器可能忽略 preload 或优先级计算错误：

| as 值 | 资源类型 |
| --- | --- |
| script | JavaScript |
| style | CSS |
| font | 字体（需 crossorigin） |
| image | 图片 |
| fetch | fetch()/XHR 请求 |

#### 工作原理

```
1. 浏览器解析 HTML，遇到 <link rel="preload">
2. 以高优先级发起资源请求
3. 资源下载完成后放入内存缓存（不执行/不应用）
4. 后续真正引用该资源时，直接从缓存读取，零网络延迟
```

#### 与其他指令对比

| 指令 | 作用 | 优先级 |
| --- | --- | --- |
| preload | 当前页马上要用 | 高 |
| prefetch | 下一导航可能用到 | 低 |
| preconnect | 提前建立连接（DNS+TCP+TLS） | 中 |
| dns-prefetch | 仅提前 DNS 解析 | 最低 |

#### 注意事项

- preload 的资源**不一定都被用到**，无效预加载浪费带宽，移动端尤其注意
- 字体 preload 必须加 `crossorigin`，否则缓存不可复用
- 不要 preload 过多资源，挤占首屏关键资源带宽

### 面试追问

1. **preload 和 prefetch 有什么区别？** preload 用于**当前页面**即将需要的资源，高优先级立即加载；prefetch 用于**未来导航**可能需要的资源，低优先级在空闲时加载。preload 是「现在就要」，prefetch 是「将来可能要」。

2. **preload 的资源优先级是怎样的？** preload 根据 `as` 属性获得不同优先级：script/style 为 High，font/image 为 Medium。但具体优先级仍低于 CSS（阻塞渲染）和 sync script。preload 不会阻塞 HTML 解析，属于异步加载。

## 53.如何理解 requestAnimationFrame 接口？如何优化渲染性能

**记忆口诀：**「rAF 对齐浏览器帧，一帧一次不紊乱；少 Layout 多 Composite，Worker 分担计算」

**核心要点：**
- requestAnimationFrame 在浏览器下一次重绘前执行回调，与渲染管线对齐
- 一帧内只触发一次，优于 setTimeout 可能一帧多次的问题
- 优化渲染：避免长 JS、减少重排、用 transform 动画、Worker 分担计算

### 详细解答

#### 是什么

`requestAnimationFrame`（rAF）是一个与浏览器**渲染帧**同步的 API，在下次重绘之前执行回调函数。

```js
function animate() {
  element.style.transform = `translateX(${pos}px)`
  pos += 2
  if (pos < 500) {
    requestAnimationFrame(animate)
  }
}
requestAnimationFrame(animate)
```

#### 为什么需要 rAF

| 问题 | setTimeout/setInterval | requestAnimationFrame |
| --- | --- | --- |
| 与帧率同步 | 否，时机不可控 | 是，帧开始前触发 |
| 一帧触发次数 | 可能多次 | 严格一次 |
| 后台 Tab | 仍然运行 | 自动暂停，节省资源 |
| 渲染管线 | 可能扰乱 | 对齐，不干扰 |

浏览器帧率不固定（取决于帧内工作量），setTimeout 无法保证与帧对齐，可能在一帧内触发多次回调，造成不必要的计算和渲染紊乱。

#### rAF vs setTimeout 执行时机

```
一帧的执行顺序：
1. 执行宏任务（含 setTimeout 回调）
2. 清空微任务
3. 执行 requestAnimationFrame 回调  ← 在这里
4. 执行 Layout / Paint / Composite
5. 显示到屏幕
```

#### 应用场景

- **动画**：元素位移、Canvas/WebGL 绘制
- **节流**：滚动事件中替代 setTimeout 节流
- **FPS 计算**：统计帧间隔

```js
// 滚动节流
let ticking = false
window.addEventListener('scroll', () => {
  if (!ticking) {
    requestAnimationFrame(() => {
      updateScrollPosition()
      ticking = false
    })
    ticking = true
  }
})
```

#### 如何优化渲染性能（目标 60fps）

| 策略 | 做法 |
| --- | --- |
| 减少 JS 执行时间 | 长计算放 Web Worker 或分片（requestIdleCallback） |
| 减少重排 | 避免交错读写 DOM，批量修改，用 transform 代替 top/left |
| 减少重绘 | 合并 DOM 操作，使用 DocumentFragment |
| 优先 CSS 动画 | CSS animation/transition 由合成线程处理，优于 JS 动画 |
| 使用 rAF | JS 动画必须用 rAF，不用 setTimeout |
| 优化事件回调 | scroll/resize 等高频事件用 rAF 或 passive 节流 |

### 面试追问

1. **requestAnimationFrame 和 requestIdleCallback 有什么区别？** rAF 在**每帧渲染前**执行，适合动画等视觉更新，优先级高，保证流畅。rIC 在**浏览器空闲时**执行，适合低优先级任务（日志上报、数据预加载），可能被饿死（连续高负载时不执行）。两者互补：rAF 做帧相关，rIC 做非紧急后台任务。

2. **CSS 动画和 rAF 动画哪个性能更好？** CSS 动画（transform/opacity）通常更好：运行在**合成线程**，不阻塞主线程 JS，浏览器可优化插值。rAF 动画在主线程执行，JS 阻塞时动画也会停。但 CSS 动画灵活性低（难以做复杂物理效果），复杂动画仍用 rAF + transform。

## 54.什么是内容安全策略（CSP）

**记忆口诀：**「CSP 白名单防注入，HTTP 头或 meta 配，不符策略的资源一律拦」

**核心要点：**
- CSP（Content Security Policy）通过白名单限制页面可加载/执行的资源来源
- 有效防御 XSS、数据注入等攻击，即使存在注入点也无法执行恶意脚本
- 通过 HTTP 响应头或 meta 标签配置，HTTP 头优先级更高

### 详细解答

#### 是什么

内容安全策略（CSP）是一个额外的**安全层**，通过定义**白名单**告诉浏览器：哪些外部资源可以加载和执行。不符合策略的资源会被浏览器**阻止**。

**核心作用：** 即使攻击者找到注入漏洞，也无法执行恶意脚本，因为 CSP 不允许加载/运行非白名单来源的代码。

#### 配置方式

**方式一：HTTP 响应头（推荐）**

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com
```

**方式二：meta 标签**

```html
<meta http-equiv="Content-Security-Policy"
  content="default-src 'self'; script-src 'self' https://cdn.example.com">
```

HTTP 头与 meta 同时存在时，**HTTP 头优先**。不支持 CSP 的浏览器会忽略，不影响正常使用。

#### 常用指令

| 指令 | 作用 | 示例 |
| --- | --- | --- |
| default-src | 默认策略（其他未指定指令的 fallback） | `'self'` |
| script-src | 允许执行的 JS 来源 | `'self' 'nonce-abc123'` |
| style-src | 允许加载的 CSS 来源 | `'self' 'unsafe-inline'` |
| img-src | 允许加载的图片来源 | `'self' data: https:` |
| connect-src | 允许 XHR/Fetch/WebSocket 连接 | `'self' https://api.example.com` |
| frame-ancestors | 允许嵌入当前页的父页面 | `'none'` |
| report-uri | 违规报告上报地址 | `/csp-report` |

#### 特殊值

| 值 | 含义 |
| --- | --- |
| `'self'` | 同源 |
| `'none'` | 禁止所有 |
| `'unsafe-inline'` | 允许内联脚本/样式（降低安全性） |
| `'unsafe-eval'` | 允许 eval()（降低安全性） |
| `'nonce-xxx'` | 仅允许带匹配 nonce 的内联脚本 |
| `https:` | 允许所有 HTTPS 来源 |

#### 防御 XSS 示例

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-rAnd0m123';
  object-src 'none';
  base-uri 'self';
```

```html
<!-- 只有带正确 nonce 的内联脚本才能执行 -->
<script nonce="rAnd0m123">console.log('allowed')</script>
<script>alert('blocked by CSP')</script>
```

### 面试追问

1. **CSP 的 nonce 和 hash 机制是什么？** 默认 CSP 禁止内联脚本。nonce 是服务端每次请求生成的随机字符串，内联 script 标签需带 `nonce="xxx"` 属性才能执行。hash 是内联脚本内容的 SHA 哈希值，CSP 配置 `script-src 'sha256-abc...'`，只有内容匹配的脚本才能执行。两者都允许安全的内联脚本，无需 `'unsafe-inline'`。

2. **CSP 和 CORS 有什么区别？** CSP 是**内容安全策略**，限制页面能加载哪些资源（防 XSS 注入），由页面自身配置，保护的是**当前页面的用户**。CORS 是**跨域资源共享**，控制其他域能否访问本域资源，由服务端响应头配置，保护的是**服务端资源**。两者互补，解决不同安全问题。

## 55.浏览器的安全沙箱策略

**记忆口诀：**「渲染进程沙箱隔离，网络存储交互全走内核 IPC；站点隔离防 Spectre」

**核心要点：**
- 安全沙箱利用 OS 安全技术，限制渲染进程直接访问系统资源
- 渲染进程不能直接读写文件、发起网络请求、操作窗口，需通过浏览器内核 IPC 代理
- 站点隔离（Site Isolation）将不同站点分配到不同渲染进程，防御 Spectre 攻击

### 详细解答

#### 为什么需要安全沙箱

单进程浏览器中，若存在漏洞，恶意网页可通过浏览器进程**读取/修改操作系统任意内容**——安装恶意软件、监听键盘、读取硬盘文件。危害远超 XSS（XSS 只能窃取 Cookie 等页面数据）。

现代浏览器采用**多进程 + 安全沙箱**：即使渲染进程被攻击，沙箱阻止其访问沙箱外的任何资源。

#### 安全沙箱是什么

在渲染进程和操作系统之间建一道**隔离墙**。渲染进程执行 DOM 解析、JS 运行、图片解码等操作时，无法直接访问或修改 OS 数据。需要系统资源时，通过 **IPC** 请求浏览器内核代理。

```
渲染进程（沙箱内）  ←IPC→  浏览器内核（沙箱外）  ←→  操作系统
  不可信的网络内容              可信的、有权限
```

#### 沙箱如何影响各模块

| 功能 | 沙箱前（渲染进程直接操作） | 沙箱后（内核代理） |
| --- | --- | --- |
| 持久存储 | 直接读写 Cookie/缓存 | 渲染进程 IPC 请求 → 内核读写 → 返回结果 |
| 网络访问 | 直接发起 HTTP 请求 | 内核检查权限（跨域、HTTPS）后代理请求 |
| 用户交互 | 直接接收键盘/鼠标事件 | OS → 内核接收 → IPC 转发给渲染进程 |
| 屏幕显示 | 直接绘制到窗口 | 渲染进程生成位图 → IPC 提交 → 内核复制到屏幕 |

#### 为什么流程这么复杂

**Q：为什么渲染进程不直接请求网络？**
A：网络内容不可信，若渲染进程有直接网络权限，漏洞被利用后可随意发起攻击。

**Q：为什么渲染进程不直接显示到屏幕？**
A：限制渲染进程监控用户输入的能力，所有输入事件由内核接收和分发。

#### 站点隔离（Site Isolation）

Chrome 将**同一站点**（相同 eTLD+1 + 协议）的页面放在同一渲染进程。不同站点的 iframe 分配到**不同渲染进程**。

```
旧方案：一个 Tab = 一个渲染进程（含跨域 iframe）
        → 恶意 iframe 可读取同进程内银行页面数据

新方案：不同站点 = 不同渲染进程
        → 恶意 iframe 被隔离，无法访问其他进程
```

这是为了防御 **Spectre/Meltdown** 等 CPU 级漏洞——攻击者可读取同一进程内的内存。

### 面试追问

1. **安全沙箱和 JS 沙箱（如 Proxy 沙箱）有什么区别？** 浏览器安全沙箱是**操作系统级**的进程隔离，由 OS 内核 enforce，渲染进程完全无法绕过。JS 沙箱（如 qiankun 的 Proxy 沙箱）是**应用级**的，通过 Proxy 拦截 window 访问，仅在 JS 层面隔离，无法防御 CPU 级攻击（Spectre）或原生漏洞，安全性远低于 OS 沙箱。

2. **Chrome 为什么要把不同站点放到不同渲染进程？** 最初按 Tab 划分进程，但 Tab 内跨域 iframe 共享进程。Spectre 漏洞允许恶意代码读取同进程内任意内存，若银行页面和恶意 iframe 同进程，用户数据就泄露了。站点隔离确保不同源内容物理隔离在不同进程中，即使被 Spectre 攻击也无法跨进程读取。

## 56.如何理解 WebSocket？

**记忆口诀：**「HTTP 握手 101 升级，全双工长连接，心跳保活 wss 加密」

**核心要点：**
- WebSocket 是 HTML5 全双工通信协议，建立连接后双方可主动发消息
- 通过 HTTP Upgrade 握手（101 Switching Protocols），之后走独立 TCP 通道
- 相比 HTTP 轮询：开销小、实时性高、长连接复用

### 详细解答

WebSocket 是 HTML5 引入的**全双工通信协议**，连接建立后服务端和客户端都可以**主动**向对方发送消息。

#### 与 HTTP 轮询对比

| 特性 | HTTP 轮询 | WebSocket |
| --- | --- | --- |
| 通信方式 | 客户端定时请求 | 全双工，双方都可主动发 |
| 协议开销 | 每次完整 HTTP 头 | 连接建立后帧头极小（2-14 字节） |
| 实时性 | 取决于轮询间隔 | 即时推送 |
| 连接 | 短连接，频繁建立/断开 | 长连接，一次握手持续通信 |
| 服务器推送 | 不支持（需轮询模拟） | 原生支持 |

#### 握手过程

WebSocket 复用 HTTP 完成初始握手，然后**协议升级**：

```http
// 客户端请求
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

// 服务端响应
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

`Sec-WebSocket-Accept` 由客户端 Key + 固定 GUID 经 SHA-1 + Base64 生成，防止非 WebSocket 服务器误接受升级。

#### 核心特性

| 特性 | 说明 |
| --- | --- |
| 数据分帧 | 消息拆分为多个 Frame，FIN 标志标识最后一帧 |
| 心跳机制 | ping/pong 帧检测连接存活，防止被中间设备断开 |
| 支持跨域 | 不受同源策略限制（握手阶段仍遵循） |
| 子协议 | Sec-WebSocket-Protocol 协商应用层协议 |
| 二进制支持 | 可传输文本和二进制数据 |

#### 基本使用

```js
const ws = new WebSocket('wss://example.com/chat')

ws.onopen = () => ws.send('Hello Server')
ws.onmessage = (e) => console.log('收到:', e.data)
ws.onclose = () => console.log('连接关闭')
ws.onerror = (e) => console.error('错误:', e)
```

#### 应用场景

- 即时通讯（IM、在线客服）
- 实时协同编辑
- Web 游戏
- 股票/体育赛事实时推送
- webpack-dev-server 热更新

#### 最佳实践

- 使用 **wss://**（TLS 加密），生产环境禁止 ws://
- 实现**断线重连**（指数退避）
- 使用 **心跳** 检测连接状态
- 成熟库如 **socket.io**（支持降级到长轮询）

### 面试追问

1. **WebSocket 和 SSE（Server-Sent Events）有什么区别？** WebSocket 是**全双工**，双方都可发消息，基于独立协议。SSE 是**单向**（服务端 → 客户端），基于 HTTP，自动重连，文本 only。SSE 更简单、兼容 HTTP 基础设施（代理/负载均衡），适合单向推送（通知、日志流）；WebSocket 适合双向实时通信（聊天、游戏）。

2. **WebSocket 连接如何保持存活？** ① 协议层 **ping/pong 帧**心跳，服务端发 ping，客户端回 pong；② 应用层定时发送心跳消息；③ TCP keep-alive。中间代理/防火墙可能在空闲时断开连接（通常 60-120s），因此心跳间隔应小于超时时间。断连后需实现自动重连机制。

## 57.为什么浏览器会出现白屏？如何检测与预防？

**记忆口诀：**「资源 404、JS 报错、死循环、组件崩溃，四类白屏要兜底检测」

**核心要点：**
- 白屏 = 页面因异常无法正常渲染，用户看到空白页面
- 常见原因：关键资源 404、JS 未捕获异常、死循环、框架组件 crash
- 检测：采样检测、DOM 打分、SW 心跳；预防：ErrorBoundary + 全局异常兜底

### 详细解答

#### 白屏类型

| 类型 | 说明 |
| --- | --- |
| 纯白屏 | 从加载到结束一直白屏，无任何响应 |
| Loading 白屏 | 出现 Loading 动画但内容始终不出来 |
| 局部白屏 | 页面部分区域因异常导致元素缺失 |

#### 常见原因

| 原因 | 示例 |
| --- | --- |
| 关键资源 404 | HTML/JS 文件缺失，SPA 路由资源加载失败 |
| JS 未捕获异常 | `undefined.xxx`、`JSON.parse('invalid')` |
| 死循环 | while(true) 阻塞主线程 |
| 框架组件 crash | React 组件错误未被 ErrorBoundary 捕获 |
| CSS 问题 | 关键样式未加载，内容存在但不可见 |
| 跨域脚本错误 | 未配置 crossorigin，错误被浏览器吞掉 |

#### 检测方案

**1. 采样检测（纯白屏）**

```js
function isWhiteScreen() {
  const points = [
    [0.5, 0.5], [0.25, 0.25], [0.75, 0.75]
  ]
  return points.every(([x, y]) => {
    const el = document.elementFromPoint(
      window.innerWidth * x,
      window.innerHeight * y
    )
    return el === document.body || el === document.documentElement
  })
}
```

**2. DOM 打分（白屏 + 骨架屏 + 局部白屏）**

```js
function getDomScore() {
  let score = 0
  const walker = document.createTreeWalker(
    document.body, NodeFilter.SHOW_ELEMENT
  )
  while (walker.nextNode()) {
    const el = walker.currentNode
    if (el.offsetWidth > 0 && el.offsetHeight > 0) {
      score += 1 / getDepth(el)
    }
  }
  return score
}
// score 低于阈值 → 判定白屏
```

**3. Service Worker 心跳（页面 crash）**

```js
// 页面定期发送心跳
setInterval(() => {
  navigator.serviceWorker.controller?.postMessage('heartbeat')
}, 1000)

// SW 中检测超时
let lastBeat = Date.now()
self.addEventListener('message', () => { lastBeat = Date.now() })
setInterval(() => {
  if (Date.now() - lastBeat > 5000) {
    reportCrash() // 页面崩溃
  }
}, 3000)
```

#### 预防措施

```js
// 1. 全局异常兜底
window.onerror = (msg, url, line, col, error) => {
  reportError({ msg, url, line, col, stack: error?.stack })
}
window.addEventListener('unhandledrejection', (e) => {
  reportError({ msg: e.reason })
})
window.addEventListener('error', (e) => {
  if (e.target !== window) reportError({ msg: '资源加载失败', src: e.target.src })
}, true)

// 2. React ErrorBoundary
class ErrorBoundary extends React.Component {
  state = { hasError: false }
  static getDerivedStateFromError() { return { hasError: true } }
  componentDidCatch(error, info) { reportError({ error, info }) }
  render() {
    return this.state.hasError ? <FallbackUI /> : this.props.children
  }
}

// 3. 跨域脚本错误可见
<script crossorigin="anonymous" src="https://cdn.com/app.js"></script>
// 服务端需返回 Access-Control-Allow-Origin
```

### 面试追问

1. **FP（First Paint）和 FCP（First Contentful Paint）与白屏有什么关系？** FP 是首次绘制任何像素的时间，FCP 是首次绘制**内容**（文字/图片）的时间。白屏持续时间 ≈ FCP 时间点。FCP 越晚，白屏越久。优化 FCP（减少阻塞资源、SSR、骨架屏）直接减少白屏感知。若 FCP 正常但用户仍看到白屏，可能是 CSS 隐藏内容或 JS 后续 crash。

2. **骨架屏能防止白屏吗？** 骨架屏不能**防止**白屏（JS 报错该白还是白），但能**缓解白屏感知**。在内容加载前展示页面结构轮廓，让用户感知到「页面正在加载」而非「页面坏了」。配合 SSR/SSG 效果更好——HTML 直出骨架屏，FCP 极快，JS 加载后再 hydrate。

## 58.HTTP 从 1.0 到 3.0 的演化之路

**记忆口诀：**「1.0 短连接 → 1.1 长连接 → 2.0 多路复用 → 3.0 QUIC/UDP」

**核心要点：**
- HTTP/1.0 每次请求新建 TCP；1.1 引入 keep-alive 长连接和管道化
- HTTP/2 二进制分帧 + 多路复用 + HPACK 头压缩，解决队头阻塞
- HTTP/3 基于 QUIC（UDP），0-RTT 建连、无 TCP 队头阻塞、连接迁移

### 详细解答

| 版本 | 核心改进 | 解决的问题 |
| --- | --- | --- |
| HTTP/1.0 | 状态码、Header、Content-Type | 只能传 HTML → 支持多种内容类型 |
| HTTP/1.1 | keep-alive 长连接、管道化、分块传输、Host 头 | 每次新建 TCP → 连接复用 |
| HTTPS | TLS 加密（非对称交换密钥 + 对称传输） | 明文传输 → 加密 + 身份验证 |
| HTTP/2 | 二进制分帧、多路复用、HPACK 压缩、Server Push | 队头阻塞、头部冗余、无法推送 |
| HTTP/3 | QUIC（UDP）、0-RTT、连接迁移 | TCP 队头阻塞、握手延迟、切换网络断连 |

#### HTTP/1.0 → 1.1

```
HTTP/1.0：请求 → 响应 → 关闭 TCP（短连接，每次三次握手）
HTTP/1.1：请求 → 响应 → 请求 → 响应 → ... → 关闭（keep-alive 长连接）
         + 管道化（pipelining，但仍有队头阻塞）
         + 分块传输（Transfer-Encoding: chunked）
         + Host 头（一台服务器多个虚拟主机）
```

#### HTTP/2 关键特性

**二进制分帧：** 将数据拆分为 Frame，Frame 属于 Stream，多个 Stream 复用一个 TCP 连接。

```
TCP 连接
├── Stream 1: GET /a.html  → Response A
├── Stream 3: GET /b.css   → Response B    ← 并行传输
└── Stream 5: GET /c.js    → Response C
```

- **多路复用**：一个连接并发多个请求/响应，无需域名分片
- **HPACK 头压缩**：静态表 + 动态表 + 霍夫曼编码，Header 体积大幅减小
- **Server Push**：服务端主动推送客户端将要请求的资源
- **流优先级**：Stream 可设权重，重要资源优先传输

#### HTTP/3（QUIC）关键改进

| 特性 | 说明 |
| --- | --- |
| 基于 UDP | 绕过 TCP 队头阻塞，丢包只影响单个 Stream |
| 0-RTT 建连 | 首次 1-RTT，后续 0-RTT 直接发数据 |
| 连接迁移 | Connection ID 标识连接，WiFi ↔ 4G 切换不断连 |
| 内置 TLS 1.3 | 加密是协议标配，非可选层 |

#### 演进痛点对照

```
HTTP/1.0  痛点：短连接，每次三次握手
    ↓
HTTP/1.1  解决：keep-alive；遗留：队头阻塞、Header 冗余
    ↓
HTTP/2    解决：多路复用、HPACK；遗留：TCP 层队头阻塞
    ↓
HTTP/3    解决：QUIC/UDP，彻底消除队头阻塞
```

### 面试追问

1. **HTTP/2 的多路复用是如何实现的？** HTTP/2 将 HTTP 消息拆分为二进制 Frame，每个 Frame 属于一个 Stream（流，对应一个请求/响应）。多个 Stream 的 Frame 交错在同一个 TCP 连接上传输，接收端按 Stream ID 重组。这样消除了 HTTP/1.x 的应用层队头阻塞，一个连接即可并行传输所有资源。

2. **为什么 HTTP/3 选择 UDP 而不是改进 TCP？** TCP 的队头阻塞是协议设计决定的——丢包时所有 Stream 都必须等待重传，无法通过升级 TCP 解决（TCP 在内核中实现，更新极慢）。QUIC 在用户空间实现可靠传输，每个 Stream 独立，丢包只阻塞该 Stream。此外 QUIC 将 TLS 1.3 集成到协议中，减少握手 RTT，Connection ID 支持连接迁移。

## 59.如何实现浏览器指纹（设备指纹）？

**记忆口诀：**「基本特征 + Canvas 渲染差 + 音频处理差，组合哈希几乎唯一」

**核心要点：**
- 浏览器指纹通过收集浏览器/设备特征信息来标识用户，无需 Cookie 也能追踪
- 三类指纹：基本指纹（UA/分辨率等）、Canvas 指纹、音频指纹
- 组合多种指纹可极高精度识别设备；防范：Tor 浏览器、禁用 JS、反指纹插件

### 详细解答

浏览器指纹（Device Fingerprinting）是通过收集浏览器和设备特征信息，生成**几乎唯一**的标识符，即使用户清除 Cookie 或使用无痕模式也能识别。

#### 三类指纹

| 类型 | 原理 | 采集信息 |
| --- | --- | --- |
| 基本指纹 | 浏览器/系统环境特征 | UA、屏幕分辨率、语言、时区、插件列表、CPU 核心数 |
| Canvas 指纹 | 不同系统/显卡/GPU 渲染 Canvas 结果存在微小差异 | 绘制文本/图形 → toDataURL() → Hash |
| 音频指纹 | 不同硬件/软件处理音频信号的差异 | OfflineAudioContext 生成音频 → 压缩 → Hash |

#### Canvas 指纹实现

```js
function getCanvasFingerprint() {
  const canvas = document.createElement('canvas')
  const ctx = canvas.getContext('2d')
  canvas.width = 200
  canvas.height = 50

  ctx.textBaseline = 'top'
  ctx.font = "14px 'Arial'"
  ctx.fillStyle = '#f60'
  ctx.fillRect(125, 1, 62, 20)
  ctx.fillStyle = '#069'
  ctx.fillText('BrowserFingerprint', 2, 15)
  ctx.fillStyle = 'rgba(102, 204, 0, 0.7)'
  ctx.fillText('BrowserFingerprint', 4, 17)

  return sha256(canvas.toDataURL())
}
```

不同 OS、浏览器、显卡驱动渲染出的像素存在细微差异，Hash 后形成唯一标识。

#### 组合指纹

单项指纹信息熵有限（如屏幕分辨率常见值有限），但组合后信息熵极高：

```js
const fingerprint = sha256(JSON.stringify({
  ua: navigator.userAgent,
  language: navigator.language,
  screen: `${screen.width}x${screen.height}x${screen.colorDepth}`,
  timezone: Intl.DateTimeFormat().resolvedOptions().timeZone,
  canvas: getCanvasFingerprint(),
  audio: getAudioFingerprint(),
  plugins: getPluginsList(),
  webgl: getWebGLFingerprint()
}))
```

#### 应用场景

| 场景 | 用途 |
| --- | --- |
| 精准广告 | 跨站点追踪用户兴趣 |
| 反黑产 | 识别同设备多账号（水军/刷单） |
| 风控系统 | 设备信誉评分，异常设备拦截 |
| 免登录识别 | 设备绑定，无需密码验证 |

#### 防范手段

- 使用 **Tor Browser**（统一指纹，所有人看起来一样）
- 浏览器插件：**Canvas Blocker**、**Chameleon** 等
- 设置 `DNT: 1`（Do Not Track，但多数网站不遵守）
- Firefox 的 **resistFingerprinting** 配置
- 禁用 JavaScript（极端方案，影响功能）

### 面试追问

1. **Canvas 指纹为什么在不同设备上不同？** Canvas 渲染依赖操作系统字体渲染引擎、GPU 驱动、抗锯齿算法、色彩配置等。不同 OS（Windows/macOS/Linux）、不同浏览器（Chrome/Firefox/Safari）、不同显卡驱动的渲染结果存在像素级差异。这些差异人眼不可见，但 toDataURL() 提取的像素数据 Hash 后不同。

2. **浏览器指纹的法律和隐私问题？** 指纹追踪无需用户同意即可跨站点追踪，违反 GDPR 等隐私法规。2023 年后 Chrome 计划限制 Canvas/Audio 指纹（Privacy Sandbox），Safari/Firefox 已部分限制。前端开发者应在隐私政策中声明，风控场景需平衡安全与用户隐私。

## 60.矢量图与位图及常见图片格式选型

**记忆口诀：**「矢量数学描述不失真，位图像素存储；照片 AVIF/WebP，图标 SVG，动画 WebP 替 GIF」

**核心要点：**
- 矢量图用数学公式描述图形，任意缩放不失真；位图逐像素存储，放大锯齿
- 常见格式各有优劣：JPEG 照片、PNG 透明、WebP 全能替代、AVIF 压缩最优
- 选型原则：图标 Logo 用 SVG，照片用 AVIF/WebP，简单动画用 WebP

### 详细解答

#### 矢量图 vs 位图

| 对比 | 矢量图（Vector） | 位图/光栅图（Raster） |
| --- | --- | --- |
| 原理 | 数学公式描述线、点、多边形 | 逐像素存储颜色值 |
| 缩放 | 任意缩放不失真 | 放大产生锯齿/模糊 |
| 文件大小 | 简单图形极小 | 与分辨率正相关 |
| 适用 | 图标、Logo、几何图形、UI | 照片、复杂场景、渐变 |
| 常见格式 | SVG、PDF、AI | JPEG、PNG、GIF、WebP、AVIF |

#### 常见图片格式对比

| 格式 | 透明 | 动画 | 压缩方式 | 颜色 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| GIF | ✅ | ✅ | 无损（256色） | 256色 | 简单动画、表情包（已被 WebP 替代） |
| PNG-8 | ✅ | ❌ | 无损 | 256色 | 简单图标、小图形 |
| PNG-24 | ✅ | ❌ | 无损 | 真彩色 | 需透明的高质量图 |
| JPEG | ❌ | ❌ | 有损 | 真彩色 | 照片、色彩丰富的图 |
| WebP | ✅ | ✅ | 有损+无损 | 真彩色 | JPEG/PNG/GIF 的全能替代 |
| AVIF | ✅ | ✅ | 有损+无损 | 真彩色 | 有损压缩最优，照片/广告 |
| JPEG XL | ✅ | ✅ | 有损+无损 | 真彩色 | 无损压缩最优 |
| SVG | ✅ | ✅(SMIL/CSS) | 文本描述 | 矢量 | 图标、Logo、简单插画 |

#### 格式选型建议

```
图标 / Logo / 简单插画  →  SVG（矢量，体积小，可 CSS 控制）
照片 / 广告 Banner       →  AVIF（有损最优）> WebP > JPEG
需要透明背景的 UI 元素   →  WebP（无损）> PNG-24
简单动画                 →  WebP 动画 > GIF
高质量存档               →  JPEG XL（无损最优）> PNG
兼容性优先（老浏览器）   →  JPEG + PNG 兜底，picture 元素渐进增强
```

#### 渐进增强用法

```html
<picture>
  <source srcset="photo.avif" type="image/avif">
  <source srcset="photo.webp" type="image/webp">
  <img src="photo.jpg" alt="描述">
</picture>
```

#### 压缩工具

- **有损压缩**：TinyPNG、Squoosh、ImageOptim
- **无损压缩**：pngquant、optipng
- **格式转换**：cwebp、avifenc、sharp（Node.js）

### 面试追问

1. **WebP 和 AVIF 有什么区别，该选哪个？** AVIF 基于 AV1 视频编码，相同质量下体积比 WebP 小 20-30%，是目前有损压缩最优格式。WebP 兼容性更好（95%+ vs AVIF 90%+），编解码速度更快。建议：追求极致压缩用 AVIF + WebP 兜底；兼容性优先直接用 WebP；两者都用 `<picture>` 渐进增强。

2. **SVG 内联和外链 img 引用有什么区别？** 内联 SVG（直接写在 HTML 中）可以用 CSS/JS 控制内部元素（改颜色、做动画），但增加 HTML 体积，无法缓存。外链 `<img src="icon.svg">` 可缓存、可 CDN，但无法用 CSS 修改内部样式（除非用 filter）。CSS background-image 类似 img，适合装饰性图标。

## 61.CDN 与资源交付优化

**记忆口诀：**「CDN 边缘节点就近交付，缓存命中零回源；静态资源上 CDN，版本号控缓存更新」

**核心要点：**
- CDN 通过全球分布式边缘节点，让用户从最近的服务器获取资源
- 核心流程：DNS 调度 → 边缘节点缓存命中直接返回 / 未命中回源
- 配合 preconnect、资源 hash、HTTP/2 等进一步优化交付

### 详细解答

#### CDN 是什么

CDN（Content Delivery Network，内容分发网络）在全球部署**分布式代理服务器（边缘节点）**，将源站资源缓存到离用户最近的节点，实现**就近访问**。

#### 工作原理

```
1. 用户请求 https://cdn.example.com/app.js
2. DNS 解析 → CDN 智能调度（根据地理位置、负载、网络质量）
3. 分配到最近的边缘节点
4. 边缘节点有缓存 → 直接返回（缓存命中，HIT）
5. 边缘节点无缓存 → 回源到源站获取 → 缓存到边缘节点 → 返回（MISS）
```

#### 关键术语

| 术语 | 说明 |
| --- | --- |
| 源站（Origin） | 原始资源所在的服务器 |
| 边缘节点（Edge Node） | 离用户最近的 CDN 服务器 |
| 回源（Origin Pull） | 边缘节点缓存未命中，向源站请求 |
| 缓存命中（Cache Hit） | 边缘节点直接返回缓存资源 |
| 缓存穿透 | 请求资源不在缓存中，每次都回源 |

#### CDN 的性能优势

| 优势 | 说明 |
| --- | --- |
| 物理距离更短 | 用户 → 边缘节点 RTT 远小于 → 源站 |
| 网络优化 | CDN 服务商优化骨干网链路 |
| 缓存命中 | 无需回源，响应极快 |
| 减轻源站压力 | 静态资源由 CDN 承担，源站专注动态请求 |
| 抗 DDoS | 分布式节点分散攻击流量 |
| 突破并发限制 | 不同 CDN 域名各自享有 6 连接（HTTP/1.1 时代） |

#### 资源交付优化最佳实践

```html
<!-- 1. 静态资源部署到 CDN -->
<script src="https://cdn.example.com/js/app.a1b2c3.js"></script>
<link rel="stylesheet" href="https://cdn.example.com/css/main.d4e5f6.css">

<!-- 2. 预连接 CDN 域名 -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin>
<link rel="dns-prefetch" href="https://cdn.example.com">

<!-- 3. 文件名带 hash，永久缓存 -->
<!-- app.a1b2c3.js → Cache-Control: max-age=31536000, immutable -->

<!-- 4. HTML 不缓存或短缓存 -->
<!-- index.html → Cache-Control: no-cache -->
```

#### 缓存策略

| 资源类型 | 缓存策略 | 原因 |
| --- | --- | --- |
| 带 hash 的 JS/CSS | `max-age=31536000, immutable` | 内容变则 hash 变，永久缓存 |
| 图片/字体 | `max-age=2592000`（30天） | 较长缓存 |
| HTML | `no-cache` 或 `max-age=0` | 确保获取最新版本 |
| API 响应 | `no-store` 或短时间缓存 | 动态数据 |

#### CDN 选型考量

- 节点覆盖范围（目标用户所在区域）
- 缓存命中率（回源率越低越好）
- HTTPS 支持、HTTP/2/3 支持
- 价格（流量计费 vs 带宽计费）
- 安全防护（WAF、DDoS 防护）

### 面试追问

1. **CDN 缓存更新策略是怎样的？** 常用**文件名 hash** 策略：构建工具生成 `app.[hash].js`，内容变则 hash 变，新 URL 自然 miss 旧缓存。HTML 不缓存（`no-cache`），每次请求最新 HTML，其中引用最新 hash 资源。也可通过 CDN 控制台手动刷新/预热缓存。避免用 query string 做版本（`app.js?v=2`），部分 CDN 忽略 query 导致缓存不更新。

2. **CDN 节点如何选择最近的？** CDN DNS 调度基于 **GSLB（全局负载均衡）**：① 用户 DNS 请求到 CDN 的 DNS 服务器；② 根据用户 IP 地理位置、各节点负载、网络延迟（Anycast/BGP）、节点健康状态；③ 返回最优边缘节点 IP。高级 CDN 还会做**实时探测**（RTT 测量）和**智能路由**（选择最优骨干网路径），不只是地理距离最近。
