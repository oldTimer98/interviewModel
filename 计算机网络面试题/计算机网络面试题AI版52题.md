## 1. GET 和 POST 的请求的区别

**记忆口诀：**「GET 幂等查资源，POST 非幂等改数据；GET 可缓存参数露 URL，POST 体大类型多」

**一句话总结：** GET 是幂等的资源获取请求，参数在 URL 中、可缓存；POST 是非幂等的资源修改/提交请求，数据在请求体中、一般不缓存。

### 详细解答

GET 和 POST 是 HTTP 中最常用的两种请求方法，语义和使用场景不同。面试中需要区分「规范语义」和「浏览器/服务器实际行为」。

| 对比维度 | GET | POST |
| --- | --- | --- |
| 应用场景 | 幂等，获取资源，不改变服务器状态 | 非幂等，提交/创建/修改资源 |
| 是否缓存 | 浏览器通常可缓存 | 一般不缓存 |
| 报文格式 | 请求体为空，参数在 URL Query | 数据放在请求体（Body）中 |
| 安全性 | 参数暴露在 URL，会进入历史记录 | 相对更安全（但 HTTPS 才是关键） |
| 请求长度 | 受浏览器 URL 长度限制（非 RFC 规定） | 理论上无 URL 长度限制 |
| 参数类型 | 主要是字符串 | 支持 JSON、文件、XML 等多种类型 |

**1. 应用场景与幂等性**

- **GET**：幂等请求，多次执行结果相同，适合查询、获取页面资源等不改变服务器状态的操作。
- **POST**：非幂等请求，多次执行可能产生不同结果，适合注册、提交表单、创建资源等会改变服务器状态的操作。

**2. 缓存行为**

浏览器会根据 GET 的 URL 做缓存（配合 Cache-Control、ETag 等），POST 因可能改变服务器状态，通常不会被缓存。

**3. 报文结构**

```http
GET /api/users?page=1 HTTP/1.1
Host: example.com

```

```http
POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json

{"name": "张三", "age": 25}
```

**4. 安全性说明**

GET 参数出现在 URL 中，会被浏览器历史、服务器日志、Referer 等记录，不适合传密码等敏感信息。但 POST 默认也是明文（HTTP 下），真正安全需依赖 HTTPS。

**5. 常见误区**

- RFC 并未严格禁止 GET 带 Body，但实际中几乎不用。
- POST 也可以做查询，但不符合 RESTful 语义，且不利于缓存。

### 面试追问

1. **GET 和 POST 在 TCP 层面有区别吗？** 没有本质区别，都是 HTTP 应用层语义；底层 TCP 连接方式相同，区别在报文结构和语义。
2. **为什么说 GET 比 POST 更不安全？** GET 参数暴露在 URL 中，容易被日志、历史记录、Referer 泄露；POST 数据在 Body 中相对隐蔽，但 HTTP 明文下两者都不加密。

## 2. POST 和 PUT 请求的区别

**记忆口诀：**「POST 创建非幂等，PUT 更新全量幂等；多次 POST 多条记录，多次 PUT 结果相同」

**一句话总结：** POST 用于创建新资源（非幂等），PUT 用于更新/替换已有资源（幂等）。

### 详细解答

POST 和 PUT 都可以向服务器发送数据，但语义和幂等性不同，是 RESTful API 设计中的核心区分。

| 对比维度 | POST | PUT |
| --- | --- | --- |
| 语义 | 创建新资源 | 更新/替换已有资源 |
| 幂等性 | 非幂等，多次请求可能创建多条记录 | 幂等，多次相同请求结果一致 |
| 目标 URL | 通常指向集合，如 `/users` | 通常指向具体资源，如 `/users/1` |
| 典型场景 | 提交表单、创建订单 | 全量更新用户信息 |

**POST — 创建数据**

向服务器提交数据，会改变资源种类或数量，每次请求可能产生新的资源。

```http
POST /api/users HTTP/1.1
Content-Type: application/json

{"name": "李四"}
```

每次调用可能创建一个新用户，属于非幂等操作。

**PUT — 更新数据**

向指定资源位置发送数据，用于修改已有资源内容，不会增加资源种类。无论执行多少次，最终结果相同。

```http
PUT /api/users/1 HTTP/1.1
Content-Type: application/json

{"name": "王五", "age": 30}
```

多次 PUT 同一 URL 和相同数据，用户 1 的状态始终一致，属于幂等操作。

**补充：PATCH**

PATCH 用于部分更新，也是非幂等（取决于实现），与 PUT 的全量替换形成对比。

### 面试追问

1. **PUT 和 PATCH 有什么区别？** PUT 是全量替换资源，PATCH 是部分更新；PUT 幂等，PATCH 通常非幂等。
2. **为什么 POST 不是幂等的？** 因为每次 POST 可能在服务器创建新资源（如重复提交订单），多次执行结果不同。

## 3. 常见的 HTTP 请求头和响应头

**记忆口诀：**「请求 Accept Host Cookie UA，响应 Date Server Cache Content-Type」

**一句话总结：** 请求头描述客户端能力与偏好，响应头描述服务器信息与资源属性；Content-Type 决定请求/响应体的数据格式。

### 详细解答

**常见请求头（Request Header）**

| 请求头 | 作用 |
| --- | --- |
| Accept | 客户端能处理的响应内容类型（MIME） |
| Accept-Charset | 客户端能显示的字符集 |
| Accept-Encoding | 客户端支持的压缩编码（gzip、br 等） |
| Accept-Language | 客户端偏好语言 |
| Connection | 连接管理方式（keep-alive / close） |
| Cookie | 当前页面设置的 Cookie |
| Host | 请求目标主机名（HTTP/1.1 必需） |
| Referer | 发起请求的页面 URL |
| User-Agent | 浏览器/客户端标识字符串 |

**常见响应头（Response Header）**

| 响应头 | 作用 |
| --- | --- |
| Date | 消息发送时间（RFC 822 格式） |
| Server | 服务器软件信息 |
| Connection | 连接管理方式 |
| Cache-Control | 缓存控制策略 |
| Content-Type | 响应体的 MIME 类型 |

**Content-Type 四种常见值**

| Content-Type | 说明 | 典型场景 |
| --- | --- | --- |
| application/x-www-form-urlencoded | key=val 形式，URL 编码 | 原生 form 表单默认提交方式 |
| multipart/form-data | 多部分表单，带 boundary | 文件上传 |
| application/json | JSON 字符串 | 前后端 API 交互 |
| text/xml | XML 格式数据 | SOAP、旧式 Web 服务 |

**代码示例**

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded
Accept: application/json
User-Agent: Mozilla/5.0

username=admin&password=123456
```

```http
HTTP/1.1 200 OK
Date: Mon, 15 Jun 2026 08:00:00 GMT
Server: nginx/1.24.0
Content-Type: application/json; charset=utf-8
Cache-Control: no-cache

{"token": "abc123"}
```

服务器向客户端发送的数据格式常见有 XML、HTML、JSON，其中 JSON 是目前 Web API 的主流格式。

### 面试追问

1. **Accept 和 Content-Type 有什么区别？** Accept 是客户端告诉服务器「我能接受什么格式的响应」；Content-Type 是告诉对方「我发送/返回的数据是什么格式」。
2. **form 上传文件为什么要用 multipart/form-data？** 因为需要在同一个请求体中传输文本字段和二进制文件，multipart 用 boundary 分隔各部分，适合混合数据。

## 4. HTTP 状态码 304 是多好还是少好

**记忆口诀：**「304 非错误是缓存命中，适量最好；太多页面不更新，太少缓存没生效」

**一句话总结：** 304 表示资源未修改、客户端可使用缓存，不是错误；适量说明缓存有效，过多说明内容更新少，过少说明缓存策略未生效。

### 详细解答

**304 的含义**

服务器对客户端缓存的资源进行验证后，发现内容与之前相同，返回 304 Not Modified，告知客户端直接使用本地缓存，无需重新下载响应体。

```http
GET /style.css HTTP/1.1
Host: example.com
If-None-Match: "abc123"

HTTP/1.1 304 Not Modified
ETag: "abc123"
Cache-Control: max-age=3600
```

304 是**正常响应**，不是错误码。它出现在「有缓存 + 条件请求验证通过」的场景下。

**多少算合适？**

| 304 频率 | 含义 | 影响 |
| --- | --- | --- |
| 适量 | 静态资源缓存策略合理 | 减少带宽，提升加载速度 |
| 过多 | 页面长期不更新 | 搜索引擎可能降低抓取频次，快照停滞、收录减少、权重下降 |
| 过少 | 缓存未生效或资源频繁变更 | 增加服务器压力和带宽消耗 |

**304 过多的常见原因**

- 页面更新周期过长或根本不更新
- 纯静态页面或强制生成静态 HTML
- 缓存时间（max-age）设置过长

**对 SEO 的影响**

搜索引擎蜘蛛会根据抓取返回的状态码调节抓取频次。长期大量 304 可能让蜘蛛认为站点更新不频繁，降低回访率；反之，频繁返回新内容（200）有助于提升收录和权重。

**优化建议**

- 静态资源（JS/CSS/图片）设置合理的长缓存 + 文件指纹（hash）做版本控制
- HTML 页面使用较短缓存或协商缓存
- 内容更新后主动刷新 CDN 缓存

### 面试追问

1. **304 和 200 从缓存命中角度有什么区别？** 200 可能是强缓存直接命中（不发请求）或协商缓存后返回新内容；304 是协商缓存命中，发了请求但服务器返回未修改，使用本地缓存。
2. **强缓存和协商缓存分别用什么响应头？** 强缓存用 Cache-Control（max-age）/ Expires；协商缓存用 ETag/If-None-Match 或 Last-Modified/If-Modified-Since。

## 5. 常见的 HTTP 请求方法

**记忆口诀：**「GET 取 POST 改，PUT 更 DELETE 删，HEAD 看头 OPTIONS 问，CONNECT 隧道 TRACE 测」

**一句话总结：** HTTP 定义了 GET、POST、PUT、DELETE、HEAD、OPTIONS、CONNECT、TRACE 等方法，分别对应获取、提交、更新、删除、查首部、跨域预检、隧道和诊断等场景。

### 详细解答

| 方法 | 语义 | 是否有 Body | 是否幂等 | 典型场景 |
| --- | --- | --- | --- | --- |
| GET | 获取资源 | 否 | 是 | 查询数据、加载页面 |
| POST | 提交/创建资源 | 是 | 否 | 表单提交、创建订单 |
| PUT | 更新/替换资源 | 是 | 是 | 全量更新用户信息 |
| DELETE | 删除资源 | 可选 | 是 | 删除一条记录 |
| HEAD | 获取响应头（同 GET 但不返回 Body） | 否 | 是 | 检查资源是否存在、获取文件大小 |
| OPTIONS | 查询服务器支持的请求方法 | 否 | 是 | CORS 预检请求 |
| CONNECT | 建立隧道 | - | - | 通过代理建立 TCP 隧道（HTTPS 代理） |
| TRACE | 回显服务器收到的请求 | 否 | 是 | 诊断/调试（生产环境通常禁用） |

**重点方法说明**

- **GET**：安全、幂等，参数在 URL，可缓存
- **POST**：非幂等，提交数据到服务器，可能改变资源
- **PUT**：幂等，上传/更新数据，多次执行结果相同
- **DELETE**：幂等，删除服务器上的指定资源
- **HEAD**：与 GET 相同但只返回响应头，用于探测资源元信息，节省带宽
- **OPTIONS**：浏览器 CORS 预检时发送，询问服务器是否允许跨域及支持的方法
- **CONNECT**：要求代理服务器建立 TCP 隧道，常用于 HTTPS 代理
- **TRACE**：服务器回显收到的请求，用于测试，存在安全风险（XST 攻击）

**CORS 预检示例**

```http
OPTIONS /api/data HTTP/1.1
Origin: https://example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type
```

### 面试追问

1. **OPTIONS 请求在跨域中起什么作用？** 浏览器在发送非简单跨域请求前，先发 OPTIONS 预检，确认服务器是否允许该 Origin、Method 和 Header。
2. **HEAD 和 GET 有什么区别？** 语义相同，但 HEAD 只返回响应头不返回 Body，适合检查资源是否存在或获取 Content-Length 而不下载内容。

## 6. HTTP 1.0 和 HTTP 1.1 之间有哪些区别

**记忆口诀：**「1.1 持久连接 Range 断点，Etag 缓存 Host 虚拟主机，新增 PUT HEAD OPTIONS」

**一句话总结：** HTTP/1.1 相比 1.0 默认持久连接、支持 Range 请求、增强缓存机制、新增 Host 字段和多种请求方法。

### 详细解答

| 对比维度 | HTTP/1.0 | HTTP/1.1 |
| --- | --- | --- |
| 连接方式 | 默认短连接（非持久） | 默认长连接（持久连接） |
| 资源请求 | 不支持 Range，只能整资源下载 | 支持 Range 请求，返回 206 Partial Content |
| 缓存机制 | If-Modified-Since、Expires | 新增 ETag、If-None-Match、If-Match 等 |
| Host 字段 | 无（一台服务器一个 IP） | 新增 Host，支持虚拟主机 |
| 请求方法 | GET、POST、HEAD | 新增 PUT、OPTIONS、DELETE 等 |
| 管道化 | 不支持 | 支持 Pipeline（但有队头阻塞） |

**1. 连接方式**

- **HTTP/1.0**：默认短连接，每次请求/响应后关闭 TCP 连接，下次需重新三次握手。
- **HTTP/1.1**：默认持久连接（Keep-Alive），多个 HTTP 请求复用同一 TCP 连接，减少握手开销。需关闭时发送 `Connection: close`。

**2. 资源请求 — Range**

HTTP/1.1 引入 Range 头域，支持只请求资源的一部分，返回 206 Partial Content，实现断点续传和带宽优化。

```http
GET /video.mp4 HTTP/1.1
Host: example.com
Range: bytes=0-1023
```

**3. 缓存机制增强**

| 版本 | 缓存相关头部 |
| --- | --- |
| HTTP/1.0 | If-Modified-Since、Expires |
| HTTP/1.1 | ETag、If-None-Match、If-Unmodified-Since、If-Match、Cache-Control |

ETag 基于内容哈希，比 Last-Modified 更精确。

**4. Host 字段**

HTTP/1.0 假设一台服务器绑定唯一 IP，URL 不含主机名。虚拟主机技术出现后，HTTP/1.1 新增 Host 字段，同一 IP 可托管多个域名。

```http
GET /index.html HTTP/1.1
Host: www.example.com
```

**5. 新增请求方法**

HTTP/1.1 新增 PUT、HEAD、OPTIONS、DELETE、TRACE、CONNECT 等方法，为 RESTful 风格 API 奠定基础。

### 面试追问

1. **HTTP/1.1 的 Pipeline 为什么没能普及？** Pipeline 允许客户端连续发多个请求，但服务器必须按序响应，队首请求慢会阻塞后续所有响应（队头阻塞），且中间代理支持不完善。
2. **ETag 和 Last-Modified 哪个更好？** ETag 基于内容生成，精度更高（秒级时间内多次修改也能检测）；Last-Modified 只能精确到秒，但计算开销更小。

## 7. HTTP 1.1 和 HTTP 2.0 的区别

**记忆口诀：**「HTTP/2 二进制帧多路复用，HPACK 压头部，服务器可推送，TCP 层仍有队头阻塞」

**一句话总结：** HTTP/2 采用二进制分帧、多路复用、HPACK 头部压缩和服务器推送，解决了 HTTP/1.1 的应用层队头阻塞，但 TCP 层队头阻塞仍在。

### 详细解答

| 对比维度 | HTTP/1.1 | HTTP/2 |
| --- | --- | --- |
| 协议格式 | 文本协议（ASCII 头 + 文本/二进制体） | 二进制协议（帧 Frame） |
| 连接复用 | 一个 TCP 连接同时只处理一个请求（Pipeline 有限） | 多路复用，一个连接并行多个请求/响应 |
| 头部处理 | 每次请求携带完整头部，冗余大 | HPACK 压缩（哈夫曼编码 + 静态表/动态表） |
| 服务器推送 | 不支持 | 支持 Server Push |
| 队头阻塞 | 应用层队头阻塞 | 应用层解决，TCP 层仍存在 |

**1. 二进制协议**

HTTP/2 是彻底的二进制协议，头信息和数据体都封装为「帧（Frame）」，分为 HEADERS 帧和 DATA 帧等，这是多路复用的基础。

**2. 多路复用**

HTTP/2 复用同一 TCP 连接，客户端和服务器可以同时发送多个请求和响应，无需按顺序一一对应等待，解决了 HTTP/1.1 的应用层队头阻塞。

**3. 数据流（Stream）**

HTTP/2 中每个请求/响应对应一个数据流，有唯一 Stream ID。同一连接中的帧可能交错到达，通过 Stream ID 区分归属。

**4. 头信息压缩 — HPACK**

HTTP/1.1 无状态，每次请求都携带完整 Cookie、User-Agent 等重复头部。HTTP/2 使用 **HPACK 算法**（不是 gzip）：

- 客户端和服务器维护**静态表 + 动态表**（首部表）
- 重复字段只发索引号，不再发送完整字符串
- 对整数和字符串使用**哈夫曼编码**压缩
- 压缩率可达 50%~90%

**5. 服务器推送（Server Push）**

服务器可主动推送客户端尚未请求的资源（通常是静态资源），减少往返延迟。注意：HTTP/2 Push 推送的是静态资源，与 WebSocket/SSE 的实时数据推送不同。

**6. 队头阻塞说明**

HTTP/1.1 的队头阻塞源于「请求-应答」串行模型：队首请求慢，后面所有请求排队等待。

HTTP/2 在应用层通过多路复用解决了这个问题，但底层仍基于 TCP——若某个 TCP 包丢失，该连接上所有 Stream 都会等待重传（TCP 层队头阻塞）。HTTP/3 改用 QUIC（基于 UDP）进一步解决此问题。

### 面试追问

1. **HTTP/2 的多路复用和 HTTP/1.1 的多个 TCP 连接有什么区别？** HTTP/1.1 通过开 6 个 TCP 连接实现并行；HTTP/2 在单个 TCP 连接上用 Stream 并行传输，减少握手开销和连接数。
2. **HTTP/2 头部压缩为什么用 HPACK 而不是 gzip？** HPACK 使用静态表/动态表 + 哈夫曼编码，专为 HTTP 头部设计，能安全地跨请求共享上下文；gzip 存在 CRIME 等安全风险，不适合压缩头部。

## 8. HTTP 和 HTTPS 协议的区别

**记忆口诀：**「HTTP 明文 80 端口，HTTPS 加密 443 端口，HTTP 加 SSL/TLS 等于 HTTPS」

**一句话总结：** HTTPS = HTTP + SSL/TLS，在 443 端口提供加密传输和身份认证，比 HTTP 明文 80 端口更安全。

### 详细解答

| 对比维度 | HTTP | HTTPS |
| --- | --- | --- |
| 全称 | 超文本传输协议 | 安全超文本传输协议 |
| 安全性 | 明文传输，易被窃听/篡改 | SSL/TLS 加密，防窃听和篡改 |
| 端口 | 80 | 443 |
| 证书 | 不需要 | 需要 CA 颁发的数字证书 |
| 连接方式 | 直接 TCP 连接 | TCP + TLS 握手后加密通信 |
| 状态 | 无状态 | 无状态（加密层不影响 HTTP 语义） |

**HTTPS 的安全机制**

1. **加密传输**：SSL/TLS 对 HTTP 报文加密，防止中间人窃听
2. **身份认证**：数字证书验证服务器身份，防止伪装
3. **数据完整性**：MAC 校验防止报文被篡改

**HTTPS 工作流程（简化）**

```
客户端                         服务器
  |--- ClientHello ----------->|
  |<-- ServerHello + 证书 -----|
  |--- 验证证书，发送密钥 ----->|
  |<-- 确认，协商完成 ---------|
  |=== 加密 HTTP 通信 =========>|
```

**注意事项**

- HTTPS 需要 CA 证书，权威 CA 签发通常有费用（Let's Encrypt 可免费）
- HTTPS 不是绝对安全：证书被信任链验证失败、混合内容（HTTP 资源）、客户端漏洞等仍可能导致风险
- 现代浏览器对非 HTTPS 站点标记「不安全」，且 HTTP/2 在多数浏览器中要求 HTTPS

### 面试追问

1. **HTTPS 的加密过程是怎样的？** 使用非对称加密交换对称密钥（会话密钥），之后用对称加密传输 HTTP 数据，兼顾安全性和性能。
2. **HTTP 和 HTTPS 可以共用 80 端口吗？** 不行，HTTP 默认 80，HTTPS 默认 443；同一端口无法同时处理明文和 TLS 握手。

## 9. 当在浏览器中输入 Google.com 并且按下回车之后发生了什么

**记忆口诀：**「解析 URL 查缓存，DNS 找 IP ARP 找 MAC，TCP 握手 TLS 加密，收 HTML 渲染页面，最后四次挥手」

**一句话总结：** 从 URL 解析、缓存检查、DNS 解析、获取 MAC、TCP/TLS 握手、数据传输到页面渲染，最后 TCP 断开，经历完整的网络通信和浏览器渲染流程。

### 详细解答

**完整流程概览**

```
URL 解析 → 缓存判断 → DNS 解析 → 获取 MAC 地址
    → TCP 三次握手 → HTTPS TLS 握手 → 返回数据 → 页面渲染 → TCP 四次挥手
```

**（1）URL 解析**

浏览器解析 URL，提取协议（http/https）、主机名、路径等。若协议或主机名不合法，跳转搜索引擎；若含非法字符则转义后再处理。

**（2）缓存判断**

检查请求资源是否在浏览器缓存中且未过期。强缓存命中则直接使用；协商缓存则发条件请求验证。

**（3）DNS 解析**

获取域名对应的 IP 地址。依次查找：浏览器缓存 → 操作系统缓存 → 本地 DNS 服务器 → 根域名服务器 → 顶级域名服务器 → 权威域名服务器。用户到本地 DNS 是递归查询，本地 DNS 到各级是迭代查询。

**（4）获取 MAC 地址**

得到 IP 后还需目的主机 MAC 地址。将 IP 与子网掩码相与，判断目标是否在同一子网：
- 同子网：ARP 协议获取目标 MAC
- 不同子网：ARP 获取网关 MAC，数据先发到网关

**（5）TCP 三次握手**

```
客户端 --SYN(seq=x)------------> 服务器
客户端 <-SYN+ACK(seq=y,ack=x+1)-- 服务器
客户端 --ACK(ack=y+1)----------> 服务器
```

**（6）HTTPS TLS 握手（若使用 HTTPS）**

1. 客户端发送协议版本、随机数、支持的加密套件
2. 服务器返回加密方法、随机数、数字证书
3. 客户端验证证书，生成随机数用公钥加密发送，附带 hash 值
4. 服务器用私钥解密，返回 hash 值供客户端校验
5. 双方用三个随机数生成会话密钥，后续通信用此密钥加密

**（7）返回数据**

服务器返回 HTML 文件，浏览器接收响应。

**（8）页面渲染**

1. 解析 HTML 构建 DOM 树
2. 解析 CSS 构建 CSSOM 树
3. 遇到 script 标签，若无 defer/async 会阻塞渲染
4. DOM + CSSOM 构建渲染树（Render Tree）
5. Layout（布局）→ Paint（绘制）→ Composite（合成），页面显示

**（9）TCP 四次挥手**

```
客户端 --FIN--------------------> 服务器
客户端 <-ACK (CLOSE_WAIT)-------  服务器
客户端 <-FIN (LAST-ACK)---------  服务器
客户端 --ACK (TIME-WAIT 2MSL)---> 服务器
```

客户端进入 TIME-WAIT 等待 2MSL，确保最后的 ACK 到达；服务器收到 ACK 后关闭。

### 面试追问

1. **DNS 递归查询和迭代查询有什么区别？** 递归：客户端只发一次请求，本地 DNS 负责全程查找并返回最终结果；迭代：DNS 服务器返回下一级地址，查询者自己继续查。
2. **为什么 TIME-WAIT 要等待 2MSL？** 确保最后一个 ACK 能到达服务器（若丢失服务器会重发 FIN），且让旧连接的数据包在网络中消散，避免影响新连接。

## 10. 对 keep-alive 的理解

**记忆口诀：**「1.0 默认短连接需手动 keep-alive，1.1 默认长连接需手动 close；复用 TCP 省握手，但占资源」

**一句话总结：** Keep-Alive 是 HTTP 持久连接机制，复用 TCP 连接传输多个请求，HTTP/1.1 默认开启，减少握手开销但长时间占用系统资源。

### 详细解答

**短连接 vs 长连接**

| 类型 | 说明 | 默认版本 |
| --- | --- | --- |
| 短连接 | 每次请求/响应后关闭 TCP 连接 | HTTP/1.0 |
| 长连接（Keep-Alive） | TCP 连接保持，多个请求复用 | HTTP/1.1 |

**版本差异**

- **HTTP/1.0**：默认短连接。需手动发送 `Connection: keep-alive` 开启持久连接；发送 `Connection: close` 关闭。
- **HTTP/1.1**：默认长连接。需发送 `Connection: close` 主动关闭。

**Keep-Alive 建立过程**

1. 客户端发送请求，首部带 `Connection: keep-alive`
2. 服务器处理 Connection 字段
3. 服务器响应 `Connection: keep-alive`
4. 连接保持，后续请求复用

**断开连接的两种方式**

| 场景 | 触发方式 |
| --- | --- |
| 服务端自动断开 | 客户端不发送 Connection 字段（HTTP/1.0），服务器响应后关闭 |
| 客户端主动断开 | 客户端发送 `Connection: close`，服务器响应后关闭 |

**优点**

- 减少 CPU 和内存消耗（更少的 TCP 连接）
- 支持 HTTP Pipeline（管线化）
- 降低 TCP 拥塞控制开销
- 减少后续请求延迟（无需重复握手）
- 出错时不必关闭 TCP 连接

**缺点**

- 长时间 TCP 连接占用系统资源（文件描述符、内存）
- 服务器需管理大量空闲连接

```http
GET /api/data HTTP/1.1
Host: example.com
Connection: keep-alive

HTTP/1.1 200 OK
Connection: keep-alive
Keep-Alive: timeout=5, max=100
Content-Type: application/json

{"data": "..."}
```

### 面试追问

1. **Keep-Alive 和 HTTP/2 多路复用有什么关系？** Keep-Alive 是 HTTP/1.x 在 TCP 层复用连接；HTTP/2 在 Keep-Alive 的 TCP 连接上进一步实现应用层多路复用（多个 Stream 并行）。
2. **长连接会不会导致服务器连接数耗尽？** 有可能，因此需要设置合理的 timeout 和 max 参数，或使用连接池、负载均衡等手段管理。

## 11. 页面有多张图片，HTTP 是怎样的加载表现

**记忆口诀：**「HTTP/1 六连接限并行，多域名分片来加速；HTTP/2 多路复用，一连接并行传」

**一句话总结：** HTTP/1.x 同域名最多 6 个 TCP 并行连接，大量图片需排队或域名分片；HTTP/2 多路复用可在单连接上并行加载所有资源。

### 详细解答

**HTTP/1.x 的加载表现**

浏览器对**同一域名**的 TCP 连接数有限制（通常 6 个）。页面有 20 张图片时：

```
连接 1: img1, img7,  img13 ...
连接 2: img2, img8,  img14 ...
连接 3: img3, img9,  img15 ...
连接 4: img4, img10, img16 ...
连接 5: img5, img11, img17 ...
连接 6: img6, img12, img18 ...
         img19, img20 需排队等待
```

前 6 张并行加载，其余排队，存在明显的串行等待。

**优化手段 — 域名分片（Domain Sharding）**

将图片分散到多个二级域名（如 `img1.cdn.com`、`img2.cdn.com`），每个域名 6 个连接，提高并行度。

| 域名数 | 最大并行连接 |
| --- | --- |
| 1 | 6 |
| 3 | 18 |
| 6 | 36 |

缺点：每个域名需 DNS 解析和 TCP 握手，HTTP/2 时代已不再推荐。

**HTTP/2 的加载表现**

HTTP/2 支持**多路复用**，一个 TCP 连接上可并行传输多个请求/响应，20 张图片可以同时发起请求，无需排队。

```
单个 TCP 连接
├── Stream 1: img1
├── Stream 2: img2
├── Stream 3: img3
├── ...
└── Stream 20: img20  （全部并行）
```

**对比总结**

| 特性 | HTTP/1.x | HTTP/2 |
| --- | --- | --- |
| 同域名并行连接 | 最多 6 个 | 1 个（多路复用） |
| 大量图片加载 | 排队等待 | 几乎同时加载 |
| 优化手段 | 域名分片、雪碧图、内联 | 多路复用天然支持 |
| 连接开销 | 多连接多握手 | 单连接低开销 |

### 面试追问

1. **为什么 HTTP/1.x 限制 6 个连接？** 防止客户端占用过多服务器资源，是浏览器厂商的约定（非 RFC 标准），不同浏览器可能略有差异。
2. **HTTP/2 时代还需要域名分片吗？** 不需要，反而有害。多域名意味着多个 TCP 连接，无法共享 HPACK 动态表，增加握手和内存开销。

## 12. HTTP/2 的头部压缩算法是怎样的

**记忆口诀：**「HPACK 静动两表建字典，索引替重复，哈夫曼压整数和字符串」

**一句话总结：** HTTP/2 使用 HPACK 算法压缩头部，通过静态表/动态表索引重复字段，配合哈夫曼编码，压缩率达 50%~90%。

### 详细解答

HTTP/1.1 每次请求都携带完整头部（Cookie、User-Agent 等大量重复内容），浪费带宽。HTTP/2 引入 **HPACK**（RFC 7541）专门压缩头部，**不是 gzip 或 compress**。

**HPACK 核心机制**

| 机制 | 说明 |
| --- | --- |
| 静态表 | 61 个常见头部名/值的预定义索引（如 :method GET = 2） |
| 动态表 | 连接存续期内，客户端和服务器共同维护，渐进更新 |
| 索引编码 | 重复字段只发索引号，不再发送完整字符串 |
| 哈夫曼编码 | 对整数和字符串进行哈夫曼压缩 |

**工作流程**

1. 连接建立时，静态表已预置常见头部
2. 第一个请求发送完整头部，同时写入动态表
3. 后续请求中相同字段只发索引号
4. 新字段追加到动态表末尾，或替换旧值

**示例对比**

第一次请求（完整头部）：

```
:method: GET
:path: /index.html
:authority: www.example.com
user-agent: Mozilla/5.0 ...
accept: text/html ...
cookie: session=abc123; theme=dark
```

第二次请求（仅差异）：

```
:method: GET          → 索引 2（静态表）
:path: /about.html    → 新值，追加动态表
cookie: session=abc123; theme=dark  → 索引号（动态表命中）
```

**关键特性**

- 动态表在 HTTP/2 连接存续期内始终存在
- 客户端和服务器各自维护一份，通过传输的索引同步更新
- 压缩率通常 50%~90%，显著减少头部开销

**与 gzip 的区别**

HPACK 专为 HTTP 头部设计，使用固定静态表 + 增量动态表，安全且高效。gzip 压缩 HTTP 头部存在 CRIME/BREACH 等安全风险，HTTP/2 明确不使用 gzip 压缩头部。

### 面试追问

1. **HPACK 的静态表和动态表分别存什么？** 静态表存 61 个 RFC 预定义的常见头部键值对；动态表存当前连接中实际出现过的头部，随请求渐进更新。
2. **如果动态表满了怎么办？** 新条目追加到表尾，旧条目被驱逐（FIFO），或使用索引替换已有条目。

## 13. HTTP 请求报文的是什么样的

**记忆口诀：**「请求行、请求头、空行、请求体，四段组成 HTTP 请求报文」

**一句话总结：** HTTP 请求报文由请求行、请求头、空行和请求体四部分组成。

### 详细解答

**报文结构**

```
┌─────────────────────────────────┐
│  请求行（Request Line）           │
├─────────────────────────────────┤
│  请求头（Request Headers）        │
│  Header1: value1                │
│  Header2: value2                │
├─────────────────────────────────┤
│  空行（CRLF）                     │
├─────────────────────────────────┤
│  请求体（Request Body，可选）     │
└─────────────────────────────────┘
```

**各部分说明**

| 部分 | 内容 | 示例 |
| --- | --- | --- |
| 请求行 | 方法 + URL + HTTP 版本 | `GET /index.html HTTP/1.1` |
| 请求头 | 键值对，每行一个，冒号分隔 | `Host: example.com` |
| 空行 | `\r\n`，标识头部结束 | （空行） |
| 请求体 | POST/PUT 等携带的数据 | `{"name": "张三"}` |

**完整示例**

```http
POST /api/login HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7)
Accept: application/json
Content-Type: application/json
Content-Length: 42
Connection: keep-alive

{"username": "admin", "password": "123456"}
```

**常见请求头字段**

- **User-Agent**：产生请求的浏览器/客户端类型
- **Accept**：客户端可识别的内容类型
- **Host**：请求的主机名，HTTP/1.1 必需，支持虚拟主机
- **Content-Type**：请求体的 MIME 类型
- **Content-Length**：请求体的字节长度

**注意**

- GET、HEAD 等方法通常没有请求体
- POST、PUT、PATCH 等方法通过请求体携带数据
- 请求行、请求头、空行属于「请求报文首部」，请求体是可选的「实体部分」

### 面试追问

1. **请求行中的 URL 可以是绝对路径还是完整 URL？** 向代理发送时用完整 URL（如 `GET http://example.com/index.html HTTP/1.1`）；向源服务器发送时通常用绝对路径（如 `GET /index.html HTTP/1.1`）。
2. **Content-Length 和 Transfer-Encoding: chunked 有什么区别？** Content-Length 声明固定长度；chunked 是分块传输，适用于动态生成、长度未知的内容，两者互斥。

## 14. HTTP 响应报文的是什么样的

**记忆口诀：**「响应行、响应头、空行、响应体，四段组成 HTTP 响应报文」

**一句话总结：** HTTP 响应报文由响应行、响应头、空行和响应体四部分组成。

### 详细解答

**报文结构**

```
┌─────────────────────────────────┐
│  响应行（Status Line）            │
├─────────────────────────────────┤
│  响应头（Response Headers）       │
│  Header1: value1                │
│  Header2: value2                │
├─────────────────────────────────┤
│  空行（CRLF）                     │
├─────────────────────────────────┤
│  响应体（Response Body）          │
└─────────────────────────────────┘
```

**各部分说明**

| 部分 | 内容 | 示例 |
| --- | --- | --- |
| 响应行 | HTTP 版本 + 状态码 + 原因短语 | `HTTP/1.1 200 OK` |
| 响应头 | 键值对，描述响应的元信息 | `Content-Type: text/html` |
| 空行 | `\r\n`，标识头部结束 | （空行） |
| 响应体 | 服务器返回的实际数据 | HTML、JSON、图片等 |

**完整示例**

```http
HTTP/1.1 200 OK
Date: Mon, 15 Jun 2026 08:00:00 GMT
Server: nginx/1.24.0
Content-Type: text/html; charset=UTF-8
Content-Length: 256
Cache-Control: max-age=3600
Connection: keep-alive

<!DOCTYPE html>
<html>
<head><title>Example</title></head>
<body><h1>Hello World</h1></body>
</html>
```

**响应行状态码分类**

| 范围 | 类别 | 示例 |
| --- | --- | --- |
| 1xx | 信息性 | 100 Continue |
| 2xx | 成功 | 200 OK、201 Created、204 No Content |
| 3xx | 重定向 | 301 Moved、304 Not Modified |
| 4xx | 客户端错误 | 400 Bad Request、404 Not Found |
| 5xx | 服务器错误 | 500 Internal Server Error、502 Bad Gateway |

**常见响应头**

- **Content-Type**：响应体的 MIME 类型
- **Content-Length**：响应体字节长度
- **Cache-Control**：缓存策略
- **Set-Cookie**：服务器向客户端设置 Cookie
- **Location**：重定向目标 URL（3xx 响应）

**特殊响应**

- **204 No Content**：成功但无响应体
- **304 Not Modified**：资源未修改，使用缓存，无响应体
- **301/302**：重定向，响应体通常很短

### 面试追问

1. **响应行中的原因短语（Reason Phrase）必须准确吗？** 不必须，它仅供人阅读，程序应依据状态码判断；HTTP/2 甚至省略了原因短语。
2. **HEAD 请求的响应报文有什么特殊之处？** 响应行和响应头正常返回，但没有响应体，用于获取资源元信息而不下载内容。

## 15. HTTP 协议的优点和缺点

**记忆口诀：**「优点简单快速无状态灵活，缺点无状态明文不安全」

**一句话总结：** HTTP 简单快速、灵活易用，但无状态导致上下文需重传、明文传输不安全。

### 详细解答

HTTP（HyperText Transfer Protocol）是超文本传输协议，默认端口 80，基于 TCP 传输，保证数据可靠性。

**优点**

| 优点 | 说明 |
| --- | --- |
| 简单快速 | 只需传送请求方法和路径，协议简单，服务器程序规模小，通信速度快 |
| 无连接 | 每次连接只处理一个请求，处理完毕即断开（HTTP/1.0），节省传输时间 |
| 无状态 | 服务器不保存客户端状态，简化服务器设计，响应快 |
| 灵活 | 通过 Content-Type 可传输任意类型数据（HTML、JSON、图片、视频等） |
| 客户端/服务器模式 | 清晰的分层架构，易于理解和实现 |

**缺点**

| 缺点 | 说明 |
| --- | --- |
| 无状态 | 不保存上下文，后续请求若需之前的信息必须重传，增加数据量 |
| 明文传输 | 报文以文本形式传输，直接暴露给网络，易被窃听 |
| 不安全 | 三大安全问题 |

**HTTP 的三大安全问题**

1. **窃听**：通信使用明文，内容可被中间人截获
2. **伪装**：不验证通信方身份，可能遭遇中间人伪装
3. **篡改**：无法证明报文完整性，内容可能已被修改

**无状态的双面性**

无状态既是优点（服务器简单、易扩展）也是缺点（无法识别用户，需 Cookie/Session/Token 等机制补充状态）。

```http
# 无状态导致每次都要带 Cookie
GET /api/profile HTTP/1.1
Cookie: session_id=abc123

GET /api/orders HTTP/1.1
Cookie: session_id=abc123
```

**解决方案**

- 安全性 → HTTPS（SSL/TLS 加密 + 证书认证）
- 无状态 → Cookie、Session、JWT 等状态管理机制
- 性能 → Keep-Alive、HTTP/2 多路复用、CDN 缓存

### 面试追问

1. **HTTP 无状态是好事还是坏事？** 两者兼有：简化服务器设计、易于水平扩展是好事；但用户登录态、购物车等需额外机制（Cookie/Session）维护状态。
2. **为什么说 HTTP/2 仍然不够安全？** HTTP/2 本身不加密，仍可被窃听；且 HTTP/2 在多数浏览器中强制要求 HTTPS，安全依赖 TLS 层。

## 16. HTTP 协议的性能怎么样

**记忆口诀：**「性能看连接和传输模式，长连接省握手，Pipeline 有队头阻塞，多连接和域名分片来解」

**一句话总结：** HTTP 性能取决于 TCP 连接模式（长/短连接）和传输方式；HTTP/1.1 的 Pipeline 有队头阻塞，可通过多连接和域名分片缓解。

### 详细解答

HTTP 基于 TCP/IP，采用请求-应答模式，性能瓶颈主要在连接管理和串行传输。

**1. 长连接 vs 短连接**

| 连接模式 | 说明 | 版本 |
| --- | --- | --- |
| 非持续连接（短连接） | 每个请求新建 TCP 连接，完成后断开 | HTTP/1.0 默认 |
| 持续连接（长连接） | TCP 连接复用，多个请求共享 | HTTP/1.1 默认 |

短连接每次需 TCP 三次握手 + 四次挥手，开销大。长连接避免重复建立/断开，减轻服务器负载。

```
短连接: [握手][请求/响应][挥手] [握手][请求/响应][挥手] ...
长连接: [握手][请求/响应][请求/响应][请求/响应] ... [挥手]
```

HTTP/1.0 可通过 `Connection: keep-alive` 开启长连接；HTTP/1.1 默认长连接。同域名浏览器通常支持 6 个持久连接。

**2. 管道化传输（Pipeline）**

HTTP/1.1 长连接基础上支持 Pipeline：客户端可连续发出多个请求，不必等前一个响应返回。

```
普通:  请求1 → 响应1 → 请求2 → 响应2 → 请求3 → 响应3
Pipeline: 请求1 → 请求2 → 请求3 → 响应1 → 响应2 → 响应3
```

但服务器必须**按顺序**响应。若第一个响应很慢，后续响应全部排队 — 这就是**队头阻塞（Head-of-Line Blocking）**。

**3. 队头阻塞及解决方案**

HTTP 请求-应答模型形成串行队列，队首请求慢则阻塞所有后续请求。

| 方案 | 原理 | 效果 |
| --- | --- | --- |
| 并发连接 | 同域名开多个 TCP 连接（最多 6 个） | 增加并行队列，减少阻塞影响 |
| 域名分片 | 多个二级域名指向同一服务器 | 6 × N 个并行连接 |
| HTTP/2 多路复用 | 单连接多 Stream 并行 | 解决应用层队头阻塞 |
| HTTP/3 QUIC | 基于 UDP，Stream 独立 | 解决 TCP 层队头阻塞 |

**性能演进**

```
HTTP/1.0 短连接 → HTTP/1.1 长连接 + Pipeline → HTTP/2 多路复用 + HPACK → HTTP/3 QUIC
```

**实际优化手段**

- 合并资源（雪碧图、内联 CSS/JS）
- 压缩（gzip/brotli）
- CDN 边缘缓存
- 域名分片（HTTP/1.x）或 HTTP/2 单连接
- 预连接（`<link rel="preconnect">`）、预加载（`<link rel="preload">`）

### 面试追问

1. **HTTP/1.1 的 Pipeline 为什么很少被使用？** 服务器必须按序响应导致队头阻塞、中间代理支持差、实现复杂，收益不明显，被多连接方案取代。
2. **HTTP/2 解决了队头阻塞吗？** 解决了应用层队头阻塞（多路复用），但 TCP 层丢包仍会阻塞所有 Stream；HTTP/3 用 QUIC 在传输层解决。

## 17. URL 有哪些组成部分

**记忆口诀：**「协议域名端口路径，文件名参数锚点，七部分拼成完整 URL」

**一句话总结：** URL 由协议、域名、端口、虚拟目录、文件名、参数和锚七部分组成，各部分用特定分隔符连接。

### 详细解答

以完整 URL 为例：

```
http://www.example.com:8080/news/index.asp?boardID=5&ID=24618&page=1#name
```

**URL 组成部分**

| 部分 | 示例值 | 是否必须 | 说明 |
| --- | --- | --- | --- |
| 协议 | `http:` | 是 | 使用的协议，`//` 为分隔符 |
| 域名 | `www.example.com` | 是 | 主机名，也可用 IP 地址 |
| 端口 | `8080` | 否 | 省略时使用默认端口（HTTP 80，HTTPS 443） |
| 虚拟目录 | `/news/` | 否 | 域名后第一个 `/` 到最后一个 `/` |
| 文件名 | `index.asp` | 否 | 最后一个 `/` 到 `?` 或 `#` 之间 |
| 参数（查询字符串） | `boardID=5&ID=24618&page=1` | 否 | `?` 到 `#` 之间，多参数用 `&` 分隔 |
| 锚（片段） | `name` | 否 | `#` 之后，页面内定位，不发往服务器 |

**结构拆解**

```
协议    域名              端口 虚拟目录  文件名     参数                    锚
http:// www.example.com :8080 /news/  index.asp ?boardID=5&ID=24618&page=1 #name
└─┬──┘  └──────┬──────┘ └┬─┘ └──┬──┘  └───┬───┘ └──────────┬─────────────┘ └─┬─┘
  │           │         │      │        │                │                  │
scheme     host      port    path    filename         query              fragment
```

**各部分详解**

1. **协议部分**：`http:` 或 `https:` 等，`//` 是协议与主机名的分隔符
2. **域名部分**：可以是域名或 IP 地址
3. **端口部分**：域名后用 `:` 分隔，省略则使用默认端口
4. **虚拟目录**：路径中的目录部分，如 `/news/`
5. **文件名部分**：路径最后一段，省略则使用默认文件名（如 `index.html`）
6. **参数部分**：又称搜索部分/查询字符串，`?` 开头，`&` 连接多个键值对
7. **锚部分**：`#` 开头，用于页面内跳转，**不会发送到服务器**

**编码规则**

URL 中只允许 ASCII 字母、数字及 `-._~` 等部分特殊字符，其他字符需百分号编码（Percent-Encoding）。

```
空格 → %20
中文「测试」 → %E6%B5%8B%E8%AF%95
```

### 面试追问

1. **URL 的锚（#fragment）会发送到服务器吗？** 不会，fragment 仅在浏览器端用于页面内定位，不会包含在 HTTP 请求中。
2. **URL 和 URI 有什么区别？** URI 是统一资源标识符（含 URL 和 URN）；URL 是统一资源定位符，指明资源的位置和访问方式，是 URI 的子集。

## 18. 与缓存相关的HTTP请求头有哪些

**记忆口诀：**「强缓存 Expires 和 Cache-Control，协商 Etag 配 If-None-Match，Last-Modified 配 If-Modified-Since」

**一句话总结：** HTTP 缓存分为**强缓存**（不发请求直接用本地）和**协商缓存**（发请求问服务器是否过期），分别由不同的请求/响应头配合实现。

### 详细解答

#### 强缓存（不发请求，直接用本地）

| 响应头 | 说明 |
| --- | --- |
| `Expires` | HTTP/1.0 产物，指定资源**绝对过期时间** |
| `Cache-Control` | HTTP/1.1 主流方案，优先级高于 Expires |

`Cache-Control` 常用指令：

```http
Cache-Control: max-age=3600          # 相对时间，3600 秒内有效
Cache-Control: no-cache              # 可缓存，但每次须向服务器验证
Cache-Control: no-store              # 禁止缓存
Cache-Control: public / private      # 公共/私有缓存
```

#### 协商缓存（发请求，304 用本地）

| 响应头 | 对应请求头 | 说明 |
| --- | --- | --- |
| `Last-Modified` | `If-Modified-Since` | 资源最后修改时间，精度到秒 |
| `ETag` | `If-None-Match` | 资源内容的唯一标识（哈希值），精度更高 |

**优先级：** `ETag` > `Last-Modified`；`Cache-Control` > `Expires`。

### 面试追问

1. **强缓存和协商缓存的执行顺序？** 先查强缓存，命中且未过期直接用；过期或 `no-cache` 再走协商缓存；都未命中则正常请求 200。
2. **`ETag` 和 `Last-Modified` 为什么常一起用？** `Last-Modified` 精度只到秒；`ETag` 基于内容哈希更精确但有计算开销，两者互补。

## 19. 什么是HTTPS协议？

**记忆口诀：**「HTTP 加 TLS/SSL，加密传输保隐私，身份认证防篡改」

**一句话总结：** HTTPS = HTTP + TLS/SSL，在 HTTP 与 TCP 之间加一层安全协议，提供**身份认证、信息加密、完整性校验**。

### 详细解答

HTTPS 经由 HTTP 通信，利用 SSL/TLS 对数据包加密。HTTP 明文传输存在窃听、篡改、劫持风险，TLS/SSL 安全层位于 TCP 与 HTTP 之间解决这些问题。

| 对比项 | HTTP | HTTPS |
| --- | --- | --- |
| 端口 | 80 | 443 |
| 传输 | 明文 | 加密 |
| 证书 | 不需要 | 需要 CA 证书 |
| 性能 | 较快 | 握手有额外开销 |

### 面试追问

1. **HTTPS 能防止所有攻击吗？** 不能。它防传输层窃听和篡改；XSS、CSRF 等应用层问题仍需单独防护。
2. **TLS 和 SSL 是什么关系？** SSL 是早期协议，TLS 1.0 基于 SSL 3.0 演进；现实际主流为 TLS 1.2/1.3。

## 20. TLS/SSL的工作原理

**记忆口诀：**「Hash 验完整，对称加密传数据，非对称协商密钥，三者组合是 TLS」

**一句话总结：** TLS/SSL 依赖**散列函数、对称加密、非对称加密**三类算法，用非对称加密协商对称密钥，再用对称加密高效通信。

### 详细解答

| 算法类型 | 代表算法 | 作用 |
| --- | --- | --- |
| 散列函数 | MD5、SHA256 | 验证完整性，防篡改 |
| 对称加密 | AES-GCM、DES | 同一密钥加解密，效率高 |
| 非对称加密 | RSA、ECC、DH | 身份认证、密钥协商 |

**综合策略：** 握手用非对称加密协商对称密钥 → 通信用对称加密传数据 → 全程用 Hash 校验完整性。

### 面试追问

1. **为什么不全程用非对称加密？** 非对称加密比对称慢数百倍，大量数据用对称更合适。
2. **对称密钥怎么安全传递？** 客户端生成预主密钥，用服务器公钥加密后发送，只有服务器私钥能解密。

## 21. 数字证书是什么？

**记忆口诀：**「CA 私钥签公钥，浏览器内置根证书，防中间人冒充」

**一句话总结：** 数字证书由 CA 用私钥对「公钥+身份信息」的摘要签名生成，接收方用 CA 公钥验证，确保公钥可信。

### 详细解答

非对称加密前提是公钥可信。数字证书由权威 CA 签发解决信任问题：

**生成：** 服务器提交公钥 → CA 对内容做 Hash 生成摘要 → CA 私钥加密摘要生成签名 → 原始信息+签名=证书

**验证：** 客户端用同样 Hash 生成摘要 A → 用 CA 公钥解密签名得摘要 B → A===B 则证书可信

浏览器内置根 CA 证书，形成信任链。

### 面试追问

1. **证书过期会怎样？** 浏览器提示不安全；Let's Encrypt 支持自动续期。
2. **自签名证书能用吗？** 可以但浏览器不信任，需手动添加例外。适合内部测试环境。

## 22. HTTPS通信（握手）过程

**记忆口诀：**「ClientHello 发随机数，ServerHello 回证书，ClientKeyExchange 加密预主密钥，三随机数生会话密钥」

**一句话总结：** HTTPS 握手通过**两次随机数 + 预主密钥**生成会话密钥，之后用对称加密传输数据。

### 详细解答

1. **ClientHello**：客户端发送 TLS 版本、随机数 C、支持的加密算法列表
2. **ServerHello**：服务器选定加密套件、返回证书和随机数 S
3. **ClientKeyExchange**：客户端验证证书，生成预主密钥 P，用公钥加密发送，附带前面内容的 hash
4. **服务器解密**：用私钥解密 P，返回 hash 供校验
5. **生成会话密钥**：双方用 C+S+P 生成对称会话密钥

### 面试追问

1. **为什么需要三个随机数？** C、S 防重放；P 仅服务器能解密，确保会话密钥只有双方知道。
2. **TLS 1.3 有什么改进？** 握手从 2-RTT 降为 1-RTT，废弃不安全算法，只保留 AEAD 加密。

---

## 23. HTTPS的特点

**记忆口诀：**「安全认证加密强，握手费时证书贵，服务器资源消耗大」

**一句话总结：** HTTPS 提供认证、加密与完整性，但带来性能开销、握手延迟、证书成本等代价。

### 详细解答

**优点：** 认证用户和服务器、加密传输防窃取篡改、大幅增加中间人攻击成本。

**缺点：** 加解密消耗 CPU、TLS 握手增加延迟、SSL 证书收费（Let's Encrypt 可免费）、传统 SSL 证书需绑定 IP。

### 面试追问

1. **全站 HTTPS 值得吗？** 值得。安全合规是主因，性能差距可通过 TLS 1.3、CDN、会话复用缩小。
2. **HTTP/2 必须 HTTPS 吗？** 规范不强制，但主流浏览器仅对 HTTPS 启用 HTTP/2。

## 24. HTTPS是如何保证安全的？数字签名

**记忆口诀：**「对称传数据，非对称传密钥，CA 证书防冒充，数字签名防篡改」

**一句话总结：** HTTPS 通过**对称加密+非对称加密+CA证书+数字签名**四层机制保证安全。

### 详细解答

- **对称加密**：高效传数据，但密钥交换不安全
- **非对称加密**：安全传密钥，但公钥可能被冒充
- **CA 证书**：解决公钥信任，但证书可能被篡改
- **数字签名**：CA 对证书内容 Hash 后用私钥加密，验证时用 CA 公钥解密对比摘要

四层层层解决上一层遗留的安全问题。

### 面试追问

1. **中间人能伪造 CA 签名吗？** 不能。CA 私钥仅 CA 持有，攻击者无法生成合法签名。
2. **数字签名和数字证书的区别？** 证书是载体（身份+公钥），签名是 CA 对证书内容的加密摘要（防篡改）。

## 25. HTTP状态码

**记忆口诀：**「2 成功 3 跳转 4 客户端错 5 服务端错，304 协商缓存 404 找不到」

**一句话总结：** HTTP 状态码分五类：2XX 成功、3XX 重定向、4XX 客户端错误、5XX 服务器错误。

### 详细解答

| 类别 | 常见码 | 含义 |
| --- | --- | --- |
| 2XX | 200/204/206 | 成功/无内容/范围请求 |
| 3XX | 301/302/304/307 | 永久/临时重定向/缓存命中/保持方法临时重定向 |
| 4XX | 400/401/403/404 | 语法错误/未认证/禁止/未找到 |
| 5XX | 500/502/503/504 | 内部错误/网关错误/过载/网关超时 |

### 面试追问

1. **301 和 302 的区别？** 301 永久，浏览器和搜索引擎更新 URL；302 临时，原 URL 仍有效。
2. **401 和 403 的区别？** 401 未认证（你是谁？）；403 已识别但无权限（知道你是谁，但不让访问）。

## 26. DNS 协议是什么

**记忆口诀：**「域名转 IP，分层分布式，应用层协议查主机」

**一句话总结：** DNS 是域名到 IP 地址的转换服务，由分层 DNS 服务器组成的分布式数据库，属于应用层协议。

### 详细解答

将人类可读的域名（如 `www.baidu.com`）解析为 IP 地址。本质是分布式数据库+查询协议，树状域名空间从根域到顶级域到权威域。

### 面试追问

1. **DNS 是应用层还是传输层？** 应用层，底层用 UDP/TCP 53 端口传输。
2. **一个域名可以对应多个 IP 吗？** 可以，多条 A 记录实现负载均衡；CDN 按地域返回不同 IP。

## 27. DNS同时使用TCP和UDP协议？

**记忆口诀：**「53 端口双协议，区域传输用 TCP，日常解析用 UDP」

**一句话总结：** DNS 占用 53 端口，区域传输用 TCP（数据量大、可靠），域名解析用 UDP（快速、<512字节）。

### 详细解答

| 场景 | 协议 | 原因 |
| --- | --- | --- |
| 区域传输 | TCP | 辅 DNS 向主 DNS 同步，数据量大 |
| 域名解析 | UDP | 响应通常<512字节，无需握手 |

响应超过 512 字节时设 TC 标志，客户端改用 TCP 重试。

### 面试追问

1. **为什么 UDP 限制 512 字节？** 传统设计避免 IP 分片；超过则截断提示用 TCP。
2. **DoH 和 DoT 是什么？** DNS over HTTPS（443）和 DNS over TLS（853），加密查询防窃听。

## 28. DNS完整的查询过程

**记忆口诀：**「浏览器缓存 → 本地 DNS → 根 → 顶级 → 权威 → 返回 IP」

**一句话总结：** DNS 解析从浏览器缓存开始，逐级查询本地 DNS → 根 → 顶级 → 权威域名服务器。

2. **hosts 文件和 DNS 谁先？** 通常先查 hosts 再查 DNS。

## 29. 迭代查询与递归查询

## 35. UDP 协议为什么不可靠？

**记忆口诀：**「不确认不重传，无超时无排序，不拥塞不跟踪，UDP 只管发不管到」

**一句话总结：** UDP 是无连接、无确认、无重传、无排序、无拥塞控制的传输协议，不保证消息可靠交付和顺序到达。

### 详细解答

UDP（User Datagram Protocol）在传输数据前不需要建立连接，接收方收到报文后也不发送确认，提供不可靠交付。与 TCP 的可靠传输形成鲜明对比，UDP 的「不可靠」体现在以下四个方面：

| 维度 | UDP 行为 | 对比 TCP |
| --- | --- | --- |
| 消息交付 | 不确认、不重传、无超时机制 | 确认应答 + 超时重传 |
| 交付顺序 | 不设置序号、不重排、无队头阻塞 | 按序交付、乱序缓存 |
| 连接状态 | 不必建立连接或维护状态机 | 三次握手建立、四次挥手释放 |
| 拥塞控制 | 无客户端/网络反馈机制 | 慢启动、拥塞避免等 |

**1. 不保证消息交付**

发送方发出数据包后，UDP 不会等待接收方确认，也不会在丢包时自动重传。若网络层出现丢包、重复或失序，UDP 不会做任何补救。

**2. 不保证交付顺序**

UDP 报文没有序号字段，接收方按到达顺序处理，不会重排乱序包。好处是不会发生 TCP 那样的队头阻塞，适合实时性要求高的场景。

**3. 不跟踪连接状态**

UDP 是无连接协议，发送方不需要先建立连接，接收方也不需要维护连接状态机，开销小、延迟低。

**4. 不进行拥塞控制**

UDP 没有内置的拥塞控制机制，发送速率完全由应用层决定。在网络拥塞时可能加剧丢包，但适合 DNS 查询、视频直播、在线游戏等对延迟敏感的场景。

**适用场景：** DNS 解析、VoIP、视频会议、QUIC/HTTP3 底层、广播/组播等。

### 面试追问

1. **UDP 不可靠，为什么还被广泛使用？** 因为无连接、无确认、头部开销小（8 字节），延迟低、实现简单，适合允许少量丢包但要求实时性的场景；可靠传输可由上层协议（如 QUIC）或应用层自行实现。
2. **UDP 和 TCP 的头部大小分别是多少？** UDP 固定 8 字节；TCP 至少 20 字节，还要维护连接状态和滑动窗口，开销更大。

## 36. TCP 的重传机制

**记忆口诀：**「定时器超时重传，三 ACK 快重传，两套机制保可靠」

**一句话总结：** TCP 通过**超时重传**（基于定时器）和**快速重传**（收到三个重复 ACK）两套独立机制，保证丢失或损坏的数据包被重新发送。

### 详细解答

由于网络层可能出现**丢失、重复或失序**，TCP 提供可靠数据传输，对认为已丢失（含比特错误）的报文段进行重传。重传机制分为两类：

| 机制 | 触发条件 | 特点 |
| --- | --- | --- |
| 超时重传 | 定时器到期仍未收到 ACK | 保守，需等待 RTO 超时 |
| 快速重传 | 连续收到 3 个重复 ACK | 激进，不必等定时器，吞吐更高 |

**1. 基于时间的超时重传**

- TCP 发送一个报文段后，启动**重传定时器**（RTO，Retransmission Timeout）
- RTO 由 RTT 动态估算（如 Jacobson 算法），并非固定值
- 若在 RTO 内未收到对应 ACK，则重传该报文段
- 多次重传失败后，放弃连接并发送 RST 复位信号

```text
发送 seq=100 → 启动定时器 → 超时无 ACK → 重传 seq=100
                              → 收到 ACK=101 → 关闭定时器
```

**2. 基于确认信息的快速重传**

- 接收方收到**失序报文**时，立即发送**重复 ACK**（对最近按序收到的报文确认）
- 发送方连续收到 **3 个重复 ACK**，认为该报文段之后的数据很可能丢失
- **不等定时器到期**，立即重传丢失的报文段
- 比超时重传更早触发，提高网络吞吐量

```text
发送: 1 → 2 → 3 → 4 → 5
接收: 1 ACK2, 2 ACK3, 4(3丢失) ACK3, 5 ACK3, 6 ACK3
      ↑ 连续 3 个 ACK3 → 立即重传 seq=3
```

**两者关系：** 快速重传是超时重传的优化补充。有重复 ACK 时优先快重传；没有足够重复 ACK 时，仍依赖超时重传兜底。

### 面试追问

1. **RTO 是如何计算的？** 基于 RTT 样本做平滑估计（SRTT）并加偏差（RTTVAR），RTO = SRTT + 4 × RTTVAR，随网络状况动态调整。
2. **为什么快速重传是 3 个重复 ACK 而不是 2 个？** 2 个可能是乱序而非丢包；3 个是经验阈值，在误判和响应速度之间取平衡。

## 37. TCP 的拥塞控制机制

**记忆口诀：**「慢启动指数增，拥塞避免线性增，快重传快恢复，cwnd 和 ssthresh 定节奏」

**一句话总结：** TCP 拥塞控制由**慢启动、拥塞避免、快速重传、快速恢复**四个算法协同，通过动态调整拥塞窗口 `cwnd` 和慢启动门限 `ssthresh` 来适应网络容量。

### 详细解答

TCP 拥塞控制的目的是防止过多数据注入网络导致路由器过载。核心变量：

| 变量 | 含义 |
| --- | --- |
| `cwnd` | 拥塞窗口，发送方允许发送但未确认的数据量 |
| `ssthresh` | 慢启动门限，区分慢启动与拥塞避免的分界 |
| `rwnd` | 接收窗口，由接收方通告，用于流量控制 |

**cwnd 与 ssthresh 的关系：**

| 条件 | 使用算法 | cwnd 变化 |
| --- | --- | --- |
| `cwnd < ssthresh` | 慢启动 | 每收到一个 ACK，cwnd + 1（指数增长） |
| `cwnd >= ssthresh` | 拥塞避免 | 每个 RTT，cwnd + 1（线性增长） |
| 检测到拥塞（超时） | 慢启动 | ssthresh = cwnd/2，cwnd = 1，重新慢启动 |
| 检测到拥塞（3 重复 ACK） | 快速恢复 | ssthresh = cwnd/2，cwnd = ssthresh，线性增长 |

**1. 慢启动（Slow Start）**

- 连接初始 `cwnd = 1`（以 MSS 为单位）
- 每收到一个 ACK，`cwnd` 加 1 → 每 RTT 约翻倍（指数增长）
- 先探测网络容量，避免一开始就发送大量数据

**2. 拥塞避免（Congestion Avoidance）**

- 当 `cwnd >= ssthresh` 时进入
- 每个 RTT 将 `cwnd` 加 1（线性增长），使网络不易阻塞
- 无论慢启动还是拥塞避免，只要**超时未收到 ACK**（视为拥塞），就将 `ssthresh = cwnd/2`，`cwnd = 1`，重新慢启动

**3. 快速重传（Fast Retransmit）**

- 收到 3 个重复 ACK，立即重传丢失报文，不必等 RTO
- 表明网络可能未严重拥塞（仍有数据到达接收方）

**4. 快速恢复（Fast Recovery）**

- 触发条件：3 个重复 ACK（而非超时）
- 执行「乘法减小」：`ssthresh = cwnd/2`
- **不执行慢启动**，而是 `cwnd = ssthresh`，直接进入拥塞避免
- 理由：能收到重复 ACK 说明网络未完全拥塞，不必退回到 cwnd=1

```text
正常传输 → 3 dup ACK → 快重传 + 快恢复（cwnd 减半后线性增）
         → 超时     → 超时重传 + 慢启动（cwnd 置 1 重新指数增）
```

### 面试追问

1. **拥塞控制和流量控制有什么区别？** 流量控制解决发送方太快、接收方来不及收的问题（`rwnd`）；拥塞控制解决网络中间节点过载的问题（`cwnd`），两者共同决定实际发送窗口 = min(cwnd, rwnd)。
2. **TCP Tahoe 和 Reno 的区别？** Tahoe 在 3 dup ACK 时只做快重传，然后 cwnd 置 1 慢启动；Reno 增加了快速恢复，3 dup ACK 时 cwnd 减半后线性增长，恢复更快。

## 38. TCP 的流量控制机制

**记忆口诀：**「滑动窗口控速率，接收方通告 rwnd，零窗口停发送」

**一句话总结：** TCP 通过**可变大小的滑动窗口**进行流量控制，接收方在 ACK 中通告剩余缓冲区大小（接收窗口 `rwnd`），发送方据此调整发送速率，零窗口时停止发送。

### 详细解答

流量控制的目的是让发送方发送速度不超过接收方处理能力。TCP 采用**滑动窗口**机制，窗口大小单位为字节。

**工作流程：**

1. **连接建立时**：双方各自分配接收缓冲区，并在报文中通告窗口大小
2. **数据传输中**：接收方在每个 ACK 中携带**窗口通告**（Window Advertisement），告知剩余缓冲区空间
3. **正常情况**：接收方读数据速度跟得上到达速度，每次 ACK 通告正的窗口值
4. **零窗口**：接收方缓冲区满，通告 `rwnd = 0`，发送方**停止发送**
5. **窗口恢复**：接收方处理完数据后重新通告正窗口，发送方继续发送

| 概念 | 说明 |
| --- | --- |
| 发送窗口 | 已发送未确认 + 允许发送但未发送的报文段范围 |
| 接收窗口 rwnd | 接收方缓冲区剩余空间，随 ACK 通告 |
| 零窗口探测 | 发送方定时发送 1 字节探测包，防止死锁 |

**滑动窗口示意：**

```text
| 已发送已确认 | 已发送未确认 | 允许发送 | 不允许发送 |
|←—— 发送窗口 ——→|
                              ↑ rwnd 决定窗口右边界
```

**与拥塞控制的区别：**

| 对比项 | 流量控制 | 拥塞控制 |
| --- | --- | --- |
| 目的 | 保护接收方 | 保护网络 |
| 控制变量 | rwnd（接收窗口） | cwnd（拥塞窗口） |
| 决定方 | 接收方 | 发送方根据网络状况 |

实际发送窗口 = **min(cwnd, rwnd)**，取两者较小值。

**零窗口问题：** 若接收方通告零窗口后崩溃，发送方会一直等待。TCP 通过**持续定时器**（Persist Timer）定期发送 1 字节探测包，避免双方死锁。

### 面试追问

1. **发送窗口和接收窗口是同一个概念吗？** 不是。发送窗口是发送方维护的可发送数据范围；接收窗口 rwnd 是接收方通告的缓冲区剩余空间，发送方据此限制发送速率。
2. **零窗口时发送方完全不能发数据吗？** 正常数据停止发送，但会启动持续定时器发送 1 字节探测包，以检测接收窗口是否恢复。

## 39. TCP 的可靠传输机制

**记忆口诀：**「连续 ARQ 加滑窗，累计确认快重传，选择重传做混合」

**一句话总结：** TCP 可靠传输基于**连续 ARQ + 滑动窗口 + 累计确认 + 超时重传 + 快速重传**，实际实现是滑动窗口协议与选择重传的混合体。

### 详细解答

TCP 在不可靠 IP 层之上，通过多层机制实现可靠、有序的字节流传输。

**核心机制一览：**

| 机制 | 作用 |
| --- | --- |
| 滑动窗口 | 允许连续发送多个报文，提高吞吐 |
| 连续 ARQ | 窗口内报文连续编号，按序确认 |
| 累计确认 | ACK 号表示该序号之前全部按序到达 |
| 超时重传 | 定时器到期重传最早未确认报文 |
| 快速重传 | 3 个重复 ACK 立即重传丢失报文 |

**1. 发送窗口管理**

发送方维护发送窗口，分为四段：

```text
| 已发送已确认 | 已发送未确认 | 允许发送 | 暂不允许发送 |
```

- 发送窗口内所有报文依次发出，并为**最早未确认报文**设置定时器
- 收到 ACK 后窗口向前滑动；定时器超时则重传所有已发送未确认报文，RTO 加倍
- 收到 3 个重复 ACK 时，启用快速重传，在定时器到期前重传所有已发送未确认报文

**2. 累计确认**

- 接收方对**按序到达**的报文返回肯定确认
- 收到**乱序报文**时直接丢弃，返回最近按序报文的 ACK（产生重复 ACK）
- 累计确认保证 ACK 号之前的报文全部按序到达，发送窗口可安全前移

**3. 与纯滑动窗口协议的区别**

标准滑动窗口协议可能缓存乱序报文并重传所有后续报文；TCP 实际实现更接近**选择重传**的混合体：

- 许多实现会**缓存乱序报文**（而非丢弃）
- 重传时通常**只重传一个**丢失报文段，而非整个窗口

**4. 发送窗口大小的决定因素**

发送窗口 = min(**rwnd**, **cwnd**)，同时受接收方处理能力和网络拥塞程度约束。

### 面试追问

1. **累计确认和选择确认（SACK）有什么区别？** 累计确认只告知「该序号之前全部收到」；SACK 在选项字段中明确列出收到的非连续块，帮助发送方精确重传，减少不必要的重传。
2. **TCP 如何保证数据不重复、不丢失？** 序号标识每个字节，确认号告知期望下一个字节；超时重传和快速重传处理丢失；接收方通过序号识别并丢弃重复报文。

## 40. TCP 的三次握手和四次挥手

**记忆口诀：**「三次握手 SYN-ACK-ACK，四次挥手 FIN-ACK-FIN-ACK，全双工分两边关，TIME_WAIT 等 2MSL」

**一句话总结：** 三次握手建立连接并同步初始序号，四次挥手因全双工需双方分别释放；客户端最后进入 TIME_WAIT 等待 2MSL 确保可靠关闭。

### 详细解答

#### 三次握手（建立连接）

```text
客户端                          服务器
  |  ──── SYN, seq=x ──────────→  |  SYN_SENT
  |  ←── SYN+ACK, seq=y, ack=x+1 |  SYN_RCVD
  |  ──── ACK, ack=y+1 ────────→  |  ESTABLISHED
  |                               |  ESTABLISHED
```

| 次序 | 发送方 | 报文 | 状态变化 |
| --- | --- | --- | --- |
| 第 1 次 | 客户端 | SYN, seq=x | CLOSED → SYN_SENT |
| 第 2 次 | 服务器 | SYN+ACK, seq=y, ack=x+1 | LISTEN → SYN_RCVD |
| 第 3 次 | 客户端 | ACK, ack=y+1 | SYN_SENT → ESTABLISHED |
| — | 服务器 | 收到 ACK | SYN_RCVD → ESTABLISHED |

**为什么必须三次握手？**

1. **确认双方收发能力正常**：两次只能确认客户端→服务器方向，第三次 ACK 让服务器确认客户端收到了 SYN+ACK
2. **同步初始序号（ISN）**：双方交换并确认 ISN，保证后续数据按序号正确接收
3. **防止失效连接请求**：若客户端旧的 SYN 延迟到达，两次握手会直接建立连接；三次握手中客户端对无效 SYN+ACK 不回复 ACK，连接不会误建立

**两次握手的问题：** 客户端发出 SYN 后若未收到确认会重传，旧 SYN 可能在连接释放后延迟到达服务器，两次握手下服务器直接建立连接并等待数据，浪费资源。

#### 四次挥手（释放连接）

```text
客户端                          服务器
  |  ──── FIN, seq=u ──────────→  |  FIN_WAIT1
  |  ←── ACK, ack=u+1 ─────────  |  CLOSE_WAIT（半关闭）
  |  FIN_WAIT2                    |
  |  ←── FIN, seq=w ───────────  |  LAST_ACK
  |  ──── ACK, ack=w+1 ────────→  |  CLOSED
  |  TIME_WAIT（2MSL）            |
  |  CLOSED                       |
```

**为什么需要四次挥手？**

TCP 是**全双工**连接，每个方向独立传输。关闭时：

- 客户端发 FIN 表示「我不再发送数据」，但**仍可接收**服务器数据 → 服务器回 ACK，进入 CLOSE_WAIT
- 服务器可能还有数据要发，发完后再发 FIN → 客户端回 ACK

因此 FIN 和 ACK **不能合并**（对比握手时 SYN+ACK 可合并），需要四次。

**TIME_WAIT 状态（2MSL）**

- 客户端发最后一个 ACK 后进入 TIME_WAIT，等待 **2MSL**（Maximum Segment Lifetime）
- 目的：确保最后一个 ACK 能到达服务器；若 ACK 丢失，服务器重传 FIN，客户端仍可响应
- 副作用：大量短连接时占用端口，可通过 `SO_REUSEADDR` 缓解

### 面试追问

1. **SYN 洪水攻击是什么？如何防御？** 攻击者伪造源 IP 大量发 SYN，服务器分配资源后等不到 ACK，半连接队列耗尽。防御：SYN Cookie、增大 backlog、防火墙限速、缩短 SYN_RCVD 超时。
2. **为什么 TIME_WAIT 是 2MSL 而不是 1MSL？** 1MSL 是 ACK 到达服务器的最大时间，再留 1MSL 确保服务器重传的 FIN 能被收到并响应，保证连接可靠关闭。

## 41. 对 WebSocket 的理解

**记忆口诀：**「HTML5 全双工，复用 HTTP 握手，ws/wss 无同源限，双向推送实时通」

**一句话总结：** WebSocket 是 HTML5 提供的**全双工通信**协议，基于 TCP，通过 HTTP 升级握手建立持久连接，支持服务器和客户端双向主动推送数据。

### 详细解答

WebSocket 属于应用层协议，解决了 HTTP 半双工、无法服务端主动推送的局限。

**核心特点：**

| 特性 | 说明 |
| --- | --- |
| 全双工通信 | 双方可同时发送和接收，实时性更强 |
| 持久连接 | 一次握手后保持连接，无需反复 HTTP 请求 |
| 数据格式 | 支持文本和二进制帧 |
| 协议标识 | `ws://`（明文）或 `wss://`（TLS 加密） |
| 默认端口 | 80 / 443，与 HTTP 相同 |
| 无同源限制 | 客户端可与任意 WebSocket 服务器通信 |
| HTTP 兼容 | 握手阶段使用 HTTP 协议，易于穿透代理 |

**工作原理：**

1. 客户端发起 HTTP Upgrade 请求
2. 服务器返回 101 Switching Protocols
3. 连接升级为 WebSocket，后续通过帧（Frame）双向传输
4. 服务器可主动向客户端推送，客户端也可主动发送

**握手请求示例：**

```http
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

**客户端使用示例：**

```js
const ws = new WebSocket('ws://localhost:9999');

ws.onopen = () => {
  console.log('连接已建立');
  ws.send('hello');
};

ws.onmessage = (event) => {
  console.log('收到消息:', event.data);
};

ws.onclose = () => {
  console.log('连接已关闭');
};

ws.onerror = (error) => {
  console.error('连接错误:', error);
};
```

**适用场景：** 即时聊天、实时通知、协同编辑、在线游戏、股票行情推送等需要低延迟双向通信的场景。

### 面试追问

1. **WebSocket 和 HTTP 长轮询有什么区别？** 长轮询每次仍是独立 HTTP 请求/响应，有头部开销和连接建立成本；WebSocket 握手一次后通过轻量帧通信，双向实时，开销更小。
2. **WebSocket 心跳机制有什么作用？** 定期发送 ping/pong 帧检测连接是否存活，防止中间代理（NAT、负载均衡）因空闲超时断开连接。

## 42. 即时通讯的实现：短轮询、长轮询、SSE 和 WebSocket 间的区别？

**记忆口诀：**「性能 WebSocket 最强，兼容短轮询最好，SSE 单向长连接，长轮询挂起等数据」

**一句话总结：** 四种方案均基于 HTTP（WebSocket 握手后独立协议），性能上 **WebSocket > SSE > 长轮询 > 短轮询**，浏览器兼容性则相反。

### 详细解答

| 方案 | 通信方向 | 连接方式 | 性能 | 兼容性 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| 短轮询 | 客户端拉取 | 定时 HTTP 请求 | 最差 | 最好 | 兼容性要求极高 |
| 长轮询 | 客户端拉取 | HTTP 长连接挂起 | 较差 | 较好 | 中等实时性 |
| SSE | 服务器推送 | HTTP 长连接流 | 中等 | 中等（IE 不支持） | 单向推送（通知、日志） |
| WebSocket | 双向 | 独立全双工协议 | 最好 | 较差 | 聊天、游戏、协作 |

**1. 短轮询（Short Polling）**

- 浏览器**每隔固定时间**（如 1-3 秒）发 HTTP 请求
- 服务器不论有无新数据都立即响应
- 优点：实现简单
- 缺点：大量无效请求，浪费带宽和服务器资源，实时性差

```js
setInterval(async () => {
  const res = await fetch('/api/messages');
  const data = await res.json();
  updateUI(data);
}, 2000);
```

**2. 长轮询（Long Polling）**

- 客户端发请求后，服务器**挂起连接**，有数据或超时后才响应
- 客户端收到响应后立即发起下一次长轮询
- 优点：减少无效请求次数
- 缺点：连接挂起占用资源，仍反复建立 HTTP 连接

**3. SSE（Server-Sent Events）**

- 基于 HTTP，服务器以**流（text/event-stream）** 持续向客户端推送
- **单向通信**：仅服务器 → 客户端
- 优点：原生 API（`EventSource`），自动重连，比轮询高效
- 缺点：不支持 IE/Edge 旧版，客户端发消息需另发 HTTP 请求

```js
const es = new EventSource('/api/events');
es.onmessage = (e) => console.log(e.data);
```

**4. WebSocket**

- HTML5 独立协议，**全双工**，双方可主动推送
- 优点：性能最好，实时性最强，帧开销小
- 缺点：服务端配置较复杂，旧浏览器不支持

**选型建议：**

- 强实时双向通信 → WebSocket
- 单向推送（通知、监控） → SSE
- 需兼容老旧浏览器 → 长轮询 / 短轮询
- 前三个方案均基于 HTTP；WebSocket 握手用 HTTP，之后切换为独立协议

### 面试追问

1. **SSE 和 WebSocket 怎么选？** 只需服务器向客户端推送（如新闻 feed、日志）选 SSE，实现简单且自动重连；需要双向实时交互（聊天、游戏）选 WebSocket。
2. **长轮询相比短轮询优化了什么？** 减少了无数据时的无效请求次数，服务器有数据才响应，但每条消息仍需一次完整的 HTTP 请求-响应周期。

## 43. 说一下 HTTP 3.0？

**记忆口诀：**「UDP 之上 QUIC 跑，TLS1.3 集成好，多路复用无队阻，0-1 RTT 握手快」

**一句话总结：** HTTP/3 基于 **UDP 上的 QUIC 协议**，集成 TLS 1.3、多路复用无队头阻塞、连接迁移，实现 **0~1 RTT** 快速握手。

### 详细解答

HTTP/3 是 HTTP 协议的最新主要版本，底层不再使用 TCP，而是基于 **QUIC**（Quick UDP Internet Connections）——在 UDP 之上实现了类似 TCP 的可靠传输能力。

**HTTP 版本演进：**

| 版本 | 传输层 | 主要特性 |
| --- | --- | --- |
| HTTP/1.1 | TCP | 持久连接、管道化（队头阻塞） |
| HTTP/2 | TCP | 二进制分帧、多路复用（TCP 层仍队头阻塞） |
| HTTP/3 | QUIC(UDP) | 传输层多路复用、0-RTT、连接迁移 |

**QUIC 核心特性：**

**1. 流量控制与传输可靠性**

QUIC 在 UDP 之上增加了可靠传输层，提供数据包重传、拥塞控制等 TCP 特性，同时保留 UDP 的低延迟优势。

**2. 集成 TLS 1.3 加密**

加密集成在 QUIC 协议内部（非叠加），减少握手 RTT。首次连接 1-RTT，后续可 **0-RTT** 恢复连接。

**3. 多路复用，无队头阻塞**

- HTTP/2 在 TCP 上单连接多 Stream，但 TCP 丢包会阻塞所有 Stream（TCP 层队头阻塞）
- QUIC 每个 Stream 独立传输，一个 Stream 丢包**不影响其他 Stream**

```text
HTTP/2 (TCP): Stream A 丢包 → 阻塞 Stream B、C
HTTP/3 (QUIC): Stream A 丢包 → 仅 A 等待重传，B/C 正常
```

**4. 快速握手（0~1 RTT）**

- 基于 UDP，无需 TCP 三次握手
- 结合 TLS 1.3，首次连接约 1-RTT 完成加密握手
- 会话恢复时可达 **0-RTT** 发送数据

**5. 连接迁移**

QUIC 用 Connection ID 标识连接而非四元组，网络切换（如 WiFi → 4G）时连接可无缝迁移，不断连。

**浏览器支持：** Chrome、Firefox、Edge 等已默认支持 HTTP/3（通常通过 Alt-Svc 头协商升级）。

### 面试追问

1. **HTTP/3 为什么选 UDP 而不是继续优化 TCP？** TCP 内置于操作系统内核，升级迭代困难；UDP 在用户态实现 QUIC，可快速迭代；且 TCP 队头阻塞难以在应用层解决。
2. **0-RTT 有什么安全风险？** 0-RTT 数据可能被重放攻击，通常只用于幂等的安全请求，非幂等操作应等握手完成后再发送。

## 44. 正向代理和反向代理的区别

**记忆口诀：**「正向代理客户端，反向代理服务器，翻墙用正向，负载均衡用反向」

**一句话总结：** **正向代理**代表客户端向外部发请求（隐藏客户端）；**反向代理**代表服务器接收客户端请求（隐藏后端服务器）。

### 详细解答

| 对比维度 | 正向代理（Forward Proxy） | 反向代理（Reverse Proxy） |
| --- | --- | --- |
| 代理对象 | 客户端 | 服务器 |
| 客户端是否感知 | 需配置代理 | 无感知，以为在访问代理 |
| 典型用途 | 翻墙、访问受限资源、缓存加速 | 负载均衡、SSL 卸载、隐藏真实 IP |
| 部署位置 | 客户端侧或内网出口 | 服务器侧入口 |
| 代表谁 | 代表客户端发出请求 | 代表服务器接收请求 |

**正向代理：**

- 客户端**主动配置**代理服务器地址
- 请求先发到代理，由代理转发到目标服务器
- 目标服务器看到的是**代理的 IP**，不知道真实客户端
- 场景：公司内网通过代理访问外网、科学上网、绕过 IP 封禁

```text
客户端 → 正向代理 → 互联网 → 目标服务器
         （代理知道客户端是谁，服务器不知道）
```

**反向代理：**

- 客户端**无需配置**，直接访问代理地址（如 `www.example.com`）
- 代理将请求转发到内部一台或多台真实服务器
- 客户端不知道后端真实服务器 IP 和数量
- 场景：Nginx 负载均衡、CDN、API 网关、SSL 终止

```text
客户端 → 反向代理 → 内部服务器 A/B/C
         （客户端不知道后端是谁，代理代表服务器响应）
```

**记忆技巧：** 「正」= 正向帮**正**客户端出去；「反」= **反**过来帮服务器接客。

### 面试追问

1. **Nginx 做反向代理时如何实现负载均衡？** 通过 upstream 配置多个后端 server，配合轮询、权重、ip_hash、least_conn 等策略分发请求。
2. **正向代理和 VPN 有什么区别？** 正向代理通常只代理特定协议（如 HTTP/SOCKS），VPN 在网络层建立隧道，代理所有流量，加密范围更广。

## 45. 浏览器缓存策略

**记忆口诀：**「Service Worker 最优先，强缓存不请求，协商缓存问服务器，Expires 让位 Cache-Control」

**一句话总结：** 浏览器缓存分四个层级，策略分**强缓存**（不发请求）和**协商缓存**（发请求验证），通过 HTTP 响应头控制；无策略时用启发式算法估算缓存时间。

### 详细解答

#### 缓存层级（优先级从高到低）

| 层级 | 特点 |
| --- | --- |
| Service Worker | 独立线程，可编程控制缓存策略，持久化，优先级最高 |
| Memory Cache | 内存缓存，读取快，关闭页面即释放 |
| Disk Cache | 磁盘缓存，容量大，读取慢，持久化 |
| Push Cache | HTTP/2 推送缓存，会话级，关闭连接即失效 |

#### 强缓存（不发请求，直接使用本地缓存）

| 响应头 | 版本 | 说明 |
| --- | --- | --- |
| `Expires` | HTTP/1.0 | 绝对过期时间，受本地时间影响，可能因改时间失效 |
| `Cache-Control` | HTTP/1.1 | 优先级更高，如 `max-age=300` 表示 5 分钟内强缓存 |

```http
Cache-Control: max-age=31536000, public
Expires: Wed, 21 Oct 2026 07:28:00 GMT
```

常用 `Cache-Control` 值：`max-age`、`no-cache`（需协商）、`no-store`（不缓存）、`public`、`private`。

#### 协商缓存（强缓存失效后，发请求验证）

| 响应头 / 请求头 | 版本 | 验证方式 | 精度 |
| --- | --- | --- | --- |
| `Last-Modified` / `If-Modified-Since` | HTTP/1.0 | 文件最后修改时间 | 秒级，可能不准 |
| `ETag` / `If-None-Match` | HTTP/1.1 | 文件内容哈希/版本号 | 更精确 |

**Last-Modified 流程：**

1. 首次响应带 `Last-Modified: Wed, 21 Oct 2025 07:28:00 GMT`
2. 再次请求带 `If-Modified-Since: Wed, 21 Oct 2025 07:28:00 GMT`
3. 未修改 → 304 Not Modified；已修改 → 200 + 新资源

**ETag 流程：**

1. 首次响应带 `ETag: "33a64df551425fcc55e4d42a148795d9f25f89d4"`
2. 再次请求带 `If-None-Match: "33a64df551425fcc55e4d42a148795d9f25f89d4"`
3. 匹配 → 304；不匹配 → 200 + 新 ETag

#### 无缓存策略时的启发式算法

未设置任何缓存头时，浏览器启发式估算：

```text
缓存时间 ≈ (Date - Last-Modified) × 10%
```

#### 完整请求决策流程

```text
请求资源 → Service Worker 拦截？
         → 强缓存有效？ → 200 from cache
         → 协商缓存 → 304 / 200
         → 网络请求
```

### 面试追问

1. **`Cache-Control: no-cache` 和 `no-store` 有什么区别？** `no-cache` 可以缓存但每次使用前必须向服务器验证（协商缓存）；`no-store` 完全不存储任何缓存。
2. **ETag 为什么比 Last-Modified 更精确？** Last-Modified 只能精确到秒，1 秒内多次修改无法区分；ETag 基于内容生成，内容变则 ETag 变，且不受服务器/客户端时钟影响。

## 46. cookie、localStorage、sessionStorage、IndexedDB 的区别？

**记忆口诀：**「Cookie 4KB 随请求走，local 持久 session 标签页，IndexedDB 大且结构化」

**一句话总结：** Cookie 容量最小但自动随 HTTP 请求发送，适合登录态；localStorage 持久化、sessionStorage 标签页级临时存储；IndexedDB 适合大量结构化离线数据。

### 详细解答

| 对比维度 | Cookie | localStorage | sessionStorage | IndexedDB |
| --- | --- | --- | --- | --- |
| 存储大小 | 约 4KB | 约 5MB | 约 5MB | 通常 50MB+，可申请更大 |
| 生命周期 | 可设过期时间，默认会话级 | 持久化，手动清除 | 标签页/窗口关闭即清除 | 持久化，手动清除 |
| 与服务器通信 | 每次 HTTP 请求自动携带 | 不参与 HTTP 请求 | 不参与 HTTP 请求 | 不参与 HTTP 请求 |
| 作用域 | 可设 Domain/Path，支持子域 | 同源策略 | 同源 + 同标签页 | 同源策略 |
| API 类型 | 字符串键值对，`document.cookie` | 字符串键值对，同步 API | 字符串键值对，同步 API | 结构化数据，异步 API |
| 典型用途 | 登录 Token、用户偏好 | 主题设置、持久配置 | 表单草稿、页面间临时数据 | PWA 离线、大量日志 |

**1. Cookie**

- 由服务器通过 `Set-Cookie` 写入，浏览器后续请求自动携带
- 容量约 4KB，可通过 `Expires`/`Max-Age`、`Domain`、`Path`、`Secure`、`HttpOnly` 精细控制
- `HttpOnly` 防止 JS 读取，降低 XSS 窃取风险

**2. localStorage**

- HTML5 持久化存储，关闭浏览器不丢失
- 不参与 HTTP 请求，适合前端长期配置

```js
localStorage.setItem('theme', 'dark');
const theme = localStorage.getItem('theme');
```

**3. sessionStorage**

- API 与 localStorage 相同，但生命周期绑定当前标签页
- 不同标签页数据不共享，适合单次会话临时数据

**4. IndexedDB**

- 浏览器内置 NoSQL 数据库，支持对象、数组等结构化数据
- 异步 API，不阻塞主线程，适合 PWA 离线缓存

### 面试追问

1. **Cookie 和 localStorage 都能存登录 Token，怎么选？** 敏感 Token 优先 HttpOnly Cookie（防 XSS 读取）；若需前端 JS 访问或非 HTTP 场景，可用 localStorage，但 XSS 风险更高，需配合 CSP 等防护。
2. **sessionStorage 和 session Cookie 有什么区别？** sessionStorage 随标签页关闭清除；session Cookie 无 Expires/Max-Age，浏览器关闭时清除，但同一浏览器所有标签页共享。

## 47. cookie 里面都包含什么属性？

**记忆口诀：**「Domain Path 定范围，Expires Max-Age 管寿命，Secure 限 HTTPS，HttpOnly 防脚本」

**一句话总结：** Cookie 通过 **Domain、Path、Expires/Max-Age、Secure、HttpOnly** 等属性控制作用范围、生命周期和安全策略。

### 详细解答

| 属性 | 作用 | 示例 |
| --- | --- | --- |
| **Domain** | 指定哪些主机可访问 Cookie | `Domain=.example.com` 子域共享 |
| **Path** | 指定 URL 路径前缀才携带 | `Path=/admin` 仅 /admin 下发送 |
| **Expires** | 绝对过期时间（HTTP/1.0） | `Expires=Wed, 21 Oct 2026 07:28:00 GMT` |
| **Max-Age** | 相对过期秒数（HTTP/1.1，优先级更高） | `Max-Age=3600` 一小时后过期 |
| **Secure** | 仅 HTTPS 连接时发送 | 防止明文 HTTP 泄露 |
| **HttpOnly** | 禁止 JS 通过 `document.cookie` 访问 | 防 XSS 窃取 Cookie |
| **SameSite** | 限制跨站请求时是否携带 | `Strict` / `Lax` / `None`，防 CSRF |

**属性详解：**

**1. Domain**

- 设置浏览器允许哪些主机访问该 Cookie
- 设为 `.example.com` 时，`www.example.com`、`api.example.com` 均可访问
- 不能设为不同主域

**2. Path**

- 请求 URL 路径匹配 Path 前缀时才携带 Cookie
- 默认 Path 为设置 Cookie 时的目录路径

**3. Expires / Max-Age**

- 未设置时，Cookie 为**会话级**，浏览器关闭即失效
- `Max-Age=0` 表示立即删除

**4. Secure**

- 仅当请求为 HTTPS 时才发送，防止中间人窃听

**5. HttpOnly**

- 服务端设置后，客户端 JS 无法读取，**防 XSS 攻击**窃取 Session
- 是安全 Cookie 的必备属性

**Set-Cookie 示例：**

```http
Set-Cookie: sessionId=abc123; Domain=.example.com; Path=/; Max-Age=3600; Secure; HttpOnly; SameSite=Lax
```

### 面试追问

1. **Domain 设为 `.example.com` 和 `www.example.com` 有什么区别？** 前者 `.example.com` 包括所有子域；后者仅 `www.example.com` 可访问，其他子域不可共享。
2. **SameSite 的三个值分别什么含义？** `Strict` 完全禁止跨站携带；`Lax` 允许顶级导航 GET 携带（默认）；`None` 允许跨站携带，但必须配合 `Secure`。

## 48. Cookie 能跨域吗？如何设置？

**记忆口诀：**「默认不跨域，CORS 配凭证，Allow-Origin 指定源，withCredentials 开」

**一句话总结：** Cookie 默认不跨域共享，跨域请求携带 Cookie 需服务端设置 `Access-Control-Allow-Credentials: true` 和具体 `Access-Control-Allow-Origin`，前端开启 `withCredentials`。

### 详细解答

**同源 Cookie 共享规则：**

- **同域名**下，Cookie 默认可以共享（受 Domain/Path 限制）
- **不同域名**下，默认不共享、不发送

**跨域携带 Cookie 的配置：**

需**前后端同时配置**，缺一不可：

| 端 | 配置 |
| --- | --- |
| 服务端 | `Access-Control-Allow-Credentials: true` |
| 服务端 | `Access-Control-Allow-Origin: https://client.com`（**不能为 `*`**） |
| 客户端 | `credentials: 'include'` 或 `withCredentials: true` |

**前端示例：**

```js
// fetch
fetch('https://api.example.com/user', {
  credentials: 'include'
});

// axios
axios.defaults.withCredentials = true;
axios.get('https://api.example.com/user');

// XMLHttpRequest
const xhr = new XMLHttpRequest();
xhr.withCredentials = true;
xhr.open('GET', 'https://api.example.com/user');
```

**后端示例（Express）：**

```js
app.use(cors({
  origin: 'https://client.com',  // 必须指定具体域名，不能 *
  credentials: true
}));
```

**注意事项：**

1. `Access-Control-Allow-Origin` 为 `*` 时，不能同时设置 `Allow-Credentials: true`
2. 跨域 Set-Cookie 需配合 SameSite=None; Secure（现代浏览器要求）
3. 子域共享用 `Domain=.example.com`，不是 CORS 跨域，而是 Cookie Domain 属性

### 面试追问

1. **为什么 Allow-Origin 不能设为 `*` 同时携带 Cookie？** 安全考虑：`*` 表示任意源都可访问，若允许携带 Cookie 则任何恶意网站都能发起带凭证请求，造成 CSRF 和数据泄露。
2. **跨域请求如何写入 Cookie？** 服务端在跨域响应中返回 `Set-Cookie`，浏览器在 Allow-Credentials 和正确 Origin 配置下会接受；Modern 浏览器要求 SameSite=None; Secure。

## 49. 对 CORS 的理解

**记忆口诀：**「简单请求直接发，非简单 OPTIONS 预检，Allow-Origin 控跨域，Max-Age 缓存预检」

**一句话总结：** CORS（跨域资源共享）是浏览器的一种安全机制，需服务器和浏览器共同支持；分为**简单请求**（直接发送）和**非简单请求**（先 OPTIONS 预检）。

### 详细解答

**跨域条件：** 协议、域名、端口任一不同即为跨域，浏览器会拦截响应 unless 服务端允许。

**简单请求（不触发预检）：**

需同时满足：

1. 方法为 `GET`、`HEAD`、`POST` 之一
2. 请求头仅包含：Accept、Accept-Language、Content-Language、Content-Type（限三种值：`application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`）

**简单请求流程：**

```text
浏览器 → 带 Origin 头直接发请求 → 服务器
       ← Access-Control-Allow-Origin: http://client.com ←
```

响应头至少包含 `Access-Control-Allow-Origin`；若需 Cookie 还需 `Access-Control-Allow-Credentials: true`。

**非简单请求（触发预检）：**

方法为 PUT/DELETE/PATCH 或携带自定义头时，浏览器先发 **OPTIONS 预检**：

```text
浏览器 → OPTIONS（Origin + Request-Method + Request-Headers）
服务器 → Access-Control-Allow-Origin
         Access-Control-Allow-Methods: GET, POST, PUT
         Access-Control-Allow-Headers: X-Custom-Header
         Access-Control-Allow-Credentials: true
         Access-Control-Max-Age: 1728000
浏览器 → 预检通过 → 发正式请求
```

**预检缓存：**

`Access-Control-Max-Age: 1728000` 表示预检结果缓存 1728000 秒，期间相同 URL 不再发 OPTIONS，减少性能损耗。

**CORS 与 Cookie：**

传递 Cookie 需满足三条件：`withCredentials: true` + `Allow-Credentials: true` + `Allow-Origin` 为具体域名（非 `*`）。

### 面试追问

1. **CORS 是前端还是后端的问题？** 本质是浏览器安全策略，需服务端返回正确的 CORS 响应头；后端不配置，浏览器会拦截跨域响应，前端无法绕过（除 JSONP 等方案）。
2. **预检请求失败返回 403 是什么原因？** 服务器未正确响应 OPTIONS，或 `Allow-Methods`/`Allow-Headers` 未包含实际请求的方法和头，浏览器判定预检失败。

## 50. 如何解决跨域问题？

**记忆口诀：**「CORS 最正统，JSONP 只 GET，postMessage 窗口通，代理 nginx Node，iframe 老方案，WebSocket 不受限」

**一句话总结：** 跨域方案包括 **CORS**、**JSONP**、**postMessage**、**nginx/Node 代理**、**iframe 技巧**（domain/hash/name）、**WebSocket** 等，现代项目首选 CORS 或开发代理。

### 详细解答

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| CORS | 服务端设置响应头 | 标准、安全、支持所有方法 | 需服务端配合 |
| JSONP | `<script>` 无跨域限制 | 兼容老浏览器 | 仅 GET、不安全（XSS） |
| postMessage | HTML5 窗口通信 API | 安全、灵活 | 需窗口/iframe 关系 |
| nginx/Node 代理 | 同源代理转发 | 开发/生产通用 | 需额外部署 |
| document.domain | 主域相同子域不同 | 简单 | 仅限同主域 |
| WebSocket | 协议无同源限制 | 全双工 | 需 WS 服务端 |

**1. CORS（推荐）**

服务端配置 `Access-Control-Allow-Origin` 等头，见 Q49。

**2. JSONP**

利用 `<script>` 标签不受同源限制，通过 callback 参数回调：

```js
function handleCallback(res) {
  console.log(res);
}
const script = document.createElement('script');
script.src = 'http://api.example.com/data?callback=handleCallback';
document.head.appendChild(script);
// 服务端返回: handleCallback({"name": "test"})
```

**3. postMessage**

```js
// 发送方
iframe.contentWindow.postMessage(JSON.stringify(data), 'https://target.com');

// 接收方
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://trusted.com') return;
  console.log(JSON.parse(e.data));
});
```

**4. nginx 反向代理**

```nginx
location /api/ {
  proxy_pass http://backend.server.com/;
  add_header Access-Control-Allow-Origin http://localhost:3000;
  add_header Access-Control-Allow-Credentials true;
}
```

**5. Node 中间件代理**

```js
const { createProxyMiddleware } = require('http-proxy-middleware');
app.use('/api', createProxyMiddleware({
  target: 'http://backend.server.com',
  changeOrigin: true
}));
```

**6. document.domain + iframe**

主域相同、子域不同时，双方设置 `document.domain = 'example.com'` 实现同域。

**7. WebSocket**

WebSocket 协议本身不受同源策略限制，建立 ws/wss 连接即可跨域通信。

### 面试追问

1. **开发环境 webpack devServer 如何配跨域代理？** 在 `devServer.proxy` 中配置目标服务器，`changeOrigin: true`，前端请求 `/api` 同源发到 devServer，由 devServer 转发到后端，浏览器无跨域问题。
2. **JSONP 为什么只能 GET？** 因为 JSONP 依赖 `<script src="...">` 发起请求，script 标签只能 GET，无法 POST 或设置自定义头。

## 51. Content-Type 值有哪些？

**记忆口诀：**「form-urlencoded 默认表单，multipart 传文件，json 传对象，xml 传结构化」

**一句话总结：** 常见 Content-Type 有 **application/x-www-form-urlencoded**（默认表单）、**multipart/form-data**（文件上传）、**application/json**（JSON 数据）、**text/xml**（XML 数据）。

### 详细解答

Content-Type 指定请求/响应体的 MIME 类型，告诉对方如何解析数据。

| Content-Type | 使用场景 | 数据格式 |
| --- | --- | --- |
| `application/x-www-form-urlencoded` | 浏览器默认表单提交 | `key1=val1&key2=val2`，URL 编码 |
| `multipart/form-data` | 文件上传、含文件的表单 | 多部分 boundary 分隔 |
| `application/json` | REST API、前后端分离 | JSON 字符串 |
| `text/xml` | SOAP、传统 XML 接口 | XML 文档 |

**1. application/x-www-form-urlencoded**

- 浏览器 `<form>` 默认 enctype
- 数据放在 body，键值对 URL 编码

```http
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=admin&password=123456
```

**2. multipart/form-data**

- 上传文件时必须使用
- 每部分用 boundary 分隔，可混合文本和文件

```http
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary

------WebKitFormBoundary
Content-Disposition: form-data; name="file"; filename="a.png"
Content-Type: image/png

(二进制数据)
------WebKitFormBoundary--
```

**3. application/json**

- 现代 API 最常用
- body 为序列化 JSON 字符串

```http
POST /api/users HTTP/1.1
Content-Type: application/json

{"name": "张三", "age": 25}
```

**4. text/xml**

- 传输 XML 格式数据，SOAP 等场景

**服务器响应常见类型：** `text/html`、`application/json`、`application/xml`、`image/png` 等。

### 面试追问

1. **上传文件为什么必须用 multipart/form-data？** urlencoded 只能传文本且需 URL 编码，无法高效传输二进制；multipart 每部分独立 Content-Type，适合混合文本与文件。
2. **GET 请求需要设置 Content-Type 吗？** 通常不需要，GET 无请求体；POST/PUT 等有 body 的请求必须正确设置，否则服务端无法解析。

## 52. XSS 和 CSRF 是什么？如何防御？

**记忆口诀：**「XSS 注入恶意脚本，CSRF 借用用户身份；转义 CSP HttpOnly 防 XSS，Token SameSite 防 CSRF」

**一句话总结：** **XSS** 是跨站脚本注入，攻击者在页面执行恶意脚本；**CSRF** 是跨站请求伪造，利用用户 Cookie 冒充身份；分别通过输出转义/CSP/HttpOnly 和 Token/SameSite/同源检测防御。

### 详细解答

#### XSS（Cross-Site Scripting，跨站脚本攻击）

**本质：** 网站未过滤恶意代码，与正常代码混合，浏览器无法区分，执行攻击者注入的脚本。

**攻击类型：**

| 类型 | 恶意代码存储位置 | 触发方式 |
| --- | --- | --- |
| 存储型 | 目标服务器数据库 | 用户访问含恶意脚本的页面 |
| 反射型 | URL 参数中 | 用户点击恶意链接 |
| DOM 型 | 不经过服务器，前端 URL 参数等 | 前端 JS 取出并执行 |

**危害：** 窃取 Cookie/localStorage、DOS、篡改页面、流量劫持。

**防御措施：**

| 措施 | 说明 |
| --- | --- |
| 输入/输出转义 | 对 `<`、`>`、`"`、`'`、`&` 等转义，或使用 `textContent` 代替 `innerHTML` |
| CSP | Content-Security-Policy 白名单，限制脚本来源 |
| HttpOnly Cookie | JS 无法读取 Session Cookie |
| 验证码 | 关键操作需人机验证 |

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

#### CSRF（Cross-Site Request Forgery，跨站请求伪造）

**本质：** 利用 Cookie 在同源请求中自动携带的特性，诱导已登录用户访问恶意页面，冒充用户向目标站点发起请求。

**攻击类型：**

- GET 型：`<img src="https://bank.com/transfer?to=hacker&amount=1000">`
- POST 型：恶意页面隐藏表单自动提交
- 链接型：`<a href="https://bank.com/transfer?...">` 诱导点击

**防御措施：**

| 措施 | 说明 |
| --- | --- |
| CSRF Token | 服务端生成随机 Token，请求时验证，攻击者无法获取 |
| SameSite Cookie | `Strict`/`Lax` 限制跨站携带 Cookie |
| 双重 Cookie | 服务端注入 Cookie，请求参数中带相同值验证 |
| 同源检测 | 检查 `Origin`/`Referer` 头 |
| 验证码 | 关键操作二次确认 |

```js
// CSRF Token 示例
// 服务端: res.cookie('csrfToken', token);
// 前端: headers: { 'X-CSRF-Token': getCookie('csrfToken') }
```

**XSS vs CSRF：**

| 对比 | XSS | CSRF |
| --- | --- | --- |
| 攻击目标 | 用户浏览器 | 服务器（冒充用户） |
| 利用漏洞 | 网站未过滤脚本 | 网站未验证请求来源 |
| 是否需要用户登录 | 否 | 是（需有效 Cookie） |
| 关系 | XSS 可窃取 Token，导致 CSRF 防御失效 | — |

### 面试追问

1. **CSP 如何防御 XSS？** 通过白名单限制脚本只能从指定源加载，内联脚本需 nonce 或 hash，阻止攻击者注入的恶意脚本执行。
2. **SameSite=Strict 和 Lax 在实际中怎么选？** 严格安全用 Strict（完全禁止跨站 Cookie）；一般网站默认 Lax，允许从外链跳转 GET 时带 Cookie，平衡安全与体验（如 OAuth 回调）。
